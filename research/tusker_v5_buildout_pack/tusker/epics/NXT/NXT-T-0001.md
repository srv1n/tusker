# NXT-T-0001 · Freeze the v5 architecture and compatibility boundary

## Intent

Lock the final v5 decisions into repo-local canon so the implementation team is not building against three competing proposals.

## Scope

In:
- codify the final v5 decisions in repo-local docs
- document the compatibility boundary between legacy Tusker and v5
- record what is deliberately transitional versus final

Out:
- shipping parser or CLI code
- performing the migration itself
- rewriting the docs exporter

## Acceptance contract

| # | Outcome | Proof required | Docs impact |
|---|---|---|---|
| 1 | One canonical v5 spec exists inside the repo-local docs surface. | Spec page committed and linked from the epic. | spec/v5-overview |
| 2 | One explicit migration plan exists with field mapping, ID collision policy, and doc-page migration rules. | Migration page committed and linked from the epic. | spec/migration-v5 |
| 3 | The implementation backlog references the canonical docs instead of re-arguing the architecture in every task. | Epic and tasks link only to the canonical pages. | spec/v5-overview, spec/migration-v5 |

## Constraints

- Do not invent a fourth model. Choose and record the transitional model that fits the current codebase.
- Call out every place where v5 is intentionally constrained by today's docs exporter or note layout.

## Escalate if

- There is evidence that a current repo invariant makes the chosen transitional model impossible without a separate break-glass phase.
- The team wants to re-open the event-sourced-state question.
