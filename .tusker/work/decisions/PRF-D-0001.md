# PRF-D-0001 · Event-driven reconcile architecture: fsnotify vs push vs longer poll

## Decision

Proposed (needs human ratification; direction set by Sarav 2026-07-11): **write-notify as the primary trigger, staggered stat-gated sweep as the safety net, no fixed fast poll.** Markdown stays source of truth; storage is not re-architected.

- **Primary — CLI/runner write-notify:** all agent/runner task mechanics already go through the `tusker` CLI. A CLI mutation marks the affected project dirty (control socket `daemon_control.go:45`, or a dirty-seq in the shared SQLite store) and the daemon immediately reconciles *only that project*. Updates land faster than today's 5s poll, at a fraction of the cost.
- **Safety net — staggered per-project rescan every 2–5 minutes:** catches out-of-band writers the CLI cannot see (Obsidian/direct edits, git checkout/merge/recovery rewrites, misbehaving agents writing markdown directly). Projects are offset so sweeps never coincide (no thundering herd). With PRF-T-0003's stat-gated scan, an unchanged sweep is milliseconds of `stat` calls.
- **Already push-shaped:** run/lease/heartbeat/attempt state lives in the SQLite runtime store, not markdown — live run status in serve never required vault scanning. Only note frontmatter needs the notify/sweep machinery.
- **Attention tier (Sarav, 2026-07-11):** the serve UI gets a per-project manual "Refresh now" (targeted reconcile via the notify path, rate-limited), and a project with an open/expanded view gets a boosted per-project sweep cadence (~15–30s) while a scoped client is attached, reverting on disconnect. Freshness follows where the human is actually looking; everything unattended stays on the slow sweep.

## Context

The daemon burns ~1.3 cores continuously because every 5s tick fully re-reads and re-parses every registered vault (~2,750 md files across 16 live projects) with zero change detection, and the serve layer re-broadcasts/rebuilds regardless of change (evidence in PRF-T-0001..0005). Sarav is open to re-architecting storage if needed. Options considered:

1. **Longer poll only** (PRF-T-0001): trivial, but each tick still costs the same; just less frequent. Mitigation, not a fix.
2. **Stat-gated incremental poll** (PRF-T-0003): keep polling, but a tick stats files and only re-parses changed ones. ~2,750 `stat` calls is milliseconds; idle ticks become near-free. No new dependencies, no platform edge cases, works with any editor (Obsidian, agents, git checkouts).
3. **fsnotify/FSEvents event-driven**: zero idle cost, but no watcher infrastructure exists in the codebase today; macOS FSEvents coalescing, watch-descriptor limits across 16+ roots, symlinked vault mounts, and atomic-rename editor writes all add correctness risk.
4. **Push-based invalidation**: Tusker CLI mutations and runners already go through the daemon's store/control socket; writers could notify the daemon which project is dirty, with a slow safety-net poll (60s+) catching out-of-band edits (human editing markdown directly).
5. **Storage re-architecture (SQLite as primary)**: abandons the file-first/Obsidian-compatible model that the whole product is built around. Not justified — the measured cost is re-parsing unchanged files, not markdown itself.

Recommendation: **4 primary + 2 as safety net** — CLI/runner write-notify drives immediate targeted per-project reconcile (near-real-time for everything that matters during review); the stat-gated incremental index (PRF-T-0003) makes the staggered 2–5 minute background sweep nearly free. Sarav's key insight (2026-07-11): since all agent mutations flow through the CLI, the notify path covers the review-latency requirement, so the sweep interval can be minutes, not seconds. Option 3 (fsnotify) revisit only if out-of-band edit latency ever becomes a real complaint; option 5 rejected.

Implication for PRF-T-0001: the interval work there is the *safety-net sweep* cadence plus stagger offsets, not a user-facing responsiveness knob — responsiveness comes from write-notify.

## Work streams

- PRF-T-0006 (CLI write-notify → targeted reconcile) — the primary trigger; core of this decision.
- PRF-T-0001 (poll default/override) — reframed as the safety-net sweep cadence + stagger offsets.
- PRF-T-0002 (registry hygiene) — shrinks the constant factor.
- PRF-T-0003 (incremental index) — makes the safety-net sweep nearly free; foundation of option 2.
- PRF-T-0004 (serve dedup) — required under any option so unchanged state stays quiet end-to-end; notify events should carry project keys for scoped UI refetch.
- PRF-T-0005 (git/ps caching) — orthogonal exec-churn cleanup.
- PRF-T-0007 (manual refresh + attention cadence) — the human-facing freshness tier; depends on PRF-T-0006.

## Consequences

- Markdown stays the source of truth; Obsidian and direct edits keep working, picked up by the safety-net poll at worst.
- Idle daemon cost drops from ~1.3 cores to near-zero; CPU is spent only when state actually changes.
- No new runtime dependencies; the risky fsnotify surface is deferred until proven necessary.
