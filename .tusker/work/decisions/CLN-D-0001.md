# CLN-D-0001 · Human gates are for ambiguity and provisioning, not code review

## Decision

Human gates exist for exactly three things: (1) the spec or problem
understanding is ambiguous and the agent must stop rather than guess;
(2) provisioning — the agent needs something only the human can supply
(credentials, accounts, paid services, physical access), stated as a concrete
ask ("set S3/R2 keys at <path>, then resume"); (3) spec approval before
expensive downstream work begins. Code review is not a human-gate category.
Review is agent work: a separate model from the author reviews by default,
escalating to a frontier profile (e.g. 5.5 Pro / Fable) for complicated or
high-risk changes, and human code review is opt-in per task, never the
default close path.

## Context

The close policy required a human acceptor for high/critical work, which in
practice meant the operator rubber-stamping code they trust the agents to
write better than they would themselves. Meanwhile the gates that actually
block progress — a missing credential, an underspecified acceptance
criterion — had no first-class shape. Gate value comes from unblocking the
agent, not from ceremony.

## Consequences

- Gate kinds get a small taxonomy: `clarify`, `provision`, `approve-spec`.
  Each carries a concrete human action and a resume condition, so the
  needs-me queue reads as a to-do list, not a review pile.
- `close_policy` changes: reviewer_agent may close all risk tiers by default;
  a human close is required only when the task declares an explicit human
  gate. `critical` retains its named release/security gates.
- Review lane keeps validator-not-author (different model than the executor);
  RUN-T-0002 profiles let the review lane run a frontier model while the
  execute lane runs a cheaper one.
- Optional escalation: a task may set `review: frontier` or `review: human`
  in its contract; absence means the default agent review.
- Applies to CLN-T-0005 (solo profile) and the close-policy surface in
  tusker.yaml.
