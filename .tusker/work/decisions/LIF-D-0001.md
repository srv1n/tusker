# LIF-D-0001 · Interactive sessions execute directly while resident automation owns background dispatch

## Decision

Tusker has four non-overlapping execution roles:

1. A direct interactive Codex or Claude session owns its own shell, tools, edits, verification, and task-state updates. It never launches another model runner or a foreground Tusker dispatch daemon.
2. The resident daemon is the only background dispatcher. It may launch implementation workers only for a registered project with automation explicitly enabled and a dispatchable ready/rework task.
3. A dispatched implementation worker is identified by `TUSKER_ATTEMPT_ID` and works exactly one injected task/attempt/workspace. The daemon claims before spawn; the worker verifies but does not claim again. The harness owns heartbeats and normalized runtime outcomes, while the worker owns implementation proof and review/blocker state. It cannot start runners or daemons.
4. A dispatched reviewer is independent and read-only. It may accept/close permitted risk tiers or return specific unmet acceptance items to rework. Automated review is bounded to three cycles before operator intervention.

Direct sessions do not need project automation enabled and do not need a daemon lifecycle claim as permission to code. They inspect any existing live run before taking over a tracked task; a live conflicting automated owner is a coordination fact, not a reason to spawn or dispatch another worker.

## Context

Earlier lifecycle work conflated manual CLI pickup with direct interactive sessions. That was useful for preventing duplicate background runs but wrong for human-driven Codex/Claude sessions: it made ordinary coding depend on daemon registration, enablement, leases, and heartbeats. It also left enough ambiguity for an agent session to interpret “automate this” as permission to recursively launch `codex exec` or `claude -p`.

## Work streams

- `LIF-T-0013` aligns Go guards, reviewer bounds, skills, repo instructions, project canon, and lifecycle specs.
- `LIF-T-0005` remains the atomic ownership implementation for daemon-created runs, not a requirement that direct sessions become daemon workers.
- `LIF-T-0006` remains the claimed-run protocol for dispatched workers only.

## Consequences

- Task logging is inert; readiness plus dependency satisfaction does not launch anything unless project automation is enabled and the independent resident daemon is running.
- Direct sessions can implement immediately, including in disabled projects.
- Background implementation and review retain runtime leases, attempts, workspaces, and normalized outcomes.
- Recursive agent spawning becomes a product invariant backed by CLI guards and instruction tests.
- Review/rework loops terminate after a bounded number of automated reviews instead of bouncing forever.
