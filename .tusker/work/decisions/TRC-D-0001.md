# TRC-D-0001 · Adopt a journal spine before making daemon.db a projection

## Decision

Adopt partially.

Tusker should add a small append-only runtime journal as the durable source for
irreversible run-control facts: lease transitions, attempt lifecycle edges,
supervisor decisions, runner approval/permission requests and decisions, human
gate suspension/resume points, and terminal classifications. Keep
`daemon.db` as the queryable runtime store for now, but treat those rows as a
projection over the journal for the journaled facts.

Do not convert every runtime table into a pure event-sourced projection in the
first step. At Tusker's current scale, a single host, one daemon, and tens of
runs/day, full event sourcing of all mutable row fields would add more agent
maintenance risk than it removes. The right first move is a journal spine that
turns the costly failures into replayable facts; rebuilding all of `daemon.db`
can follow once the journal has covered real incidents.

## Context

The mining notes have two independent sources arguing the same inversion.
Restate describes a persisted log plus event loop plus embedded state store,
where the store is a projection of journal events
(`docs/design/aie2026-mining/durability-loops.md`, R18, 5:22:08). Amnara makes
the same claim for agents: the log is primary, everything else is a view, and
workers are disposable (`durability-loops.md`, A5-A7, 6:50:30/6:51:05).

Tusker currently points the other way. `cmd/tusker/runtime_store.go` defines
`runs`, `attempts`, `turns`, `supervisor_decisions`, `sessions`,
`apply_inputs`, `external_loop_events`, and `daemon_settings` in SQLite.
Per-attempt JSONL exists under `<state-root>/runs/<project_key>/<record_id>/`,
but `cmd/tusker/event_log.go` keeps an in-memory sequence counter per
`EventLog` object and rewrites the file on append, so it is evidence exhaust,
not a replayable authority. `docs/specs/05-runner-and-session-protocol.md`
states the same current split: lease state, attempts, turns, and sessions live
in `daemon.db`; raw event streams live under `<state-root>/runs/`.

The 2026-07-06 incidents show the cost. RUN-T-0007 records a
`retry_queued` continuation self-block where the diagnosis came from side
effects: a queued continuation counted against its own project cap and wedged
until manual intervention. The feedback note
`.tusker/feedback/agents/2026-07-06-agent-sarav-retry-queued-self-block.md`
adds that the resident daemon had also died, so nothing was polling. RUN-T-0008
and `.tusker/feedback/agents/2026-07-06-agent-sarav-daemon-sqlite-busy-no-instance-guard.md`
record the other incident: two daemons contended on `daemon.db`; the incumbent
exited on `SQLITE_BUSY`, leaving no first-class narrative of what had been in
flight.

### What Breaks Today

Verified against the schema and write paths in `cmd/tusker/runtime_store.go`,
`cmd/tusker/daemon.go`, `cmd/tusker/runner_codex_live.go`, and
`cmd/tusker/event_log.go`:

| State | Current authority | Survives daemon kill if `daemon.db` is intact? | What is lost or ambiguous |
|---|---|---:|---|
| `runs` aggregate row | SQLite `runs` | Partial | Last row survives, but crash windows leave no ordered explanation of why `lease_state`, `attempt_outcome`, `next_retry_at`, `active_attempt_id`, process ids, or `last_error` changed. Dead processes can remain as `running` or `retry_queued` until reconcile/sentinel logic interprets them. |
| Lease ownership and capacity | Columns on `runs` | Partial | `lease_owner`, `lease_generation`, expiry, pid, pgid, and heartbeat survive as row values. The sequence claim -> start -> heartbeat -> retry/release is not authoritative, which is why RUN-T-0007 had to be diagnosed by reading side effects instead of replaying capacity decisions. |
| `attempts` | SQLite `attempts` | Mostly | Rows survive once saved. A crash between `SaveAttempt`, `UpsertRun`, runner start, and the second `SaveAttempt` can leave an attempt without a matching run aggregate, final process fields, or session ref. |
| `turns` | SQLite `turns` plus per-attempt JSONL | Partial | Turn rows survive when `SaveTurn` ran. Boundary events may exist in JSONL, but there is no authoritative offset that proves which events were projected into `turns` before the crash. |
| `supervisor_decisions` | SQLite table, mirrored to current attempt JSONL | Mostly, but not log-primary | Decisions survive in SQLite once `SaveSupervisorDecision` succeeds. The JSONL mirror is best-effort after the DB write and can be missing; the DB row is still the authority. |
| Runner sessions | SQLite `sessions` | Partial | `session_ref`, `last_message_ref`, resumability, and state survive. Compatibility checks can resume a stored session, but the reasoned suspension/resume chain is not journaled. |
| Approval and permission decisions | Attempt JSONL only | Weak | `codex_approval_decision` events are written to per-attempt JSONL. They are not in `daemon.db`, not indexed as durable gate state, and pending permission prompts are not represented as a restart-surviving suspension. This is the exact Amnara A13 failure class: a permission prompt can vanish on crash-resume (`durability-loops.md`, A13, 6:54:12). Restate's durable-promise suspension is the model for fixing it (`durability-loops.md`, R8, 5:13:24). |
| Human gates and closeout waits | Vault task/gate/proof frontmatter | Yes for V7 gates; no for runner-native prompts | First-class Tusker gates survive because they are markdown records with `state_rev`. Runner-native approval prompts do not become Tusker gates; if the runner process dies while waiting, the daemon has no durable prompt object to surface and resume. |
| `external_loop_events` | SQLite table with idempotency key | Mostly | Idempotent external-loop events survive after insert, but they share the same projection problem: no broader journal order with lease/attempt transitions. |
| `daemon_settings` and project rows | SQLite | Yes | Operational settings and registered projects survive DB restart. They are configuration/projection concerns, not the main crash narrative. |

### Migration Shape

Add a run-scoped journal file under the daemon state root, not under tracked
task markdown:

```text
<state-root>/runs/<project_key>/<record_id>/runtime.events.jsonl
```

Each record gets a monotonic `event_id`, `project_id`, `record_id`,
`work_revision`, `lease_generation`, `attempt_id` when known, `event_type`,
`created_at`, `producer`, and typed payload. The journal must be append-only
with `O_APPEND`/fsync boundaries or equivalent SQLite WAL durability if the
implementation chooses a single `runtime_events` table first. The important
contract is log-primary ordering, not the file extension.

Projection mapping:

| Current table/state | Projection status |
|---|---|
| `runs` | Rebuildable aggregate from events such as `run_registered`, `lease_claimed`, `attempt_started`, `heartbeat`, `retry_scheduled`, `terminal_classified`, `lease_released`, `run_reconciled`. |
| Lease state | Derived from the latest valid lease event per `(project_id, record_id, lease_generation)`, with TTL/dead-pid reconciliation appending explicit `lease_reclaimed` or `runner_abandoned` events rather than silently mutating the row. |
| `attempts` | Rebuildable from `attempt_started`, `attempt_process_observed`, `attempt_finished`, `attempt_handoff`, and terminal outcome events. |
| `turns` | Rebuildable from `turn_started`, usage updates, boundary events, and `turn_completed`; per-attempt runner JSONL can remain raw detail, but the journal owns projection offsets. |
| `supervisor_decisions` | Should become pure journal facts. The existing table is already append-shaped and can be projected from `supervisor_decision` events. |
| Runner approval/gate state | New journal facts: `approval_requested`, `approval_decided`, `gate_suspended`, `gate_resumed`, `gate_cancelled`. Pending approval must be queryable after daemon restart and must consume zero runner compute while blocked. |
| `sessions` | Projection from `session_opened`, `session_seen`, `session_closed`, `session_marked_resumable`. |
| `external_loop_events` | Can stay SQLite initially because it already has idempotency keys. Later projection is straightforward from `external_loop_event_recorded`. |
| `daemon_settings`, `projects` | Do not event-source in this workstream. They are low-volume configuration records; CAS/provenance work belongs elsewhere. |

Rebuild cost is trivial at current scale. Tens of runs/day with a few hundred
events/run is thousands, not millions, of events. A cold rebuild can scan the
state root, replay per-run journals into an empty `daemon.db`, and finish well
inside one daemon startup budget. If that stops being true, add snapshots keyed
by journal offset; do not compromise the append-only source.

`state_rev` CAS remains the guard for durable markdown records. Runtime journal
events do not replace task/gate/decision CAS. Instead, events that intend to
write markdown carry `observed_state_rev`; the control operation still performs
CAS against the note. On success, append or complete a `vault_write_committed`
event with the new `state_rev`. On CAS conflict, append `vault_write_conflict`
and leave the row projection blocked/retryable. Journal order explains the
attempt; `state_rev` still protects the file.

### Cost

| Cost | Assessment |
|---|---|
| Write amplification | Acceptable for journaled control facts. A dispatch already writes attempt rows, run rows, prompt files, event JSONL, logs, sessions, and review packets. Adding one append for lease/decision/gate transitions is cheap. Full event-sourcing every heartbeat/token update immediately is less attractive; batch or coalesce noisy updates. |
| Poll-loop latency | Negligible if appends are local and small. The current default reconcile tick is 30s; a local append and projection update are not the latency driver. Fsync on every heartbeat would be overkill; fsync irreversible transitions, tolerate coalesced heartbeat projection. |
| Complexity | Real. The codebase is maintained by agents, so two authoritative paths would rot fast. The implementation must enforce one helper for "append event then project" and tests that rebuild from scratch equals the live DB. Anything less is worse than the current design because it creates two liars. |
| Operational burden | Low if files stay under `<state-root>/runs/` and `daemon.db` remains the query surface. Higher if the first step tries to redesign all runtime storage, migrations, serve API, and runner adapters at once. |
| Debug value | High. The next RUN-T-0007 class bug should be answerable by replaying `lease_claimed -> turn_completed -> supervisor_decision -> retry_scheduled -> capacity_blocked`, not by inferring from stale rows. |

### Recommendation

Adopt partially now:

1. Build the runtime journal spine for lease transitions, attempt lifecycle
   edges, supervisor decisions, approval/gate suspension, terminal
   classifications, and projection offsets.
2. Keep `daemon.db` as the live query/projection store and preserve existing
   CLI/API reads.
3. Add a rebuild verifier that can drop/recreate a test `daemon.db` from
   journals and prove equivalence for `runs`, `attempts`, `turns`,
   `supervisor_decisions`, and pending gate/approval state.
4. Only after that verifier exists, flip individual tables from authoritative
   writes to projected writes.

Reject the full immediate inversion. It is architecturally clean but too much
surface area for the current scale and maintenance model. The conditions to
reopen full adoption are: multi-daemon or multi-host operation, persistent
state divergence between `daemon.db` and journals after the journal spine
ships, inability to resume pending approvals from journaled suspension, or
runtime volume high enough to require snapshot/replay architecture anyway.

## Consequences

- TRC-T-0004 scopes the journal spine and durable approval/gate suspension.
- TRC-T-0005 scopes projection rebuild and table-by-table authority flip.
- RUN-T-0008's single-instance and busy retry fixes remain valuable; event
  sourcing does not remove the need to avoid double writers.
- TRC-T-0001/TRC-T-0002 remain attempt-level boundary trace/replay work.
  This decision is runtime-control durability, not a replacement for boundary
  trace records.
