# RUN-D-0001 · Sequential-first workspaces: keep worktrees, make merging trivial

## Decision

Keep git-worktree isolation for every dispatched run, but treat merging as a
policy problem, not a workflow stage. Runs are sequential-first (concurrency 1,
max 2 with disjoint file ownership), each run branches from current HEAD, and
landing is automatic when the result fast-forwards or rebases cleanly onto
HEAD. Only a real textual conflict escalates — it becomes a needs-me queue
entry, never a silent overwrite. There is no standing "merge management"
activity for the solo operator.

## Context

Worktrees look like multi-agent machinery, and the obvious solo simplification
is to run agents directly in the main checkout. That is wrong for three
reasons. First, the operator's checkout is routinely dirty (uncommitted vault
edits, in-progress hand edits); an in-place agent run would interleave its
changes with the operator's and make attribution impossible. Second, a failed
or interrupted attempt in a worktree is discarded by deleting the worktree —
in-place it means untangling a half-finished diff from the working copy.
Third, merge pain is a function of temporal overlap, not of worktrees:
sequential runs branched from HEAD fast-forward back by construction. The
cost we actually avoid is concurrent-overlap conflict resolution, and we avoid
it with the concurrency cap and file-ownership partitioning of tasks, not by
giving up isolation.

## Consequences

- Daemon/dispatch keeps `workspace: worktree`; no in-place strategy is built.
- Landing policy: ff-merge or clean rebase lands without human involvement;
  conflict pauses the run and surfaces in the needs-me queue with the two
  branch heads named.
- Parallelism stays bounded (max_active_runs 2) and tasks that share files are
  serialized at planning time; the merge step is expected to be a no-op.
- The serve UI shows landed/unlanded state per run so unmerged work is never
  invisible.
