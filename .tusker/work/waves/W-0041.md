# W-0041 · Harden run execution, recovery and run UI

## Intended result

Long Codex, Claude, Devin and Muse runs survive Tusker restarts, resume the same native thread where the harness supports it, never double-spawn, never lose an interactive claim, and the run page shows truthful state with server-declared actions only.

## Shared context

This wave fixes audit defects found in committed W-0039 / claim work (commit c5a5da52). Every defect below was re-verified against current source on 2026-09-23; line numbers drift, so re-locate by function name.

Governing contract: `.tusker/specs/run-session-continuity.md` ("Harness routes and operations", "Run states shown to operators") and decision record `.tusker/specs/decisions/2026-09-23-harness-sessions-grill.md` (D2 headless exec, D3 interrupt+resume, D5 never `--bare`). Key locked facts:
- Codex resume form is `codex exec <exec-flags> resume <id> -` (exec flags BEFORE `resume`). codex-cli 0.155.1 `codex exec resume --help` accepts only -c/--last/--all/--enable/--disable/-i/--strict-config; `codex exec resume --sandbox ...` fails with "unexpected argument '--sandbox'".
- Claude runs `claude -p` stream-json, detached, with a Tusker-assigned `--session-id <uuid>` persisted before the first prompt completes; resume is `claude -p --resume <id>` with the same MCP/settings flags. Claude Code 2.1.280 supports `--session-id <uuid>`. Never `--bare`.
- The server computes allowed run actions with the SAME preflight the action endpoint uses; the UI never guesses. Failure/blocked reasons should be typed codes, not substring matches (full typed-failure work belongs to wave B; do not widen scope here).
- Stop persists intent, suppresses retry and completes only after ownership/process settlement. Start fresh is always explicit.
- Neither a heartbeat nor an expired lease alone proves safe continuation or reclaim.
