# W-0042 · One exec-based session contract for Claude Code, Codex, Muse and Devin

## Intended result

From the CLI, then Serve API and UI, an operator sees a truthful normalized state for any run (Working, Waiting on you, Quiet, Blocked, Failed, Lost), a typed reason with guidance when blocked or failed, and can Say to, Interrupt, or Continue the same native thread on Claude Code, Codex, Muse and Devin without Tusker driving provider turns.

## Shared context

Governing contract: `.tusker/specs/run-session-continuity.md` sections "Harness routes and operations" and "Run states shown to operators"; decisions D2 (headless exec is the primary route, app-server is not) and D3 (interrupt plus resume is the universal steering primitive) in `.tusker/specs/decisions/2026-09-23-harness-sessions-grill.md`; messaging routes in `.tusker/specs/agent-coordination.md` "Delivery routes — 23 September 2026 update". Tusker never drives provider turns through app-server or MSP in this wave.

Audit facts (verified against source 2026-09-23; re-locate by function name, line numbers drift):
- `Runner` interface: `cmd/tusker/runner.go` (Name, Capabilities, Start, Resume, Reconcile, Interrupt, Collect). `RunnerCapabilities` has StructuredEvents, ResumeSession, ExplicitApprovals, Heartbeats, MachineFinalStatus, UsageMetrics, ArtifactEnumeration; there is no declaration for soft say, hard say, pre-assigned session identity or resume after process death. `runnerForName` (daemon.go) is the runner registry; `nativeResumeRunnerCapabilities` (work_recovery.go) is a second, hand-written name switch covering only codex_exec, muse and devin.
- Failure classification is substring matching on free text in two places that disagree: `classifyRetryFailure` (daemon.go, consumed by `(*Daemon).scheduleRetry`) and `runtimeFailureClass` (run_runtime_commands.go, surfaced as `failure_class` in `tusker runs inspect --json`). A Codex "usage limit" message matches no marker and is retried as a generic failure.
- The only terminal status channel from a detached child is `runnerProcessStatus` {exit_code, completed_at, outcome, reason, turns_used} (runner_exec.go), written by `writeRunnerStatusFileIfAbsentWithOutcome` (runner_raw_log_limit.go) and read by `classifyRunnerProcessExit` (runner_exit_classification.go). There is no reason-code field.
- Operator interrupt is one shared path: `interruptRuntimeRunScoped` (run_runtime_commands.go) -> daemon control or `interruptRunProcess` (daemon.go: process group SIGINT, then SIGTERM, then SIGKILL, with identity verification; ACP goes through `interruptACPWrapperProcess`). It ends in `finishRuntimeRunIfSnapshot(..., LeaseStateInterrupted, AttemptOutcomeCancelled, 130, ..., resumable=true)`. Per-runner `Interrupt` methods for Claude, Codex exec and Muse are no-ops, but the process-group path already covers them.
- Native Continue exists: `queueNativeSessionContinuation` (work_recovery.go), reached only from Serve `handleRunRecovery` action `continue` (serve_command.go). It is fenced (UpsertRunIfSnapshot, QueueRunDirective, wave authorization, context fingerprint). There is no CLI Continue command and no way to attach a message or typed failure summary. The resumed attempt's prompt is built by `renderAttemptPromptForResume` (daemon.go) and passed to `runner.Resume` inside the daemon dispatch path.
- A fenced, idempotent operator-to-worker delivery store exists: `WorkerDelivery` / `PutWorkerDelivery` / `transitionWorkerDelivery` / `markWorkerDeliveryState` (worker_coordination.go), keyed by `WorkerAttemptIdentity` (project, task, attempt, provider, native session, work revision, attempt generation) plus idempotency key, used today by `tusker worker message` (worker_coordination_commands.go) for Devin cloud and qualified Muse session-message transports only.
- The mailbox of record is `agent_messages` (agent_messages.go; `tusker message ask|reply|list`). An unanswered worker question is an `AgentMessage` with Kind `question`, OriginTaskID = task and empty AnsweredAt.
- Serve run summary: `serveRunSummary` (serve_types.go) built by `runSummaryChecked` (serve_runs.go). `serveRunLiveness` labels a run "dead" after 120s without events, which contradicts the spec rule that silence is not proof of a hang.
- CLI namespace: `tusker run <TASK|WAVE>` already means "queue for background work" (`directRunCmd`). The per-run operator namespace is `tusker runs ...` (inspect, logs, events, interrupt, release, retire, redrive; dispatched in cli.go). New verbs go under `tusker runs`, not `tusker run`.
- Muse: `MuseRunner` (runner_muse.go) discovers the session id only from output after process exit (`classifyMuseCLIOutput` in `monitorRunnerCommand`, runner_exec.go, emits `muse_session_started` at exit). A Muse attempt lost mid-run therefore has no saved native identity. Resume appends `--session-id` (`museCLIResumeArgv`).
- Devin: `ACPRunner.Resume` already uses negotiated `session/load` (runner_acp.go `startLiveACPForRunnerWithSession`). `ACPRunner.Reconcile` returns released/abandoned for any lost attempt. `acpTerminalStatus` maps ACP outcomes to AttemptOutcome with free-text reasons. `cmd/tusker/testdata/fake_acp` advertises `loadSession: false`.
- Claude: `claudeLiveHandle` (runner_claude_live.go) already writes stream-json user messages (`sendUserMessage`) and control requests (`controlRequest`) to the child's stdin, but lives in-process. `ClaudeRunner.Capabilities` declares ResumeSession=false. Wave A (A:claude-detached) moves Claude under the detached wrapper with a pre-assigned `--session-id`.

Research facts (2026-09-23 provider research, not source; tests must not depend on live binaries): Claude Code 2.1.280 supports `--session-id <uuid>` and `--resume <id>` after kill (cwd need not match since 2.1.223); result subtypes success, error_max_turns, error_during_execution, error_max_budget_usd; `permission_denials` in the result and `system/permission_denied` events; `tool_progress` heartbeat every 30s while a tool runs; stdin stream-json user messages are picked up between tool calls; interrupt via control_request or SIGINT. Codex 0.155.1 exec emits thread.started(thread_id), turn.started/completed/failed, item.started/updated/completed and error; usage-limit and auth failures appear only as message text; `exec resume` takes an explicit id and flags such as --sandbox/-C must precede `resume`. Muse Code 1.3.0 `muse exec --json` emits run.terminal.completed|failed|cancelled with a reason and accepts `--session-id <uuid>`. Devin CLI 3000.11.1 `devin acp` advertises loadSession true, has no mid-turn prompt in ACP v1, and stop reasons are end_turn, max_tokens, max_turn_requests, refusal, cancelled.

Wave A (drafted in parallel) owns: `codex exec resume` argv (A:codex-resume); Claude under the detached wrapper with pre-assigned session id and --resume (A:claude-detached); server-projected allowed actions and freshness fields (A:run-controls-backend); error events and tool merge in CLI activity parsing (A:activity-fidelity); ACP tool merge and plan/usage (A:acp-updates); and the first RunDetail/SessionRecoveryControls UI pass (A:run-controls-ui). Consume their results; do not redo them.

Those tasks declare overlapping owned paths (daemon.go, run_runtime_commands.go, serve_runs.go, serve_types.go, runner_acp.go, runner_wrapper.go, work_recovery.go, runtime_store.go, internal/serve/ui/src/features/runs). This wave extends that code and does not re-implement it; if a W-0039 member is active on a shared file, serialize and ask.
