# W-0043 · Agent mailbox: questions, answers and messages across running agents

## Intended result

A worker on Claude Code, Codex exec, Muse exec or Devin ACP can ask its architect or the operator through an injected Tusker MCP tool; the question appears in the UI and in the architect's interactive Claude Code/Codex session through a hook; the reply reaches the worker (soft between tool calls where verified, else hard interrupt plus resume of the same thread, else on the next continue); a stalled or completed wave reports to its architect.

Harness research (2026-09-23; help output checked on this machine: claude 2.1.280, codex-cli 0.155.1, muse 1.3.0):
- Claude: `--mcp-config <json|file>`, `--settings <file|json>` (hooks, permissions), MCP_TOOL_TIMEOUT default ~28h; stdio tool idle timeout 30 min unless progress notifications are sent. PostToolUse hook output `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"..."}}` is documented; UserPromptSubmit accepts additionalContext; Stop accepts `{"decision":"block","reason":"..."}`.
- Codex exec: `-c mcp_servers.<name>.command=... -c mcp_servers.<name>.args=[...]`, `tool_timeout_sec` default 60 (configurable), per-tool approval mode; MCP stdio servers get a minimal environment unless env/env_vars are configured (verify exact keys in Codex docs). Hooks are stable in 0.155.1 and share the Claude hooks.json format, but require persisted hook trust (`--dangerously-bypass-hook-trust` exists) and whether a post-tool hook adds model context in `codex exec` is UNVERIFIED.
- ACP: `session/new` and `session/load` take `mcpServers` (stdio entries: name, command, args, env[{name,value}]).
- Muse 1.3.0: `muse exec --help` has NO MCP flag; `muse mcp` only logs in/out of streamable-HTTP entries under `mcpServers` in settings.json; `--agents <JSON>` is an ephemeral agent-definition overlay (MCP support unverified). `muse session-message send` exists (native cross-session messaging; not used by this wave).
