# W-0030 · Make wave progress and recovery obvious

## Intended result

A human can understand a wave at a glance, inspect one task without reading internals, and recover a failed machine stage through the correct supported action.

## Shared context

This is a delta after the 2026-09-17 Alpha/Beta manual walkthrough, not a rewrite of Tusker. Reuse the current Serve projections, recovery endpoints, DAG and task inspector. Do not add a new state machine, store, event taxonomy, router or component framework.

Observed installed behavior:
- Alpha W-0002 reached Completed, but its task drawer still said accepted proof was unavailable and exposed raw receipt hashes, worktree paths, provenance IDs and self-claim instructions as primary content.
- Beta W-0003 showed normal dependency blockers and a material fingerprint as alarming Technical details; it used generic filler instead of a compact progress summary.
- BET-T-0002 and BET-T-0003 were sibling frontier members. The project was configured for one active run, so one executed while the other remained Ready. The UI did not expose the occupied capacity slot, making the DAG look broken.
- During pause/resume, BET-T-0003 appeared Failed with current command proof missing and no applicable recovery control. The wave misclassified this as Wave setup needs attention. Resume did not explain whether it merely restored authorization or also queued recovery.
- Run detail rendered implementation and independent review as Attempt 1/Attempt 2, suggesting an unexplained retry; navigation back to the originating wave/DAG was unclear.

Read-only source-of-truth inspection after the screenshots found W-0003 authorized/Waiting: BET-T-0001 and BET-T-0002 completed, BET-T-0003 ready, BET-T-0004 dependency-waiting. Treat screenshots as a real historical transition and retained current state as a separate observation. Preserve attempts, receipts, budgets and project identity. Do not reset, reseed, force completion, fabricate proof, change the disposable campaign, or mutate RZN.

W-0029 remains Planned/inert even though its recovery changes were implemented outside its tracker lifecycle. Do not start W-0029 or duplicate its already-present DAG-default and basic Retry review/Rerun checks work. This wave owns only the remaining delta verified in current source and the Beta walkthrough.

Locked product rules:
- Machines execute checks and independent review. Humans act only on explicit decisions or explicitly authorize a new bounded attempt window after exhaustion.
- Pause blocks new admissions; active work may finish. Resume restores unchanged authorization; it must not imply that a failed task was retried unless a retry was actually admitted.
- Expected dependency waiting is not an error. Ready work constrained by project capacity must say it is waiting for a slot and name the effective limit.
- Default UI is human language and decisions. Raw hashes, internal codes, worktree paths, receipt wire data and provenance remain available only under Technical.
- Status and the single next applicable action are always visible. No confirmation modal, terminal relay or self-claim command in an ordinary daemon-owned flow.
- Architect/origin is this Codex conversation with no verified Tusker message address. Return only unresolved product choices through the operator with task and acceptance ID, evidence and a recommendation.
