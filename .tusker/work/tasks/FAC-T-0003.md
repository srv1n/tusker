# FAC-T-0003 · Give every new task a plain-language top layer and a builder appendix

## Intent

Every task should open with a few plain sentences a former product manager can
read cold: what this is, why it matters, and what "done" looks like as things
you can actually see. The technical detail — the files, the moving parts, the
exact commands — belongs in a clearly separate appendix that only the person
doing the hands-on work needs to open.

Today a freshly created task is a bare stub with a single "to be decided," so
every author reinvents the structure and the plain-language layer often never
appears. This task makes the default shape of a new task carry both layers from
the start: a product-readable top and a builder's appendix beneath it.

Done looks like: creating a new task produces a body that already has a plain
top section and a separate, clearly-labelled appendix for the builder, with the
"done" conditions written as visible outcomes rather than as code.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | A newly created task's body has a plain-language top section and a separate builder appendix. | Inline verification |
| A2 | The appendix is clearly marked as builder-only detail, distinct from the plain top. | Inline verification |
| A3 | The "done" scaffold reads as visible outcomes, not as code internals. | Inline verification |

## Non-goals

- No rewrite of existing tasks; this changes the shape of newly created ones.
- No enforcement that the plain layer stays plain — the warning check is a separate piece of work.
- No change to the frontmatter fields, only the generated body.
- No new task types or acceptance grammar beyond the two-layer scaffold.

## Implementation notes

Best-guess file map — verify before editing:

- The stub body is generated in the `tusker new task` path. Best guess:
  `newV7Task` in `cmd/tusker/commands_v7.go` builds the template body (the
  `## Intent` / to-be-decided block seen in freshly created files).
- Add the two-layer scaffold: a plain `## Intent`, a separate
  `## Implementation notes` appendix marked for builders, and the
  Acceptance / Verification / Non-goals sections phrased as outcomes.
- Follow the two-layer style the spec's operating principle 5 mandates; the ORC
  tasks under `.tusker/work/tasks/` are the reference shape.
