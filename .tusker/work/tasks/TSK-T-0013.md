## Intent
The wave header currently makes users read boilerplate and internal blocker codes before they can answer: what is happening, what is waiting, and do I need to act?

## Verified seams and ownership
`WaveAuthority.tsx` owns status prose, progress, controls and issue grouping. `integrationModel.ts` owns stage interpretation. The Dependencies DAG is already the first/default view from prior work; preserve it rather than rebuilding it.

## Implementation contract
Replace the large prose card with a compact glanceable summary: lifecycle badge, `completed / total`, counts for executing, reviewing, ready/waiting and failed, effective project capacity when it constrains work, and the one applicable primary action. Color and icon supplement text; never make color the only signal.

Delete filler such as `Work is prepared; nothing is running yet` and `This starts only the currently eligible tasks...`. Start, Pause and Resume may have one short contextual hint only when the behavior is not obvious. Normal dependency waits stay on the DAG node as `Waiting for <task title>`; they do not appear in an issue panel or raw Technical details. Material fingerprints and internal codes stay off the wave surface entirely; Diagnostics and `tusker wave review --json` carry them.

A ready member blocked only by `maxActiveRunsPerProject=1` reads `Ready — waiting for an execution slot` and the wave shows `1 task at a time` with the existing settings destination, if available. Do not claim the scheduler is broken or offer parallel execution when the configured limit forbids it. When capacity is available, the UI may say `Ready — starting automatically` only after durable authorization exists.

Replace the generic fallback `Wave setup needs attention` with the specific task/lane failure and its supplied recovery action. Genuine route/configuration defects retain a setup message. Expected dependencies and capacity never fall through to that fallback.
