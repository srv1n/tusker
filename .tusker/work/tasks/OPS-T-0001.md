# OPS-T-0001 · Wave primitive: named batches with derived landed-state

## Intent

Binding design: `docs/design/prior-art-playbook.md` §5 decision 1 (donor: Gas Town Convoy, `docs/design/research/research-operating-models.md` §1.2). The operator already works in waves — batches of independent tasks dispatched together and reviewed together at the boundary — but the ledger has no record of them: epics are thematic, not temporal, so "what shipped in this wave / what is this wave waiting on" is reconstructed by hand every time. Make the wave a first-class V7 record.

Semantics (deliberately minimal, two-state like the donor):

1. `tusker wave create "<title>" <TASK-ID>...` creates a wave record (`kind: wave`, ids `W-####`) listing member tasks; `tusker wave add/remove` edits membership; a task belongs to at most one open wave (frontmatter back-pointer `wave:` maintained by reconcile).
2. Wave state is **derived, never hand-set**: `open` while any member is not `done`; `landed` when all members are `done` (stamped with the timestamp of the last close); adding a member to a landed wave re-opens it. Reconcile owns the derivation.
3. `tusker wave show <id>` renders the boundary view: members grouped by status (done / review / parked / running / ready / blocked), with per-member one-line proof status — this is the batch-review worklist.
4. Review-queue dashboard and `tusker list` gain wave filters (`--wave W-0001`).
5. Serve API exposes waves (`/api/waves`, `/api/waves/{id}`) read-only so the UI can group the board by wave; no UI work in this task.
