# RUN-T-0022 · Add `tusker runs retire`: operator path from sentinel violation to terminal record

## Intent

Found live during the RUN-T-0017 re-entry trial, step 1. The sentinel correctly opened the invariant circuit on seven legacy run records (`attempt_count_within_caps`: counts up to 95 with `terminal=0`), and `daemon resume` correctly refused to matter until the cause was cleared. But no CLI command can clear that cause: `tusker runs release` frees the lease yet leaves the record non-terminal, `redrive` goes the other direction (restores dispatchability), and `interrupt` targets live runs. The operator's only path out of the circuit was hand-editing `daemon.db` with sqlite — unacceptable as the paved road.

Semantics:

1. `tusker runs retire <task-id-or-record-id> --reason <text> [--by <actor>] [--json]` marks the run record terminal (preserving `attempt_outcome` if set, else `abandoned`), releases any lease, and records the retirement as a run event with actor and reason.
2. Retire refuses (without `--force`) if the record has a fresh heartbeat AND a verified-alive pid — retiring a genuinely live run is `interrupt`'s job, and the guard names it.
3. Retiring all records behind an open `invariant_violation` circuit followed by `tusker daemon resume` closes the circuit; the trial's sqlite surgery becomes `retire` + `resume`.
4. Surface in `runs --help` and in the circuit-open error text (the violation summary should name the repair command — the operator at 3am should not need the playbook).
