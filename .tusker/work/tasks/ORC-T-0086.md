# ORC-T-0086 · Split fleet health and repair into explicit authority scopes

## Intent

Setup and rollout diagnostics preserve every finding but quarantine only incompatible core state, and repair changes only the explicitly selected core, automation, service, or integration scope.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Fleet output reports core compatibility, interactive readiness, automation configuration, wave authorization, runtime health, and optional integrations independently for every registered project and once for the managed service. | See mapped verification. |
| A2 | Missing vaults and incompatible core schemas may quarantine core work, while stale or missing optional handoff and provider contracts block only workflows that require those integrations. | See mapped verification. |
| A3 | Core repair is the default and changes only deterministic core files or generated installs; automation, service, and integration repair require their explicit scopes. | See mapped verification. |
| A4 | No repair scope enables project automation, arms a wave, changes credentials, invokes a provider, moves a ref, releases, or spends, and service start remains a separate explicit operation. | See mapped verification. |
| A5 | Repeated doctor and repair converge idempotently across healthy, disabled, missing-vault, missing-skill, legacy-runner, stale-optional-provider, stale-service, and mixed sibling fixtures without one project blocking unrelated siblings. | See mapped verification. |
