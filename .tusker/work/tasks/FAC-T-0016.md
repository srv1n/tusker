# FAC-T-0016 · Run one task from the UI: one-shot human dispatch with automation off

## Intent

- What this is: a Run button on a task's page in the web UI. Pressing it asks
  the background runner to execute exactly that one task, once, even when the
  project's automation is switched off. The press is recorded as the
  operator's own authorization; the run appears live in the runs view like
  any other, and the task comes back as reviewable work with proof.
- Why it matters: the operator wants to build confidence in automated
  execution gradually. Today the only choices are "automation on" (the
  runner picks up everything eligible) or "automation off" (the UI can
  describe work but never start it). One-task-at-a-time, human-pointed
  execution is the missing middle — it turns automation-off into "nothing
  runs unless I point at it" instead of "nothing runs at all."
- What "done" looks like: with automation off, open a ready task, press Run,
  watch the run go live in the runs view, and find the task in review with
  proof when it finishes. Pressing Run on a task that is not runnable, or
  when the background runner is not alive, explains why instead of silently
  doing nothing. Nothing else starts running — one press, one task, one run.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | A ready or rework task's page offers Run; pressing it records a one-shot dispatch directive attributed to the human operator and returns immediately with a visible "queued for dispatch" state. | Inline verification |
| A2 | The resident daemon executes the directive even when project automation is disabled: exactly the named task, exactly one attempt, through the normal claim/lease/worker protocol. No other task starts. | Inline verification |
| A3 | The directive is refused with a plain reason when the task is not in a runnable state, when a live run already owns it, or when the daemon is not running — never a silent no-op, never a second concurrent worker. | Inline verification |
| A4 | An unclaimed directive expires after a bounded window and the task page shows it lapsed, so a dead daemon cannot leave an invisible pending run trap. | Inline verification |
| A5 | The run is visible in the runs view from claim to terminal state, and the human authorization (who pressed Run, when) is recorded on the attempt trail. | Inline verification |
| A6 | Interactive agent sessions remain forbidden from dispatching: the directive path is honored only by the resident daemon loop. | Inline verification |

## Non-goals

- No multi-task or wave dispatch from this button; wave arming stays its own
  explicit flow.
- No change to the automation toggle's meaning for planned (non-directed)
  work.
- No runner selection UI; the directive uses the project's configured runner.

## Implementation notes

Builder appendix — verify the paths before editing.

- Depends on FAC-T-0013 (dispatch honors automation; session runs visible) —
  the directive is the explicit-authorization carve-out to the same check
  that task adds, so land 0013 first and extend its gate: automation.enabled
  OR a live one-shot directive for this exact task.
- Directive record: runtime store (daemon side), not task frontmatter — it is
  session/runtime state per the V7 rule. Shape: {task, project, requested_by:
  human:<user>, requested_at, expires_at}; single active directive per task.
- Serve: POST /api/tasks/{id}/run in `cmd/tusker/serve_actions.go` following
  the acknowledge-action pattern (refusal reasons in-band as {refused,
  reason}); task detail payload gains the pending/lapsed directive state.
  Daemon liveness is already surfaced via /api/daemon — refuse at POST time
  when the daemon is down (A3).
- Daemon: the automation plan/dispatch loop consumes directives before (and
  independent of) eligibility planning; expiry default ~10 minutes unclaimed.
- UI: Run button + queued/lapsed state on the task page in
  `internal/serve/ui/src/` (task detail feature); runs view needs no change
  beyond what FAC-T-0013 provides.
- Attribution: reuse the human-actor default being added for UI status
  changes so the directive and the attempt trail carry `human:<user>`.
