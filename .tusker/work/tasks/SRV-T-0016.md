# SRV-T-0016 · UI Retry swallows redrive refusals and offers actions that cannot apply: silent retire behind a stale Ready badge

## Intent

Observed today (2026-07-08) on the AGX-T-0005 run detail page. The status badge read "Ready" with an active Retry button. The operator clicked Retry and nothing visibly happened. The DB shows what actually occurred: `attempt_outcome=blocked, terminal=1, last_error="retired by sarav: operator redrive error: task is in review, no execution needed"` — the redrive was refused because canonical status was `review` at that moment, and the row was retired, all invisible in the UI. The badge also said Ready while canonical said review — a stale status source feeding the badge.

Semantics:

1. **Retry means redrive, and says so.** The Retry control maps to `tusker redrive` (reset the attempt window, requeue, daemon spawns a fresh codex exec attempt) and the UI labels it as such — no ambiguous "Retry" that hides which operation it triggers.
2. **Surface the response.** The redrive API result — success or refusal reason — surfaces as visible feedback (toast/inline). A refusal like "task is in review, no execution needed" is shown, not swallowed; a retire is never silent.
3. **Disable when meaningless.** Retry is disabled, with an explanation, when the task state makes redrive a no-op (review/done): the UI says the correct lane there is review/land, not retry.
4. **Canonical badge.** Status badges read canonical task state (review), never a stale run-row / UI-cached status (Ready).
