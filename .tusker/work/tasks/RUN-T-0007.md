# RUN-T-0007 · Continuation retries must not be capacity-blocked by their own run slot

## Intent

Observed 2026-07-06 on AGX-T-0003: a runner exited cleanly at the `max_turns: 1` turn boundary, the supervisor queued a `continue_thread` retry (`lease_state=retry_queued`, `next_retry_at` in the past), and the continuation never dispatched. Root cause: `CountProjectActiveRuns` counts `retry_queued` toward `max_active_runs_per_project`, and the dispatch capacity check does not exempt the run being dispatched — so at limit 1 the run's own parked lease occupies the only slot and the run deadlocks against itself. Every multi-turn task at limit 1 wedges at its first turn boundary until a human bumps `work_revision`, which also discards the session thread the continuation was meant to resume.

Fix the capacity accounting so a run's own lease never blocks its own retry/continuation dispatch. The limit must still hold across *distinct* runs: a second task's dispatch while another run is claimed/running/retry_queued stays blocked at limit 1.

Repro evidence: supervisor decision 01KWV00X4T69AXSYCNB8QWCFCV (continue_thread, 2026-07-06T05:57:07Z) followed by >8 minutes of no dispatch under a live daemon; cleared only by a `work_revision` bump at 06:05Z. See feedback note `.tusker/feedback/agents/2026-07-06-agent-sarav-retry-queued-self-block.md`.

| A2 | The limit still binds across distinct runs: with one run claimed/running/retry_queued, a *different* task's dispatch remains blocked at limit 1 (regression test). | Inline verification |

- No daemon liveness surfacing (tracked via feedback; different surface).
