# Event-driven status and bounded resource use

## Intent

CLI writes should be the normal source of status updates. The daemon should
coalesce project notifications immediately, retain lightweight active-run
liveness checks, and reconcile external edits periodically (five-minute default)
instead of rescanning every vault on each active tick. Startup and explicit
refreshes still load current material; dispatch and mutation checks retain their
freshness and ownership fences.

This delivery also removes resource amplification on the same status path:
reuse one note index per read operation, scope runtime queries, ingest only new
complete log records, stream file hashes, bound log buffers/tails and native pipe
draining, reuse Serve request snapshots, and coalesce web/native refreshes. Hidden
views resume with current state. Truncated authoritative runner output must not
produce a successful proof. Arbitrary verification commands cannot share a pass
using an incomplete repository-only input key.

## Ownership and validation

Source seams are cmd/tusker daemon/reconciliation/Serve/note/runtime/runner/proof
code, internal/runner, internal/serve/ui, apps/mac/TuskerBar, and scripts. This is one
integrated resource-efficiency delivery, implemented by the current interactive
session and native Sol subagents with disjoint file ownership. Existing user
changes are preserved; no daemon, background dispatch, or new provider job is
started. Root integrates interfaces and runs the complete `make check` release gate before committing. Task recording reruns the focused regressions below so the full release build is not duplicated. Unbound origin:
current Codex conversation; there is no registered automatic return route.

Nested release checks reuse their parent's live validation lock. Unrelated jobs remain serialized, and stale inherited tokens cannot bypass admission.

Regression cases include notifications during an active poll, missed external
edits, append/truncate/replace logs, incomplete records and write failures,
inherited child pipes, reused process IDs, stale receipts, hidden/resumed views,
and concurrent native refresh requests. Runtime/profile behavior is verified
with local fixtures; installed-service and human UI acceptance are not implied.
