# S46: Unify document identity, lifecycle and portable storage

## Story and implementation

As a documentation reader, I need document purpose, lifecycle and code conformance to be explicit. Today ParseDocHeaders/kindForPath infer kind from roots, scanRepository skips every INDEX.md, and docmap writes generated artifacts into docs/system. Implement the spec's explicit doc/proposal/decision kind and kind-specific lifecycle rules with independent conformance, preserving last_verified scope/date/commit semantics. Read old roots with migration diagnostics; new documents use docs/system. Move generated graph/index outputs into .tusker/_generated/docs while keeping authored indexes visible. Extend existing resolver/alias/supersession machinery for legacy references without duplicate subject ownership. Publish the normalized Document/API-facing model and compatibility expectations for cli, routing and ui consumers.

Failure cases: explicit kind beats path; invalid enums or matches without verification are rejected; legacy canonical is not silently translated into approved/implemented; ambiguous duplicate subjects fail; authored nested INDEX.md remains visible while known generated output is excluded; path escapes and symlink protections remain enforced. Reuse current APIs or document the smallest signature change. Own the wave material resolver consumer in cmd/tusker/v7_wave_authorization.go as well. Make material hashing resolve the same subject/path/section and legacy-forwarded document as authoring and packet readers, while hashing actual current source bytes and preserving authorization invalidation on change. Test missing/ambiguous subjects, changed content and moved legacy paths. Do not weaken preflight or fabricate a file at the subject name. Other command and UI files belong to dependent stories.
