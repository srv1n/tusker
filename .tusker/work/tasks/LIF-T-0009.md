# LIF-T-0009 · Make work board distinguish live execution from attempt history

## Intent

Make the Work board truthfully combine durable task lifecycle with live execution and historical attempt outcomes. `In progress` must answer "what owns work now," while failures and blockers answer "what happened previously" without making a terminated run appear active or making a failed task disappear.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | A task with a fresh claimed/running lease appears in `In progress` even though its durable status remains ready/rework; it leaves immediately after submit, fail, interrupt, or stale classification. | focused_test |
| A2 | Ready/rework/review cards expose the latest relevant attempt outcome and timestamp separately from current liveness, including failed, early-exit/declined, and interrupted outcomes. | focused_test |
| A3 | Blocker/needs-you panels deduplicate multiple attempt signals for one task and never count historical failure cards as active work. | focused_test |
| A4 | Counts update from daemon stream/reconcile events without reload and remain consistent between board, table, epic rollups, project settings, and run detail. | focused_test |
| A5 | Empty, active, stale, failed-with-no-diff, submitted-with-proof, and retry-running states have deterministic API fixtures and UI tests. | broad_test |

## Non-goals

- Do not introduce `in_progress` as a durable frontmatter status.
- Do not hide failed attempts merely because the task became dispatchable again.
- Do not label process execution as delivered work without deliverable and verification state.
