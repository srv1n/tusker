## Intent
D3 soft delivery and D4 architect inbox both need one primitive: "list pending messages for this recipient, render them for a hook, mark them delivered exactly once". There is no such command; `message list` is JSON-only and marks nothing. Build `tusker message inbox` once and declare, per harness, whether soft delivery is verified.

## Verified seams
- `agent_messages.go` store API and the CAS consume helper + identity validator added by `mcp-server` (hard dependency; shared cli.go is also serialized by this edge).
- `agent_message_commands.go agentMessageCmd` and the cli.go `message ...` route (~199) — add `message inbox` beside them; do not change existing verbs.
- `execution_ledger`/`ExecutionView`: registered external executions carry `ProviderSessionID` (the native conversation id) and `Source` direct_claude|direct_codex|direct_devin.
- Claude hook output shapes (shared_context). Codex 0.155.1 hooks need persisted trust; post-tool context injection in exec is unverified.

## Implementation contract
Locked:
- `tusker message inbox --project <id> (--run <attempt-id> | --for task:<id>|execution:<id>|operator) [--format hook|text|json]`.
  - `--run`: recipient is `task:<item>` of that attempt, validated with the mcp-server live-owner check (attempt must be the live owner). Refuses otherwise.
  - `--for execution:<id>` or, with `--format hook` and no --for/--run, the recipient is resolved from hook stdin `session_id`: every registered execution in the project whose ProviderSessionID equals it and whose Source is direct_claude|direct_codex. No registration => empty output.
- Pending = not consumed AND transport_state not 'delivered'. Emitting marks transport_state 'delivered' with a single conditional UPDATE (from its current value, WHERE transport_state<>'delivered'), so two concurrent hook runs deliver each message once. `check_messages` (MCP) still returns delivered-but-unconsumed messages and consumes them.
- `--format hook` reads the hook JSON from stdin and keys on `hook_event_name`: PostToolUse and UserPromptSubmit => `{"hookSpecificOutput":{"hookEventName":<event>,"additionalContext":<text>}}`; Stop => `{"decision":"block","reason":<text>}` only when messages were delivered in this call, else nothing. Unknown event or nothing pending => no stdout, exit 0. Any internal error => exit 0, no stdout, one line on stderr (a broken Tusker must never block or break the host session; never exit 2).
- The rendered text lists each message as id, kind, sender, reply-to and body, followed by the exact reply command (`tusker message reply --project <p> --reply-to <id> --sender <recipient address> --key <unique> --body ...`) and, for workers, a pointer to the MCP `check_messages` tool. Bounded to 16 KiB; overflow says how many were omitted and leaves them pending.
- `--format text|json` are read-only views for humans/scripts and mark nothing unless `--mark-delivered` is passed.
- Soft-delivery capability, one function `workerSoftDelivery(harness string) (supported bool, reason string)`: Claude = supported (documented PostToolUse additionalContext); Codex = unsupported "codex exec post-tool hook context unverified; hard say is used" until a recorded probe flips it; Muse = unsupported (no hook facility found in 1.3.0 help); Devin ACP = unsupported (no hook facility; prompt only between turns). Consumed by `worker-mcp-launch` (whether to inject hooks) and `ask-wait-delivery` (soft vs hard).
Proposed: file layout; the Codex probe procedure text below.

## Codex probe (probe-first, fallback documented)
Record in the task result the documentation/help evidence for (1) whether exec honours PostToolUse `additionalContext`, (2) how per-invocation hooks can be supplied without the user's CODEX_HOME given Tusker's `--ignore-user-config`, (3) what hook trust requires. Do not run a live model. Unless all three are verified from primary docs, Codex stays unsupported and the fallback is hard say (D3). A fixture test pins the current declaration so flipping it is a deliberate change.

## Failure and edge cases
- Hook fires with no pending messages: no stdout (forbidden: an empty additionalContext object that adds noise every tool call).
- Two PostToolUse hooks race: each message appears in exactly one output.
- Stop hook after a delivery: next Stop call with nothing new outputs nothing (forbidden: infinite block loop).
- Store locked/unavailable or project unknown: exit 0, stderr only.
- `--run` with a superseded attempt: refused; messages stay pending for the new owner.
- Session id registered for two projects: only the `--project` one is read; session registered twice in the project (generation replaced): only executions still referenced by a current contact generation are read.
- Message addressed to execution:X consumed via CLI before the hook runs: not re-delivered.
