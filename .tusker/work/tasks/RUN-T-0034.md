# RUN-T-0034 · Audit wrapper direct-store exit classification: daemon-less exit 0 with tracker active must record early_exit

## Intent

Suspect finding from RUN-T-0017 trial run 3, step 2. During the daemon outage window (13:18:10–13:19:20Z), AGX-T-0005's wrapper exited on child exit and its attempt recorded `Outcome: succeeded, ExitCode: 0` — yet the task was still `ready` and the restarted daemon fenced and re-dispatched a fresh attempt. Under RUN-T-0030's semantics that attempt was an early exit (tracker state still active), not a success.

RUN-T-0030's classification fix lives on the daemon's status-observation path (`cmd/tusker/daemon.go`). The wrapper also records outcomes directly to the store when it outlives the daemon (RUN-T-0013/0018 direct-heartbeat path). Audit whether that path consults tracker state before classifying exit 0, and align it with the daemon path — one classification function, both writers.

The consequence today is bounded (the mislabeled attempt still consumed cap budget and re-dispatch was capped), but `succeeded` records that aren't successes poison the evidence trail and any future learning loop built on attempt outcomes.

Semantics:

1. One shared exit-classification function (per the WORKFLOW.md Runner Exit Classification table) used by every outcome writer: daemon status path AND wrapper direct-store path.
2. Wrapper recording an outcome daemon-less: exit 0 with tracker state still `ready`/`rework` records `early_exit`.
3. If the audit finds the wrapper cannot read tracker state cheaply at exit time, record `exit_unclassified` and let the daemon's adoption/reconcile pass classify it — never default to `succeeded`.
