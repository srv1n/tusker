# DOC-T-0001 · Rebuild canonical documentation from current source

## Intent

Tusker had years of plans, tickets, reports, and competing descriptions. They
made it hard to know what the product does now. Remove that history and write
one plain guide from the current code. The result must let a new reader learn
the product without first learning its old names.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | The old tracker state and historical document packs are absent. | Repository search and fresh tracker validation |
| A2 | The current CLI, task model, proof, runtime, runners, Serve UI, macOS app, and platform support have source-backed pages. | Documentation map and source-reference audit |
| A3 | The root, component, and agent guides point to the current document set and use plain language. | Link search and documentation checks |
| A4 | User-facing docs do not describe product generations. Exact stored-format identifiers remain clear and limited. | Repository search |
| A5 | The source cleanup and generated UI still build and pass focused checks. | Go, UI, and Swift checks |

## Non-goals

- Keep historical tickets for reference.
- Preserve removed command aliases or migration guides.
- Rename stored schema identifiers. They are file-format contracts.
- Claim that a local build is a public release.

## Implementation notes

Builder appendix:

- Current product docs: `docs/system/`.
- Entry points: `README.md`, component README files, and the Tusker skill.
- Tracker: `.tusker/` after a full project-scoped reset.
- Code cleanup: retired CLI routes, dead UI routes, and old fixture text.
- Generated outputs: the document graph, tracker dashboards, and Serve UI dist.
