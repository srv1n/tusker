# ACO-T-0004 · Yield blocked workers and resume from architect or peer answers

## Intent

A blocking question must release scarce execution capacity while preserving the worker context and workspace. Its applicable answer should resume the legitimate worker, and a peer question should not wake the architect.

## Implementation notes
Mandatory spec section: .tusker/specs/agent-coordination.md#wakeups-and-waiting. The installed delivery schema inherits spec_refs at plan level; this anchor limits the required section read.

Recommended implementation: GPT-5.6 Sol / medium. Independent review: GPT-5.6 Sol / medium. These are deliberate task choices, not a reason to silently change model/effort or permissions.

Connect the existing public ask/reply path to safe waiting and the admitted recipient route. Persist question/wait intent before safely settling the sender process and releasing the execution slot; do not release workspace/resource protection prematurely. On answer, recheck task/material revision, question, recipient and current owner before scheduling. Preserve partial work and legitimate native context. An idle architect waiting for its first question must be able to release capacity through a supported public operation; expose a missing seam rather than simulating it with dummy messages or polling.

Handle reply-before-yield, answer-before-resume and stop-during-send. Existing busy/parked protection must not deadlock a legitimate answered clarification; distinguish protected active ownership from a safely settled reply wait. Retain one message/wakeup identity per claim; a safe recipient turn can include multiple individually claimed pending messages with independent receipts. Urgent blocking questions must not wait for a batch. Detect required-reply cycles and preserve relevant independent runnable work. Do not call the architect for a routine status tick, transport retry or peer-only exchange.
