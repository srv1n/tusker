# SRV-T-0002 · Edit documentation from the serve UI

## Intent

- What this is: the ability to fix a document right where you are reading it.
  The rendered document page IS the editor: place the cursor in the text and
  type — no separate edit mode, no raw-markdown textarea. The front-matter
  header card is editable in place too (status, keywords, part_of). Saving
  writes to the same file on disk that the command line and editors see, and
  the document's rules are checked before the save is accepted — a broken
  header or a duplicate subject is refused with a clear message instead of
  being written.
- Why it matters: the operator reads documentation while reviewing work; the
  moment they spot something stale is the moment they should fix it. Any
  mode switch or trip to a code editor means the correction never happens.
- What "done" looks like: open a document, click into a sentence, change it,
  save (button or Cmd+S), see the file updated on disk — and see a refusal
  message if the edit would break the document's header rules. A document
  that was opened but not edited never writes.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | The rendered document is directly editable in place (rich text over the markdown, no mode toggle, no raw YAML); a save action writes the file to disk, and an unedited document never writes. | Inline verification |
| A5 | Round-trip fidelity: an unedited document never writes; on an edited document, headings, lists, tables, code fences, and wiki-links survive serialization intact, and a body-only save leaves the YAML header bytes untouched (header edits re-marshal only the header). | Inline verification |
| A2 | A save that breaks header rules (bad front-matter, duplicate subject, tombstone without successor) is refused with the named defect and writes nothing. | Inline verification |
| A3 | After a save, the rendered page, list, and backlinks reflect the new content without restarting the server. | Inline verification |
| A4 | Concurrent-edit safety: a save against a file that changed on disk since it was loaded is refused with a reload prompt, never a silent overwrite. | Inline verification |

## Non-goals

- No creation or deletion of documents from the UI (creation stays with
  `tusker docs new`; deletion stays a tombstone workflow).
- No editing of task or epic files; documentation corpus only.
- No collaborative/multi-cursor editing; last-writer-wins is prevented by
  the revision check, nothing fancier.

## Implementation notes

Builder appendix — verify paths before editing.

- Backend: `PUT /api/docgraph/doc?project=<id>&subject=<subject>` in
  `cmd/tusker/serve_docgraph.go` alongside the SRV-T-0001 read endpoints.
  Request `{base_rev, body?, header?}`; the server splices only what was
  sent into the on-disk file (header re-marshal only when header edited, so
  untouched headers keep their exact bytes). Validate before write by
  running the corpus through `internal/docgraph` with the edited content
  substituted in memory; refuse on any new defect (422 with named defects).
  Optimistic concurrency: `base_rev` is the sha256 the client loaded (GET
  must return `rev`); mismatch with on-disk → 409, never a silent overwrite.
- The serve API is localhost-only; no auth work needed, but the write path
  must only ever address files already in the loaded corpus by subject —
  no client-supplied paths, no path escapes.
- Frontend: TipTap (already installed: @tiptap/* v3 + tiptap-markdown) over
  the SRV-T-0001 reader — the rendered view is the editor, styled to match.
  Wiki-links stay navigable inside the editor. Dirty tracking gates the
  save affordance; Cmd+S saves; refusals and conflicts surface inline.
- If the docs map artifacts go stale because of an edit (title change), say
  so in the save response (validate names it) rather than regenerating
  silently.
