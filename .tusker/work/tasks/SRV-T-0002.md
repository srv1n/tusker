# SRV-T-0002 · Edit documentation from the serve UI

## Intent

- What this is: the ability to fix a document right where you are reading it.
  From any document page in the web app, switch to an edit view, change the
  text, and save. The save writes to the same file on disk that the command
  line and editors see, and the document's rules are checked before the save
  is accepted — a broken header or a duplicate subject is refused with a
  clear message instead of being written.
- Why it matters: the operator reads documentation while reviewing work; the
  moment they spot something stale is the moment they should fix it. Sending
  them to a code editor for a one-line correction means the correction never
  happens.
- What "done" looks like: open a document, click edit, change a sentence,
  save, see the updated page immediately — and see a refusal message if the
  edit would break the document's header rules.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | A document page offers an edit mode with the raw markdown (including front-matter) and a save action; saving writes the file to disk. | Inline verification |
| A2 | A save that breaks header rules (bad front-matter, duplicate subject, tombstone without successor) is refused with the named defect and writes nothing. | Inline verification |
| A3 | After a save, the rendered page, list, and backlinks reflect the new content without restarting the server. | Inline verification |
| A4 | Concurrent-edit safety: a save against a file that changed on disk since it was loaded is refused with a reload prompt, never a silent overwrite. | Inline verification |

## Non-goals

- No WYSIWYG editing; a plain markdown textarea with preview is enough.
- No creation or deletion of documents from the UI (creation stays with
  `tusker docs new`; deletion stays a tombstone workflow).
- No editing of task or epic files; documentation corpus only.

## Implementation notes

Builder appendix — verify paths before editing.

- Backend: `PUT /api/docs/<subject>?project=<id>` in `internal/serve/`
  alongside the SRV-T-0001 read endpoints. Validate before write by running
  the corpus through `internal/docgraph` with the edited content substituted
  in memory; refuse on any new defect. Optimistic concurrency: client sends
  the content hash it loaded; mismatch with on-disk hash → 409.
- The serve API is localhost-only; no auth work needed, but the write path
  must be restricted to files inside the corpus roots (docs/system/,
  .tusker/specs/) — refuse any path escape.
- Frontend: edit toggle on the SRV-T-0001 document page; textarea + preview
  using the same renderer; surface refusal messages inline.
- If the docs map artifacts go stale because of an edit (title change), say
  so in the save response (validate names it) rather than regenerating
  silently.
