# RUN-T-0036 · Active-run cap counts retry_queued rows: queue longer than cap live-locks dispatch

## Intent

Found minutes into the second soak (2026-07-07, first exec-lane fleet after RUN-T-0035). After the operator redrove four parked rows on top of the boot fleet's continuations, the store held 8 `retry_queued` + 1 `running` rows. Every plan then returned `do_not_dispatch` with `global active run limit reached (9/5)` / `project active run limit reached (9/5)`: the active-run counter includes `retry_queued` rows, so queued rows block their own dispatch. The count only decreases when a row reaches terminal state, and no row can reach terminal state without dispatching — a permanent live-lock whenever queue length exceeds the cap. Raising the limit is not a repair: any limit is re-stalled by a longer queue, and a limit above the real queue defeats the concurrency bound entirely.

Semantics:

1. The active-run cap (global and per-project) counts only runs that actually consume capacity: leases in `running` state (live wrapper/heartbeat) and a dispatch currently in flight. `retry_queued`, `released`, `interrupted`, `parked_*`, and `unclaimed` rows do not count.
2. Queued rows dispatch as slots free, oldest `next_retry_at` first; the cap bounds concurrent execution, not queue depth.
3. The RUN-T-0028 pre-dispatch attempt-cap park guard and the sentinel over-cap corruption defense are unchanged — this task touches only the active-run capacity counter.
4. The plan blocker text stays honest: when capacity is genuinely full it names the running count (e.g. `global active run limit reached (5/5)`), never a figure inflated by queued rows.
