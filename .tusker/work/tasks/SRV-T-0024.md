# SRV-T-0024 · Notification event contract: enriched stream events + /api/summary badge counts

## Intent

The Mac shell (MAC-T-0003) will consume the serve SSE stream to post native macOS notifications and show a badge count. Today the stream (`/api/stream`, handler wired at `cmd/tusker/serve_command.go`; emitters in `cmd/tusker/daemon_stream.go`: poll_tick, dispatch, lease_transition, task_status_change, review_batch) carries only cache-invalidation keys — not enough for a client to decide "notify the human" without refetching everything.

Define and implement a notification-grade event contract, additively:

- Enrich stream events with a payload alongside the existing invalidation keys (existing serve-UI consumers must keep working unchanged): `id` (monotonic per serve process), `kind`, `project`, `task_id`, `title`, `status`, `urgency` (`info` | `attention` | `critical`), `deep_link_path` (a path that resolves in the serve UI router, e.g. `/tasks/<ID>` — match the actual router), `occurred_at` (RFC3339).
- Ensure the kinds cover the notification cases the shell needs; add kinds if the existing five cannot express them: task entered review / waiting-on-human (urgency `attention` or `critical`), run failed (`attention`), run completed (`info`), review batch ready (`attention`). Every human-gate/review event must carry a non-empty `task_id`, `title`, and `deep_link_path`.
- New endpoint `GET /api/summary` returning badge counts computed from the same projections that power `/api/needs`, `/api/runs`, and `/api/review/batch`: `{attention, review, running, failed_recent, generated_at}`. It must be cheap (single-digit milliseconds against a warm store; no full vault rescan per request) because the shell refetches it on every relevant stream event.
- Write the contract down: a doc (e.g. `docs/serve-stream.md` or the repo's existing docs location) specifying event kinds, payload fields, urgency semantics, and `/api/summary` — this doc is the interface MAC-T-0003 codes against, so it must be exact.
- De-duplication guidance in the doc: event `id` is monotonic so clients can drop replays after reconnect.

- No Swift/shell work (MAC-T-0003 consumes this contract).
- No serve UI changes (SRV-T-0023 is separate).
- No auth changes; serve remains localhost-bound.
