# SRV-T-0003 · TipTap reading and editing layer for docs and specs

## Intent

Add the reading/editing layer to `tusker serve` per the phase-2 design approved in SRV-T-0001: a TipTap-based markdown editor for docs, specs, and task body sections, tuned for fast reading first (clean typography, rendered wikilinks, table support). Writes are the risky part and must be airtight: frontmatter state fields are never editable from the UI; body edits go through a write API that reuses the same mutation/validation paths as the CLI, with CAS on `state_rev` so concurrent agent writes conflict loudly instead of silently losing work; every save re-runs note validation and surfaces issues inline. Risk is high because this adds the first write surface to the web UI.

Reuse note (from the 2026-07-06 cinta review): do NOT share code with the cinta/BrainDump app — its editor is a webpack UMD vanilla-JS monolith bridged to WKWebView with Swift-side markdown/frontmatter handling; incompatible stack. Copy and adapt only its four bridge-free Obsidian-flavor TipTap extensions (~760 lines total): TipTap/src/extensions/ofm-wikilink.js, ofm-callout.js, ofm-embed.js, and TipTap/src/ofm.js from /Users/sarav/Downloads/side/guppie/cinta. Use tiptap-markdown for round-trip (not cinta's custom parser). Its ObsidianBaseService.swift is a design reference only for any frontmatter table view.

Addendum (2026-07-06): the read layer and editor shell shipped early — the front-end team ported the cinta OFM core into `internal/serve/ui` (inline WYSIWYG doc reader/editor, markdown as source of truth, wiki-links against the vault index) saving through a mock CAS machine. A1 is therefore largely satisfied in the front-end already; this task narrows to the write side: the real CAS write API (A2), server-side protected-field rejection (A3), save-time revalidation (A4), and swapping the mock CAS for the real endpoint. Two guardrails bind the remaining work: no UI save path may reach real vault files until the server-side CAS and protected-field checks exist, and the front-end's planned save-time markdown diff guard must byte-preserve the frontmatter block through every round-trip — the editor never parses, reorders, or rewrites frontmatter, even cosmetically.
