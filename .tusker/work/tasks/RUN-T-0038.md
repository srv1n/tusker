# RUN-T-0038 · Heartbeat watchdog reaps runners silent during long non-streaming commands: idle-kill needs command-aware tolerance

## Intent

Found via the RUN-T-0015 park post-mortem (2026-07-07, session `019f3d85-…`). All three attempts spawned, streamed substantial real work (attempt 1: 96 command runs, 42 file changes over ~17.5m), then were reaped with exit 124 and `last_error: runner heartbeat dead: no events since <ts>` — each time while a long non-streaming operation was in flight: the build/test gate in attempt 1, the focused suite + `git diff` self-review in attempt 3 (its 4 focused tests had just passed). `codex exec --json` emits no JSONL events while a spawned command is still running, so the idle watchdog's "no events" window reads an actively working runner as dead. The park at cap 3 was honest given the signal, but the signal over-triggers: this is a false idle-kill, not a hang. Evidence: run rows + per-attempt logs under `runs/tusker/RUN-T-0015/`, worktree deliverables preserved on `snapshot/RUN-T-0015-20260708` (5da2e1c).

Semantics:

1. The idle watchdog must distinguish two silences. **In-flight silence** — the JSONL stream shows a command execution begun and not yet completed — is a live runner; the idle clock is suspended (or replaced by a separate, much longer in-flight cap, configurable) while that state holds. **True silence** — no in-flight item — keeps the existing window and reap behavior unchanged.
2. A reap that does fire records which silence it was in the run row's error text (e.g. `runner heartbeat dead (idle)` vs `runner in-flight command exceeded cap`), so post-mortems can tell a stall from a runaway command.
3. Existing containment is untouched: attempt caps, park-at-cap, `dispatch_declined`, and early-exit classification behave exactly as today.
