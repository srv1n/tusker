# SRV-T-0004 · Serve backend: settings API with provenance, action endpoints, notifications

## Intent

The approved serve UX (docs/design/tusker-serve-ux-packet.md and the owner-reviewed frames) needs a Go backend in the tusker binary before any frontend work can bind to it. Build the HTTP layer per the SRV-T-0001 spec (localhost-only, JSON, served by `tusker serve` alongside the embedded SPA):

1. Settings API. GET returns effective settings for the app scope and per project, with per-value provenance naming the layer that supplied it (built-in / user-global / project / machine-local), backed by the RUN-T-0002 resolver. PUT follows the write-path rule: app-scope writes land in the user-global config, project-scope writes in `tusker.local.yaml` — the committed `tusker.yaml` is never written by the API. Daemon settings (port, global concurrency, event retention) read/write the daemon settings store.
2. Read API. Projects list with attention counts; needs-me queue (open human gates, waiting_on_human tasks, failed/stale runs) with gate kind, blocked-count, and age; runs (active + recent) with runner, lane, model, token totals, liveness state; task/epic browser serving rendered contract markdown and capsule fields; per-project details (repo, branch, HEAD, vault path, active worktrees with lease state).
3. Action endpoints wrapping existing CLI mutation paths — never bypassing them: gate satisfy (with acknowledgement payloads like the provision checkbox), dispatch a ready task, resume, interrupt/release a run. Errors return the same agent-legible messages the CLI produces.
4. Notifications. The daemon emits events on human-gate creation and stale-run detection; deliver via macOS user notification (and expose an SSE/poll feed the SPA can consume), honoring the notify on/off settings. Respect the transport decision recorded in the SRV-T-0001 spec.

## Non-goals

- No document write endpoints (phase-2 editing per spec).
- No remote or multi-user access.
