# RUN-T-0035 · Codex lane: dispatch via codex exec, one process per attempt; retire the app-server turn loop

## Intent

Found in the first authorized daemon soak (2026-07-07, right after RUN-T-0017 closed). Every codex app-server attempt runs exactly ONE model turn and exits: `turn_started` → usage climbing (~70k input) → `turn_completed` → session end, ~60–90s total. Evidence: FBK-T-0003 attempt 3 events at `runs/tusker/FBK-T-0003/rev-00-execute-attempt-0003-01kwycgt7v9x4c7fsp06t4br9g.events.jsonl`. Multi-turn tasks make zero code progress and park at the attempt cap; only tasks completable in a single turn ever finish (CLN-T-0006 did).

Root cause is architectural, not a loop bug to patch: the app-server protocol is the IDE-extension interface where the CLIENT owns the conversation loop. Tusker should not own an inner turn loop at all. Prior art is unanimous — Conductor is a workspace layer around Claude Code's own loop; Gas Town drives whole interactive sessions via tmux; nobody reimplements the agent's inner loop. The agent CLI owns the inner loop; the orchestrator owns process lifecycle, workspace, tracker, and gates.

**Decision (2026-07-07, planner + operator): switch the codex lane to `codex exec --json`, one OS process per attempt.** `codex exec` runs a session to completion internally (the model loops over turns on its own), emits a JSONL event stream on stdout (`thread.started`, `turn.started`, `turn.completed` with token usage, `item.*`), and `codex exec resume <SESSION_ID>` continues a prior session with transcript intact. This also fits the wrapper model better: leases, heartbeats, kill-9 adoption, and budget kills are all process-oriented already.

Semantics:

1. **Dispatch**: a codex attempt spawns `codex exec --json` (flags for sandbox/approval per policy) under the existing wrapper. The process runs the whole task; Tusker never sends continuation turns. The session id from `thread.started` is recorded on the attempt for later resume.
2. **Continuation**: when the outer attempt loop redispatches (early_exit or runner failure with retry budget remaining), it uses `codex exec resume <session-id>` with the continuation prompt, so context is not re-read from scratch. Fresh-session dispatch (Ralph) remains the fallback when no session id exists, the session is suspected poisoned (e.g. prior attempt was budget-killed), or resume itself fails.
3. **Budget**: the governor meters cumulative usage from the event stream across the whole attempt process and kills the pid at the ceiling → `budget_exceeded` (existing outcome). Verify token growth across resumed attempts stays bounded by the per-attempt ceiling.
4. **Turn ceiling**: `max_turns` from WORKFLOW.md is no longer a loop bound Tusker drives; it becomes a safety ceiling — count `turn.started` events and kill on breach → distinct outcome `turn_cap_exhausted`, never `early_exit`.
5. **Exit classification** (RUN-T-0030) is unchanged: process exit 0 with tracker still `ready`/`rework` records `early_exit`; completion records `succeeded`.
6. **App-server retirement**: the app-server session client leaves the dispatch path entirely (delete or clearly quarantine; no half-wired dual path). Event recording ports to the exec JSONL stream — event names are near-identical.
