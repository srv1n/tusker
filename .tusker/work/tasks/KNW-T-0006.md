# KNW-T-0006 · Adopt command triages legacy documentation

## Intent

- What this is: for repositories that already have years of code and
  scattered documentation, an adoption command inventories every existing
  documentation file and produces a triage table: for each file, a proposed
  disposition — promote it into the official set, merge its content into an
  existing subject, retire it with a signpost to its replacement, or leave
  it alone (readmes, licenses, vendored files). A human approves the table
  as a whole; the command then applies it.
- Why it matters: our real repositories are not greenfield. Without a triage
  path, old documents compete with the official set and someone eventually
  reads the wrong one. Adoption must be incremental — no two-week migration
  project — but from day one every subject has exactly one findable answer.
- What "done" looks like: running inventory on a repo with mixed legacy docs
  produces a reviewable table; applying an approved table creates
  signposts and header blocks so that search always routes forward; nothing
  is deleted, and files marked "leave" are untouched.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Inventory finds markdown files outside the managed folders and emits a triage table (path, guessed subject, last change date, proposed disposition) as a file a human can edit. | Inline verification |
| A2 | Apply consumes the approved table: promote moves/stamps a header, merge records the target subject for a follow-up task, tombstone rewrites the file as a signpost, leave touches nothing. | Inline verification |
| A3 | After apply, validation passes and search routes every tombstoned subject to its successor; no file is deleted by any disposition. | Inline verification |
| A4 | The whole flow is exercised on a realistic fixture repo (mixed promote/merge/tombstone/leave) end to end. | Inline verification |

## Non-goals

- No automatic disposition without human approval of the table.
- No content rewriting for merges — merge emits follow-up work, it does not
  attempt the edit itself.

## Implementation notes

- File map (best guess): `cmd/tusker/docs_adopt_cmd.go`
  (`tusker docs adopt --inventory` / `--apply <table>`), triage model in
  `internal/docgraph/adopt.go`, fixture under `cmd/tusker/testdata/adopt/`.
- Table format: markdown table in `.tusker/scratch/docs-adopt.md` (editable,
  reviewable, committable); dispositions `promote|merge|tombstone|leave`.
- Guessed subject: slug of H1 or filename; last change via `git log -1
  --format=%cs -- <path>`.
- Disposition proposals are heuristic only (e.g. README/LICENSE/vendored →
  leave; name-similar to existing subject → merge); the agent/human refine
  the table before apply. Apply must be idempotent and refuse an unknown
  disposition value.
- Acceptance artifact for the epic (per the decision log): first real run
  happens on the rzn repo, operator-driven — NOT part of this task's
  machine proof.
