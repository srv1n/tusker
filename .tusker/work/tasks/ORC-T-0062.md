# ORC-T-0062 · Reconcile execution lifecycle and capability-aware control

## Intent

Operators can distinguish delivery state from process and provider reality, understand detached parents and unsettled children, and request only controls that Tusker can safely prove.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Delivery, admission, process, provider, outcome, session, and child attention persist as separate evidence dimensions with one documented derived phase and no transition that erases stronger contradictory evidence. | See mapped verification. |
| A2 | Cancellation records request, provider acknowledgement, wrapper signal, descendant settlement, timeout, escalation, and final operating-system evidence separately under existing generation and process-identity fences. | See mapped verification. |
| A3 | Parent completion, exit, or loss never forges child completion; detached resumable, non-resumable closed, unknown, lost, abandoned, failed-child, and needs-attention states survive restart and remain actionable. | See mapped verification. |
| A4 | Parent, managed-child, and provider-child controls are derived from fresh adapter capabilities and ownership facts; independent provider child stop or resume is absent unless specifically proved. | See mapped verification. |
| A5 | Reconciliation after daemon crash, wrapper death, provider unavailability, delayed acknowledgement, PID reuse, and duplicate control requests converges idempotently without false success or collateral process termination. | See mapped verification. |
