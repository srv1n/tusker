## Problem and intended result

Make the project Background work switch self-explanatory and auditable through the existing CLI/API. Persist actor/source, timestamp, prior/new value and scoped identity for successful enable/disable, with failure semantics that cannot claim an audited success when persistence failed. Expose the currently valid authorization scope that enable would resume, including old armed waves and task-scoped directives, without arming anything. Read this data from the UI and doctor.

## Verified seams and integration ownership

Verified: RuntimeStore.SetProjectEnabled, setProjectAutomation/setProjectEnabledCmd in daemon.go, existing project settings/action handlers in serve_actions.go and Serve project projections. Consume the upstream wake path. Existing TSK-T-0035 owns per-request setting validation; preserve it. New tests use real store rollback/failure paths, not merely log-string assertions.

## Failure cases and boundaries

Enabling resumes every still-valid authorization in that exact project, even if older than the currently selected wave; show that list/count before action and read it back afterwards. Paused, stale and inert waves are explicitly excluded. Disabling prevents new admission but does not report active work cancelled. Fresh audit events must distinguish UI, CLI and daemon-driven changes where applicable; unknown historical actor remains unknown. Concurrent toggles must return current authoritative value and scope. An effective change may race with refreshed scope; report the applied state rather than claiming the preview was a frozen transaction.
