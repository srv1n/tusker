# SRV-T-0013 · Runs API must not present unclaimed placeholder rows as running

## Intent

Found live during the RUN-T-0017 re-entry trial, step 1 ("UI honest"). With exactly one genuinely live run (store: `lease_state=running`, fresh heartbeat), `/api/runs` returned 16 rows with `leaseState: "held"`, `outcome: "running"` — 15 of them store-truth `unclaimed`, `attempt_count=0`, no heartbeat, no pid. The board shows a fleet of phantom runs; the operator cannot tell real work from placeholder rows. This is the exact dishonesty class the 2026-07-06 incident taught us to kill: UI state must be derived from verified liveness, not from row existence.

Semantics:

1. The serve runs mapping distinguishes store lease states faithfully: `unclaimed` rows with zero attempts are either omitted from `/api/runs` by default (they are queue potential, not runs) or presented with `leaseState: "unclaimed"`, `outcome: "idle"` behind an explicit `?all=true`.
2. `outcome: "running"` requires a held lease AND a heartbeat fresher than the reclaim grace window; anything else derives an honest label (`stale`, `released`, `parked_*`, `terminal`).
3. The UI run board renders only genuinely live/parked/terminal runs; phantom rows disappear.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | `/api/runs` over a fixture store with 1 live + N unclaimed rows returns 1 running run by default; unclaimed rows are absent or explicitly labeled unclaimed under `?all=true`. | Inline verification |
| A2 | `outcome` labels derive from lease state + heartbeat freshness per the reclaim grace window; a held lease with a stale heartbeat is `stale`, never `running`. | Inline verification |
| A3 | Full suite green. | Inline verification |

## Non-goals

- No store schema changes; this is presentation-layer honesty only.
- No UI redesign beyond the run board reflecting the corrected API.
