# RUN-T-0004 · Daemon run lifecycle hardening: orphans, zombies, approvals

## Intent

First real daemon dogfood (2026-07-06, SRV-T-0001 / AGX-T-0003) surfaced four lifecycle defects, all recorded as feedback notes under `.tusker/feedback/agents/2026-07-06-*`. Fix them:

1. One-shot dispatch orphans children. `tusker automation dispatch`, `tusker refresh`, and `tusker daemon run --once` spawn the runner as a child of the exiting CLI, so the runner dies seconds later while the lease stays `running` (AGX-T-0003 attempts 1-2, SRV-T-0001 attempt 1 all died this way). Either detach the child so it survives, or refuse with an agent-legible error telling the operator to use the resident daemon.
2. Zombie retry leases deadlock the queue. A `retry_queued` lease with a dead pid is never re-dispatched (next_retry_at stays empty) yet still counts against global and per-project active-run limits. The poll tick must detect dead-pid leases and either resume (session resumable) or release them.
3. Dead runs cannot be cleared. `tusker runs interrupt` fails with HOOK_FAILED live runner handle not found when the process is gone. Add `tusker runs release <ID>` (or make interrupt handle dead processes) as the sanctioned unstick path; operator needed raw sqlite surgery on daemon.db.
4. Approval auto-reject starves runners of verification. With codex approval_policy on-request, command approval requests are auto-rejected by Tusker, so the runner cannot execute its Verification commands (observed live: rtk go test rejected on AGX-T-0003). Autonomous lanes need a policy that lets sandboxed workspace commands run (approval_policy never inside workspace-write, or an allowlist mirroring the Verification-check prefixes) while keeping escalations legible.
