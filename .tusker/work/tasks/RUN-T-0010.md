# RUN-T-0010 · Kill the continuation-retry loop: plan-gated dispatch, capped continuations, honest leases

## Intent

Live incident (2026-07-06 evening, first real daemon cohort after the wave-2 hardening): **FBK-T-0002 reached attempt 88 with 1.63B recorded input tokens; RUN-T-0001 hit 72 attempts (1.50B) the same way earlier; AGX-T-0006 reached 10.** Mechanism, observed directly in the live process table: the task had already moved to `review` (`readiness: waiting_on_review`, `next_owner: reviewer`), but its run record still had an active lease. The daemon re-dispatched the execute lane anyway; the runner agent correctly ran `tusker automation plan`, saw `do_not_dispatch`, declined, and exited cleanly; the daemon recorded *"runner exited cleanly while tracker state remained active; queued continuation retry"* and dispatched again — every few seconds, forever. The D5 circuit breaker (RUN-T-0007) caps **failure** retries; clean-exit **continuation** retries are uncapped. Worse, each continuation appends a new message to the *same* codex thread, so per-attempt input grows roughly linearly and total burn quadratically. The daemon and the runner each did what their local contract said; the system looped because the dispatcher never asks the question the runner asks.

Secondary findings from the same incident, owned here because they share the fix surface:

1. **Stale leases on non-dispatchable tasks**: run records showed `lease: held / outcome: running` for tasks in `done` (CLN-T-0001), `backlog` (SRV-T-0001), and `blocked_by_dependency` (SRV-T-0008). The reconciler adopts and sweeps dead pids but never re-checks whether the *task* still warrants a run at all.
2. **No `tusker daemon stop`**: the operator had to `kill -TERM <pid>` by hand to stop the burn. `tusker daemon` offers only `run | status | limits`.
3. **D2 scope gap (document, decide, don't necessarily fix here)**: on daemon SIGTERM, all `codex app-server` children exited with it — app-server runners are stdio-pipe-coupled, so "runners survive daemon death" currently holds for shell runners only. Record the decided semantics in `docs/design/execution-stability-workstreams.md` §2 (either accept pipe-coupling for app-server runners as designed shutdown behavior, or decouple; do not leave it undocumented).

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Before any dispatch or continuation, the daemon evaluates the same eligibility the runner would get from `tusker automation plan`; tasks whose plan says do-not-dispatch (review, done, backlog, blocked, waiting-on-human) are never dispatched on the execute lane, and the run record says why it was skipped. | Inline verification |
| A2 | Clean-exit continuation retries are capped (small bound, configurable, default ≤3 per attempt window); at the cap the run goes terminal with a distinct loud state (not silent, not `interrupted`), visible in `daemon status` and the serve API. | Inline verification |
| A3 | The poll-loop reconciler releases or terminally closes run leases whose task is no longer dispatchable (done/backlog/blocked/review-with-reviewer-owner); after one poll tick no held lease exists for such tasks. | Inline verification |
| A4 | `tusker daemon stop` exists: finds the incumbent via the instance guard, requests graceful shutdown, waits bounded, reports result; `daemon status` reflects the stop. Child-runner semantics on stop are documented in the workstreams doc §2 (D2 scope note). | Inline verification |
| A5 | Full suite green including the crash-recovery e2e suite; a new e2e scenario reproduces the review-state continuation loop and proves it terminates within the cap. | Inline verification |

## Non-goals

- No change to failure-retry semantics (D5 stays as shipped in RUN-T-0007).
- No codex thread-reuse redesign beyond what the cap makes moot (fresh-thread-per-attempt is a separate optimization decision).
- No serve UI changes (the loud terminal state just flows through existing run fields).

## Knowledge delta

Failure class #5 for the workstreams doc §1: **two locally-correct policies compose into a global loop** (dispatcher trusts run-record state; runner trusts task plan; nobody reconciles the two). The general rule: any actor that *re*-dispatches work must consult the same eligibility source the work itself will consult.
