## Intent
An architect working in an interactive Claude Code or Codex session cannot receive worker questions: registered external contacts resolve to "no installed connector can deliver to a pre-existing conversation". D4 locks a UserPromptSubmit/Stop hook in that session reading the mailbox. Make the registered route truthful, document the hook the operator installs, and teach the architect agent to answer.

## Verified seams
- `execution register --contact-role architect --wave|--task ... --harness claude-code|codex --source direct_claude|direct_codex --conversation-id <native id> ...` (execution_commands.go executionRegisterContact -> RegisterExternalAgentContact) already records the session as an execution contact; wave-level contacts are inherited by members (ResolveAgentContactBinding ~280-292).
- `ResolveAgentContactBinding` returns state 'unsupported' + externalConnectorUnsupportedReason for registered externals (~353-360, ~407).
- `tusker message inbox --format hook` resolves the recipient from hook stdin session_id (message-inbox); daemon keeps these 'held' not 'unsupported' (ask-wait-delivery).
- `tusker message reply` requires sender = original recipient unless operator override (agent_messages.go putAgentMessage).
- skills/tusker/references/OPERATE.md and HANDOFF.md are the repo copies of the skill bundle (skills/tusker/bundle.go embeds them).

## Implementation contract
Locked:
- Binding for registered claude-code/codex externals becomes state `inbox` (capabilities: RetrieveResponse true, MessageWhileRunning false) with reason "delivered when that session's Tusker inbox hook runs (next prompt or turn end); not a live push". Devin externals keep the unsupported reason. No change to registration verbs or storage.
- Documentation (docs/system/orchestration.md for the model, docs/system/cli.md for commands) gives copy-paste hook snippets for Claude Code (UserPromptSubmit and Stop -> `tusker message inbox --project <p> --format hook`) and the Codex equivalent marked "unverified in installed Codex; qualify before relying on it". Snippets go in the operator's own settings by the operator; Tusker never writes them.
- Document how the architect session learns its own conversation id for registration (verify the lowest-effort documented method for Claude Code and Codex; label unverified) and the full register command.
- OPERATE.md and HANDOFF.md tell an architect agent: questions arrive as injected context with message IDs; answer with `tusker message reply --project <p> --reply-to <id> --sender execution:<its execution id> --key <unique> --body-file -`; wave reports arrive the same way; never auto-apply continuation (ApplyArchitectContinuation stays operator-invoked). Keep edits short and in the existing voice.
Proposed: whether `tusker message inbox --format text` without --for prints the registration hint.

## Failure and edge cases
- Session registered then replaced (generation 2 points elsewhere): old session's hook stops receiving; new session receives pending messages not yet delivered.
- Hook installed but session not registered: nothing injected; binding for the wave still shows the unregistered state.
- Architect replies with a wrong --sender: store refuses ("reply sender does not match original recipient"); docs show the correct sender.
- A wave report and a worker question pending together: both injected in one hook output with distinct IDs.
- Stop hook: blocks once with the new messages, then does not loop (message-inbox contract).
