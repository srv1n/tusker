# RUN-T-0040 · Merge/reconcile silently rewinds terminal task state: a closed task regresses done to review with close stamps gone

## Intent

Found after today's six-branch land wave (2026-07-08). RUN-T-0037 was closed cleanly — transition `review -> done`, accepted_by human:sarav at ~2026-07-08T02:30Z, committed with fresh close stamps. After the land wave's merges plus multiple `tusker reconcile` runs, its file read `status: review` again with the accepted_by/accepted_at/closed_at stamps gone — silently, no control operation recorded in events. An operator had to re-close it. Two suspect seams: (a) a Land merge bringing branch-side or merge-base task-file content over main's newer close (the file existed on branches predating the close), or (b) reconcile "repairing" a stale object rev in the wrong direction, rewinding the canonical file to an older revision.

Semantics:

1. **Monotonicity.** Canonical task status is monotone under merge and reconcile: a task in a terminal state (done/cancelled) can leave it only through an explicit control op that mints a fresh state_rev. No merge, no reconcile, may move a terminal task back to a non-terminal state.
2. **Fail loud, never rewind.** A merge or reconcile that would regress a terminal task — older branch/merge-base content or an older object rev arriving over a newer close — must fail loudly (CAS conflict / refuse-and-report), not silently overwrite. The operator resolves the conflict; the tracker never rewinds on its own.
3. **Seam identified first.** The actual seam is confirmed from git history before the guard lands: `git log --oneline --follow -- .tusker/work/tasks/RUN-T-0037.md` across 02bc2fa..HEAD and the six Land merges (371bbc9, 3160b97, 52b05d5, e76a593, 111cece, 9fef4b2), so the guard is placed on the path that actually rewound the file, not a guessed one.
