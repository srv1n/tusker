# FAC-T-0015 · Executable proof rows: accept re-runs command checks itself

## Intent

- What this is: today a worker runs a task's verification commands, watches
  them pass, and then writes "pass" into the task's proof table by hand — the
  system trusts the transcription, not the observation. This task makes the
  acceptance step execute the command-backed proof rows itself and record the
  results, so a result cell is something the tool observed, never something an
  agent claimed.
- Why it matters: transcribed results are the weakest link in the proof chain —
  they can be stale, mistaken, or hallucinated, and this factory has already
  caught a vacuous green (proof commands aimed at a package with no tests).
  Re-running is cheap now; the decision log locked the principle that we
  re-verify at the moment of decision instead of trusting records made
  earlier.
- What "done" looks like: accepting a task runs its command rows fresh and
  fills the results; a failing row blocks acceptance with the failure named; a
  worker no longer needs to edit result cells at all; rows requiring a human
  stay exactly as they are — waiting for the human.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Accept executes each `command:` verification row fresh and records pass/fail per row; any fail refuses acceptance naming the failing row and first error. | Inline verification |
| A2 | Workers no longer need to write result cells for command rows: a pending command row is not a gate refusal at review-request time, only at accept time (where it is executed). | Inline verification |
| A3 | `manual proof:` rows are untouched — still human-confirmed, still refusing accept while pending. | Inline verification |
| A4 | Command rows execute with the repo root as working directory and a bounded timeout; a hung command fails the row rather than hanging accept. | Inline verification |
| A5 | The executed results are written back into the task's verification table so the accepted contract shows what actually ran and when. | Inline verification |

## Non-goals

- No sandboxing or command allow-listing beyond what dispatch already applies
  — accept runs with the operator's own authority, as it does today.
- No change to manual-proof or gate semantics.
- No parallel execution of rows; serial is fine at this scale.

## Implementation notes

Builder appendix — verify the paths before editing.

- Accept path lives in `cmd/tusker/commands_v7.go` (accept + proof gate); the
  covers-parser that reads verification tables is the same one the evidence
  gate uses — reuse its row model rather than re-parsing.
- Execution: `command:` rows run via the shell from the repo root; capture
  exit code plus a short tail of output for the refusal message; write
  results back through the same table-writing path `tusker verify add` uses
  so formatting stays canonical.
- Timeout: per-row, configurable with a sane default (e.g. 10 minutes);
  on timeout record fail with "timed out".
- Review-request gating change (A2) means `finish --request-review` accepts
  pending command rows; check `v7ProofStatus` / closeout logic for where
  pending rows currently refuse.
- Keep `tusker verify add` working — agents may still pre-run and record, and
  accept re-running simply overwrites with fresher truth.
