## Intent
Operators see raw lease states, an outcome string and a `liveness` of fresh/stale/dead, where "dead" means only 120s without events. The spec defines one state model for every harness: Working, Waiting on you, Quiet, Blocked, Failed, Lost, derived from canonical run, lease and event facts, where silence never claims a hang. This task adds that single pure projection and exposes it from the CLI. Serve and UI wiring is api-ui's job.

## Verified seams
- `RunStatus` fields LeaseState, Terminal, AttemptOutcome, LastEventAt, LastHeartbeatAt, ProcessPID/PGID (runtime_store.go); `runProcessGroupAlive` (daemon.go) verifies process identity, not just PID existence.
- Lease states and outcomes: runner.go (`LeaseState*`, `AttemptOutcome*`, `projectedAttemptOutcome`).
- Open questions: `RuntimeStore.ListAgentMessagesForTask` (agent_messages.go); a question is `Kind == "question"` with empty AnsweredAt.
- Tool activity: `runActivityTail` / `cliRunActivity` / ACP activity (run_activity.go), after A:activity-fidelity merges tool start and completion by id. Codex in-flight command detection already exists as `codexExecInFlightCommandStartedAt` (runner_codex_exec_events.go).
- CLI exposure point: `buildRunInspection` / `runInspection` / `runsInspectCmd` (run_runtime_commands.go).
- Typed reason code, class and guidance from typed-reasons.

## Implementation contract
Locked rules, evaluated in order by one pure function `deriveRunOperatorState(facts, now, quietAfter)` in run_state.go:
1. Live owner = lease claimed or running and verified process group alive (or a matching live handle). With a live owner:
   - an unanswered question for this task, a recorded provider permission wait, or outcome waiting_for_human -> `waiting_on_you`;
   - else provider activity (message, tool call/result, plan, Claude `tool_progress`) within `quietAfter`, or a tool started and not completed -> `working`;
   - else `quiet`. Wrapper heartbeats alone never produce `working`: a heartbeat is not progress.
2. No live owner but lease still claimed/running and no terminal status, or outcome_unknown, or reason class `lost` -> `lost`.
3. Terminal failure whose code class is `blocked` -> `blocked`; an operator Stop or interrupt that settled (code cancelled) -> `stopped`; any other terminal failure -> `failed`.
4. Default quiet window 120s, overridable by `tusker runs inspect --quiet-after <duration>` (ponytail: no workflow knob until someone needs per-project windows).
Output object `operator_state` in `runs inspect --json`: `state`, `since`, `reason` {code, class, guidance, retryable, source} or null, `evidence` {owner_alive, last_activity_at, last_heartbeat_at, tool_in_flight, open_question_id}, `quiet_after_sec`. Human output prints one line, for example `State: Quiet — no agent activity for 4m, no tool running`.
Locked 2026-09-23 by the architect: runs that are queued (retry_queued/unclaimed before start) report `queued`, and succeeded/waiting-for-review runs report `finished`; these two are outside the six problem states and carry no reason.
Guidance text for `quiet` must never contain "hung", "stalled", "dead" or "stuck".

## Failure and edge cases
- Live owner, last activity 10 minutes ago, a `command_execution` item started with no completion: `working` with tool_in_flight true. Forbidden: `quiet` or `lost`.
- Live owner, fresh wrapper heartbeat 5s ago, last provider activity 10 minutes ago, no tool: `quiet`. Forbidden: `working`.
- Lease running, recorded PID reused by an unrelated process (identity mismatch): `lost`. Forbidden: `working`.
- Unanswered question and fresh activity at the same time: `waiting_on_you` wins.
- Question answered 1s ago: no longer waiting; falls through to working/quiet.
- Terminal with code usage_limit: `blocked` with that guidance. Terminal with code provider_error: `failed`. Terminal legacy row with no code: `failed` with code unknown, source legacy_text.
- `now` earlier than LastEventAt (clock skew): treated as fresh, never negative durations.
- Same facts evaluated twice give byte-identical JSON.
