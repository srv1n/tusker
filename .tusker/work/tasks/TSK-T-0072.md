## Intent
Run failures are classified twice by substring matching on free text: `classifyRetryFailure` (daemon.go, drives `scheduleRetry` retry/park decisions) and `runtimeFailureClass` (run_runtime_commands.go, the `failure_class` shown by `tusker runs inspect`). They disagree, match accidental words ("config", "auth" inside unrelated text), and miss real provider signals: a Codex "usage limit" message is retried as a generic failure. The spec requires failure and blocked reasons to be typed codes produced by drivers. This task defines the one closed code set, carries it from the detached child to the run row, makes retry decisions consume it, and adds the capability fields every later task declares.

## Verified seams
- `runnerProcessStatus` (runner_exec.go) is the only terminal status envelope from a detached child; writers are `writeRunnerStatusFileIfAbsentWithOutcome` (runner_raw_log_limit.go) and `publishRunnerTerminalStatus` / `monitorRunnerCommand` (runner_exec.go).
- `classifyRunnerProcessExit` (runner_exit_classification.go) turns status into outcome and reason.
- `(*Daemon).scheduleRetry` calls `classifyRetryFailure(reason)`; `failureReasonIndicatesContextPressure` chooses fork-thread vs stop-for-audit.
- `RunStatus` and `RunAttempt` live in runtime_store.go; columns are added with `ensureColumn` migrations.
- `runtimeFailureClass` feeds `runInspection.FailureClass`.
- `RunnerCapabilities` (runner.go) has no say, pre-assign or resume-after-death fields.

## Implementation contract
Locked:
- One closed reason-code set in `run_failure_reasons.go`: `usage_limit`, `auth_expired`, `permission_denied`, `sandbox_denied`, `network_denied`, `missing_access`, `context_window`, `max_turns`, `max_budget`, `config_invalid`, `provider_error`, `process_lost`, `outcome_unknown`, `cancelled`, `unknown`. Each entry declares: class (`blocked`, `failed` or `lost`), automatic retryability, the AttemptOutcome it implies, and one sentence of operator guidance that says what to fix and which action applies (for example usage_limit: "The provider usage limit was reached. Wait for the limit to reset or switch profile, then Continue."). The blocked class is exactly usage_limit, auth_expired, permission_denied, sandbox_denied, network_denied, missing_access, config_invalid, max_budget. process_lost and outcome_unknown are class `lost`. Everything else is `failed`.
- `runnerProcessStatus` gains `reason_code` (omitempty). The status writer accepts a code; existing callers pass "" until a driver maps its signal. Old status files without the field still parse.
- `RunStatus` and `RunAttempt` persist the code (new column, default ''). `classifyRunnerProcessExit` carries it through; finish paths store it with the reason text.
- `classifyRetryFailure` becomes code-first: a known code decides retryability and outcome from the table. Only when the code is empty does it fall back to today's substring rules, and that fallback reports code `unknown` with source `legacy_text` so the UI never presents a guessed code as typed. `runtimeFailureClass` is derived from the code when present and keeps its legacy text path only for rows without a code.
- Codex exec mapping lives here because Codex exec exposes these failures only as message text (research): when a codex_exec child exits non-zero, read the bounded tail of its raw log for the last `error` event or `turn.failed` error message and map it with one driver-owned function (`codexExecFailureCode`): usage/rate-limit text -> usage_limit, 401/unauthorized/login text -> auth_expired, sandbox/permission text -> sandbox_denied, otherwise provider_error. This text matching is labelled as the Codex driver's mapping, not a daemon classifier.
- `RunnerCapabilities` gains `SoftSay`, `HardSay`, `PreassignSessionID`, `ResumeAfterDeath` (all false by default, so an undeclared driver is honestly unsupported). This task sets no driver's values; each driver task sets its own.
Proposed (worker may refine with a note in the task): the exact helper names, and whether the reason source (`driver` vs `legacy_text`) is persisted or derived.

## Failure and edge cases
- Codex exec raw log ends with `{"type":"error","message":"You've hit your usage limit..."}` and exit 1: run records code usage_limit, outcome blocked, not retried. Forbidden: a retry_queued lease or a new attempt.
- Same Codex log but message "stream disconnected before completion": provider_error, retryable per table; a retry is scheduled exactly as today.
- A pre-existing run row and status file with no code and reason "invalid token": legacy fallback keeps today's non-retryable blocked decision, reports code unknown with source legacy_text. Forbidden: presenting auth_expired as if a driver had typed it.
- Reason text containing "configuration" inside an unrelated tool output line, with a driver code provider_error: the code wins; no config_invalid classification.
- `delivery_unknown` / "child exited without terminal status" text with no code: still outcome_unknown and not retryable (projectedAttemptOutcome behaviour preserved).
- Context-window code still selects the fork-thread supervisor decision.
- A status file written by an older binary during an upgrade (no reason_code) parses and classifies via fallback.

## Ownership and coordination
Owns the files listed. daemon.go, runtime_store.go and run_runtime_commands.go are also declared by held W-0039 tasks; if one is active, serialize and ask. Downstream in this wave: run-state reads the code and class; say-continue-cli puts the typed summary into Continue; claude-soft-say, muse-parity and devin-parity map their native signals to these codes and set their capability fields. None of them may add codes; a needed new code is a question to the operator.
