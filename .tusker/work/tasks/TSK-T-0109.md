## Problem

A reviewer can return `changes_requested` with a blocking finding that only
asserts a defect. `parseReviewerFinding` (cmd/tusker/reviewer_finding.go)
requires `acceptance`, `evidence`, `consequence`, and `closure_condition` for a
blocking finding, but nothing requires the reviewer to show the defect is real.
A false-positive blocking finding costs a full rework loop: the implementer
repairs nothing real, and a second independent review must close it.

The fix borrows the "prover" phase from Anthropic's Bug Hunter flow: a
candidate finding must be reproduced before it can block.

## Intended change

Add one optional field to `reviewerFindingRecord`:

```go
Reproduction string `json:"reproduction,omitempty"`
```

`reproduction` is the exact shell command the reviewer ran against the
reviewed material that demonstrates the defect (a failing test, a failing
build, a command whose output shows the wrong behavior). Free-text steps are
accepted when no command can show the defect (for example a docs-only defect),
but the field must be non-empty.

Rules (locked decisions):

1. `validateReviewResultFindings` refuses a `changes_requested` result whose
   blocking finding has `repair_scope: material` and an empty `reproduction`.
   Error text: `blocking material finding requires reproduction: the command or
   steps that show the defect on the reviewed material`.
2. Proof-scoped blocking findings (`repair_scope: proof`) and advisory findings
   do not require `reproduction`.
3. `parseReviewerFinding` trims the field and caps it at
   `reviewResultMaxEvidenceChars`; it does NOT require it. Stored findings from
   older reviews must still parse (the requirement lives only at submission in
   `validateReviewResultFindings`).
4. `reviewerFindingFlagExample` includes a `reproduction` value on the blocking
   example, so every generated reviewer prompt (cli.go help,
   workflow.go review template, work_session_cmd.go next-step text) teaches it.
5. The returned-to-implementer section (`returnReviewerFindingToImplementer` /
   generated reviewer-findings section) shows the reproduction so the
   implementer can run it first and confirm the defect before repairing.
6. The review prompt text in workflow.go near the `changes_requested` guidance
   tells the reviewer to run the reproduction and put its output receipt in
   `evidence`.

Out of scope: Tusker executing the reproduction itself. That is a later step.

## Edge cases

- A finding with `reproduction` on an advisory or proof-scoped finding is
  accepted and displayed.
- Whitespace-only `reproduction` counts as empty.
- `review_proposal.go` builds `reviewerFindingRecord` values; make sure any
  blocking material finding it builds carries a reproduction or is not
  submitted as blocking.

## Docs

Update docs/system/proof-and-closeout.md where reviewer findings are described
to state the reproduction requirement in one or two sentences.
