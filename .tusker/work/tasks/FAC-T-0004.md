# FAC-T-0004 · Warn when a task's plain-language layer slips into code words

## Intent

The top layer of a task is a promise to a non-engineer reader. That promise is
easy to break: an author slips a file path, a function name, or a wall of jargon
into the plain layer, and suddenly the former product manager can't follow it.

This task adds a check that flags when the plain top layer slips into code
words, so the promise is actually kept before a task is allowed to move forward.
It looks only at the top layer; the builder's appendix is exempt, because that
is where the technical detail belongs.

Done looks like: a task whose top section is full of code words is flagged with
a clear message that points at the offending words, a clean plain-language top
passes quietly, and a demanding task cannot go ready while its top layer still
reads like code.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Code words in the top layer are flagged, with the offending word named in the message. | Inline verification |
| A2 | The builder appendix is exempt from the check. | Inline verification |
| A3 | A clean plain-language top passes, and a demanding task cannot go ready while its top layer fails. | Inline verification |

## Non-goals

- No auto-rewrite of offending text; the check warns, it does not edit.
- No linting of the appendix, acceptance commands, or verification rows — only the plain top layer.
- No exemption for trivial tasks beyond what the spec's ready-gate rules already grant.
- No natural-language grading beyond spotting obvious code-shaped tokens (paths, dotted filenames, backticked or camel-case symbols).
