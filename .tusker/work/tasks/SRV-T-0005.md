# SRV-T-0005 · Snapshot fixture generator: real vault + queue state emitted in the UI's domain shapes

## Intent

The serve UI (`internal/serve/ui`) was built front-end-first against hand-written mock fixtures, and the drift is already documented: fabricated task IDs, wrong epic counts, a missing TRC epic, and a "needs you" count of 3 when the true value was 0 (see `internal/serve/ui/BACKEND-GAPS.md` §0 and `docs/design/serve-ui-supplement.md` §1). This task ships the fix named there as the single highest-value gap: `tusker serve fixtures --snapshot`, a CLI subcommand that emits fixture JSON from the real vault (`.tusker/work/**` frontmatter) and the real automation queue (the same data behind `tusker automation queue --json`), in exactly the shapes declared in `internal/serve/ui/src/types/domain.ts`. The front-end's mock seam (`src/mock/` + `src/lib/api.ts`) consumes the generated file unchanged.

Honesty rules: fields the backend cannot yet supply (rework/bounce count, wave-boundary signal, gate payloads, heartbeat fields — the BACKEND-GAPS §3 list) are emitted as explicit nulls, never invented. The `Risk` domain type must gain `"critical"` — the Go schema defines four tiers (`cmd/tusker/schema.go`: low/medium/high/critical) and the needs-me derivation's signal 1 depends on it. Epics are derived from the vault, so every epic present appears (regression: TRC must show up). Output is deterministic for a given vault+queue state — stable ordering, no timestamps injected at generation time beyond those in the source data — so committed snapshots diff cleanly.

Deprioritized (2026-07-06, operator decision): no further mock-fixture work — real endpoints (SRV-T-0002, now unblocked and p0) are the path to honest data. This task is retained at p3/backlog because a deterministic vault+queue snapshot emitter is still the right way to build test fixtures for the serve API's own tests; it is no longer a demo-honesty vehicle and must not be dispatched ahead of SRV-T-0002.
