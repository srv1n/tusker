# SRV-T-0005 · Status-change notes reach the task page and the next worker

## Intent

- What this is: when the operator changes a task's status from the web UI and
  writes a note explaining why, that note currently lands in an append-only
  history file that nothing displays. The person never sees their own words
  again, and the agent picking the task back up never reads them. This task
  makes the note visible in both places: a small activity history on the task
  page, and the note included in the briefing the next worker receives.
- Why it matters: a rework note is a human decision — the one artifact the
  factory's economics say must never be dropped. Today the operator's
  instruction silently disappears, which means the next attempt can redo the
  work without addressing the actual complaint, and the operator loses trust
  that writing notes does anything.
- What "done" looks like: change a status with a note; the task page shows a
  short history ("review → rework, by you, with your note, two minutes ago");
  the next worker's briefing for that task quotes the note; a human action
  from the UI is attributed to the human, not to a generic agent name.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | The task detail page shows recent status transitions with actor, time, and the note text; the operator's rework note is readable right where they changed the status. | Inline verification |
| A2 | The next worker's task briefing (packet/capsule) includes the most recent status-change note when the task is in rework, so the complaint is addressed, not guessed at. | Inline verification |
| A3 | Status changes made from the UI are attributed to the human operator, not silently recorded under an agent actor name. | Inline verification |

## Non-goals

- No general event-stream browser; only task-scoped recent transitions.
- No editing or deleting of history entries.

## Implementation notes

Builder appendix — verify paths before editing.

- Events already carry the payload: `emitV7Event` in
  `cmd/tusker/v7_control_cmd.go` writes `status_changed` events with
  `{from, to, reason}` to `.tusker/events/YYYY/MM/<ID>--*.json`. Read them
  task-scoped (filename prefix) — do not build an index.
- Serve: add recent transitions to the task detail payload in
  `cmd/tusker/serve_command.go` (`handleTask`); UI renders them on the task
  page near the current-state card (`internal/serve/ui/src/` task detail
  feature).
- Packet/capsule: `tusker packet <id> --for agent` and `show --capsule`
  assembly in `cmd/tusker` — include the latest rework reason line.
- Attribution (A3): the serve status action defaults `by` to
  `agent:<username>`; when the request comes from the UI without an actor,
  record `human:<username>` instead (see `handleTaskStatusAction` in
  `cmd/tusker/serve_actions.go`).
