# LIF-T-0013 · Separate interactive ownership from daemon automation and forbid nested runners

## Intent

Make execution ownership unambiguous across direct interactive sessions, resident daemon automation, dispatched implementation workers, and reviewer workers. Direct sessions own their tools and edits without launching nested model runners; only an independently running, explicitly enabled daemon may create background runner processes.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Repo instructions, the canonical Tusker skill, project canon, and lifecycle specs define the same four execution roles without contradictory manual-claim or nested-runner guidance. | Instruction-contract tests and skill validation. |
| A2 | A Codex/Claude session environment cannot start a foreground dispatch daemon or recursively invoke automation dispatch, while read-only planning/status and ordinary shell work remain available. | Focused CLI guard tests. |
| A3 | Project automation remains an explicit per-project opt-in and only the resident daemon dispatches ready/rework implementation work. Dispatched workers are scoped to exactly one injected task/attempt. | Existing and focused daemon dispatch tests. |
| A4 | Review dispatch is independent, read-only, one review per handoff, and bounded to three automated review cycles before human/operator intervention. | Reviewer policy and lifecycle tests. |
| A5 | Direct interactive work does not require project automation enablement or a daemon-run claim; coordination with already-running automated work is an inspection/conflict check, not permission to code. | Skill/spec assertions. |

## Non-goals

- Do not make task creation itself dispatch work.
- Do not let implementation workers edit as reviewers.
- Do not require a resident daemon for direct human-driven Codex or Claude sessions.
