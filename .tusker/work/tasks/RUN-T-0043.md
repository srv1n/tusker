# RUN-T-0043 · Daemon dispatch: claim runs via atomic ClaimRunLease CAS, not blind UpsertRun (prevent stale-claim overwrite of concurrent transitions)

## Intent

From the GPT-5.5 Pro Extended pre-push review (handoff `cgpt_mrc05ks3_5fcda4b9`), MEDIUM finding on dispatch concurrency. `dispatchRun` (`cmd/tusker/daemon.go:2194`) claims work by mutating an in-memory `RunStatus` and blindly `UpsertRun`-ing it, even though `RuntimeStore` already exposes an atomic `ClaimRunLease` (`cmd/tusker/runtime_store.go:976`). The workspace prep, prompt rendering, `SaveAttempt`, and final upsert are **not** guarded by a compare-and-swap against the row read at poll start.

Consequence: a concurrent control action (stop/cancel/limit change from the CLI or serve UI) or a second `daemon`/`once` process can be silently overwritten by a stale dispatch claim — a lost update / lease race that can double-dispatch or clobber a just-changed runtime transition. Low probability in single-daemon operation, but it undermines the invariant that the active-run cap and lease state are authoritative.

Fix: move dispatch claiming to the atomic store operation (`ClaimRunLease`) with `owner`/`generation`/`work_revision` preconditions **before** any external side effects (workspace prep, spawn), and make every subsequent write in the dispatch path conditional on the same `lease_owner` + `lease_generation`. On a failed CAS, abort the dispatch cleanly (another actor won the row) without side effects.

## Non-goals

- No multi-daemon coordination feature work; this only closes the existing single-store CAS gap.
