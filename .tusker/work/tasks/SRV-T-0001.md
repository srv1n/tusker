# SRV-T-0001 · Draft the design spec for tusker serve

## Intent

Design a local web control room served by the tusker binary itself (`tusker serve`): a modern SPA — React + Vite + TanStack Router + TanStack Query + Tailwind — built to static assets and embedded in the Go binary via go:embed, talking to a JSON API that reads the SQLite runtime store and vault markdown. Single-binary distribution is preserved; localhost-only. The organizing principle is attention routing, not chronology: the first view answers "what needs me now?" (human gates, `waiting_on_human` tasks, failed runs), then active runs (attempt status, token totals, workspace), then a task/epic browser rendering markdown contracts, then review evidence. The spec must define: routes and views, the JSON API surface and its mapping from SQLite tables + vault files, the refresh model (poll vs SSE), the frontend build/embed pipeline (pnpm + Vite, no external CDN at runtime), what deliberately stays in Obsidian, MVP cut lines, and the phase-2 editing architecture (SRV-T-0003): a TipTap-based reader/editor whose writes go through the same mutation paths as the CLI with CAS on `state_rev` and protected state fields — design now, implement later. Write it as `docs/specs/10-tusker-serve.md`.

Design-review outcomes (2026-07-06, owner-reviewed UX frames) the spec must incorporate:

1. Serve is a daemon-level app spanning all registered projects (multi-project sidebar), not a per-repo page.
2. The MVP API is read-mostly plus a narrow set of action endpoints wrapping existing CLI verbs — gate satisfy (with acknowledgement inputs like the provision checkbox), dispatch/start run, resume, interrupt. Document editing remains phase-2 (SRV-T-0003).
3. Settings API: read effective settings with per-value provenance (built-in / user-global / project / machine-local, per RUN-T-0002); writes follow the RUN-T-0002 write-path rule — app-level edits land in user-global config, project-level edits in `tusker.local.yaml`, never the committed `tusker.yaml`. The UI labels each value's source.
4. Notification hooks: daemon emits notifications on human-gate creation and stale-run detection; spec defines the transport (macOS notification, web push, or both) and the on/off settings shown in the design.
5. Status-column mapping: board columns derive from V7 statuses; "in progress" is a projection of an active run on a ready task, not a durable status; rework renders as a badge, not a column.
6. Draft-contract affordance: tasks without a filled contract show a "Draft contract" action (planning-lane, future work) — the spec fixes the copy so the UI never implies a placeholder contract can be Ready or runnable.
7. Incorporate `docs/design/serve-ui-supplement.md` (2026-07-06): the per-region data contract (one source of truth per UI region), the closed derived definition of "needs me" (five signals, explicit non-signals), wave-boundary review batching as the primary review surface, the roster's three first-class columns (working-on / blocked-on / handing-off-to) with handoff edges, unblock actions as thin wrappers over existing CLI verbs, and the mock-fixtures-from-real-snapshot policy.
8. Reconcile with the shipped front-end rather than reinventing it: the SPA exists at `internal/serve/ui` (Bun tooling, not pnpm — update the build/embed pipeline section accordingly), `internal/serve/ui/src/types/domain.ts` is the de-facto wire contract, and `internal/serve/ui/BACKEND-GAPS.md` is the front-end team's statement of the API surface (§4 endpoint table) and missing fields (§3). Where the spec disagrees with those shapes it must say so explicitly and why; silent divergence is a defect.
