# RUN-T-0005 · Parallel work streams: auto-landing, file claims, git abstraction

## Intent

Scale per-project concurrency from 1 to N (target 3-4 parallel streams) without the operator ever touching git. Three mechanisms, layered:

1. Planning-time overlap avoidance. Tasks may declare `file_claims` (path globs) in frontmatter, normally written by the planning agent at authoring time. Dispatch never runs two tasks with overlapping claims concurrently — it serializes them instead. Claims are advisory (agents are not jailed to them) but they make conflicts rare by construction, per the lean fan-out doctrine: disjoint ownership, union merge.
2. Isolation on demand. When N > 1 runs are active, additional runs auto-select worktrees per RUN-T-0004 A5 / RUN-D-0001; the first run may stay in place. Subagent policy per profile (RUN-T-0002) governs what each stream may spawn beneath itself.
3. Landing without git verbs. When a run's work is accepted by review, Tusker lands it automatically if it fast-forwards or rebases cleanly onto HEAD, and records landed state on the run. On a real conflict, the branch is parked untouched and a needs-me card is created naming the two heads and the conflicting files — presented as a choice, not a git exercise. Optionally (off by default), a conflict-resolution lane may take one agent pass at the conflict before the card is created, with a dedicated prompt; if it cannot produce a clean, test-passing resolution the branch parks as usual (design reference: docs/design/competitive-notes-conductor.md). Work is never discarded: branches persist until landed or explicitly dropped by the operator; after a successful land, branch cleanup is configurable (default: keep the branch). Interrupt or kill mid-run must leave the repo clean (worktree discarded, or in-place run rolled to a stash-like safe point) — never a half-landed state.

The operator's entire surface is: write the contract, answer needs-me cards. Everything between is machine.

### Flow governor addendum (2026-07-06, from docs/design/aie2026-adoption-plan.md workstream 3)

Concurrency without flow control floods the operator. Landing capacity, not run capacity, is the binding constraint, so the governor regulates *output in flight*, not just active runs:

- `max_open_landings` (per project, default 1): the count of accepted-but-unlanded branches. When at the cap, dispatch of new fresh runs pauses; continuations of already-running work are exempt. This is the backpressure valve — dispatch keys off review/landing state, not only the active-run count.
- Pre-flight placement: the open-landings check runs at dispatch decision time, before any workspace/worktree is created — never after checkout.
- Legibility: a run held by the governor gets a queue reason naming the branch(es) it is waiting behind, distinct from the active-run-limit reason.
- Ratchet, not oscillation: raising concurrency is a deliberate config change; the governor never auto-raises. Auto-lowering on repeated conflict-parks (a disturbance dampener) may be logged as a recommendation but must not silently change config.

## Non-goals

- No CRDT or live co-editing; git remains the merge substrate underneath.
- No cross-repo streams (single project scope).
- No automatic conflict resolution beyond clean rebase by default; the agent-assist lane is opt-in and a failed assist still escalates.
