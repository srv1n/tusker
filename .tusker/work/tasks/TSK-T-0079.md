## Intent
Workers can only ask by shelling out to `tusker message ask` with hand-built flags, and they cannot address the operator at all (recipient kinds are task|execution). D4 locks an injected Tusker MCP server bound to the worker's run identity as the ask route for all four harnesses. Build `tusker mcp serve`: a stdio MCP server whose tools write only through the existing message store.

## Implementation contract
Locked:
- `tusker mcp serve [--max-wait <seconds>]` speaks newline-delimited JSON-RPC 2.0 on stdin/stdout, diagnostics on stderr only. Methods: `initialize` (reply with the client's requested protocolVersion when supported, else the newest supported; capabilities `{tools:{}}`; serverInfo name `tusker`), `notifications/initialized` (ignored), `ping`, `tools/list`, `tools/call`, `notifications/cancelled` (aborts the matching in-flight wait). Unknown method => -32601; malformed JSON => -32700 and keep serving; stdin EOF => exit 0. No new dependency.
- Identity comes only from env: TUSKER_PROJECT_ID, TUSKER_ITEM_ID, TUSKER_ATTEMPT_ID, TUSKER_LEASE_GENERATION, TUSKER_WORK_REVISION. Every `tools/call` re-validates against the runtime store: run for (project, item) exists, `ActiveAttemptID == TUSKER_ATTEMPT_ID`, `LeaseGeneration` matches, not Terminal, lease claimed|running. Failure => tool result `isError:true` with a plain reason and NO store write. `initialize`/`tools/list` still succeed so the harness does not fail to start.
- Sender is always `task:<TUSKER_ITEM_ID>`; tool arguments cannot set sender, project, revision or generation. WorkRevision/RouteGeneration are stamped from env.
- Tool `ask` {to: "architect" | "operator" | "peer:<name>", question: string, wait_seconds?: int}: architect/peer resolve through `ResolveEffectiveAgentContact`; an unresolved architect is an error telling the agent to ask `operator` (never a silent reroute). Operator recipient is the new address kind `operator` with id `operator` (accepted by `validate()`/`normalizeAgentAddress` in agent_messages.go only; contacts stay task|execution). Idempotency key `mcp:<attempt>:<first 16 hex of sha256(to NUL question)>` so a retried call returns the existing message — and its answer if already answered (reply-before-wait race). Kind `question`, ReplyRequired true, YieldSender = wait_seconds > 0. Operator-addressed questions do not queue an agent wakeup (the UI is their delivery); other recipients keep `queueAgentMessageWakeup`.
- Wait: poll the store (about every 2s, zero model calls) for an answer whose ReplyTo is the question; bound = min(wait_seconds, --max-wait, 900). If the request carried `_meta.progressToken`, emit `notifications/progress` at least every 15s. On answer: mark the answer consumed and return its body plus question/answer IDs. On timeout: return a non-error result stating the question ID is recorded and pending, and that if the agent cannot continue without it, it should say so and end its turn; the answer arrives by soft delivery, hard say or continue.
- Tool `post_update` {text}: append event kind `worker_update` (payload text, bounded 4 KiB) to TUSKER_EVENT_SINK via `EventLog.Append`. Missing sink => isError. It writes no message row.
- Tool `check_messages` {}: return messages addressed to `task:<item>` that are not consumed (kinds answer, instruction, notice, question from peers), oldest first, each with id/kind/sender/replyTo/body, then mark each consumed with `MarkAgentMessage`. Empty => "no pending messages".
- Tool output never includes env values, state-root/DB paths, endpoint bindings, tokens or other tasks' messages.
Proposed: file split and exact tool description wording.

## Failure and edge cases
- Env present but attempt released/superseded (generation bumped): ask refuses; forbidden: a message row sender `task:<item>` from the stale attempt.
- No TUSKER_ATTEMPT_ID (interactive shell): every tool refuses; forbidden: falling back to `--sender` or any operator identity.
- Same ask twice (harness retry): one row; second call returns the same ID (and answer if present). Same key, different question text => different key by construction; forbidden: idempotency error surfaced as a crash.
- Answer committed between the ask insert and the first poll: returned immediately.
- Client cancels during wait: in-flight call ends, question stays pending, server keeps serving other requests.
- wait_seconds 99999: capped at --max-wait; forbidden: unbounded blocking.
- Body > 32 KiB: store validation error returned as isError.
- Two concurrent `check_messages` calls: a message is returned by at most one (consume-if-not-consumed under a single UPDATE ... WHERE consumed_at=''); forbidden: duplicate delivery.
- Operator address `operator:operator` passed to contact APIs (`parseAgentAddress`) is still rejected.
