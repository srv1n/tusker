## Intent
The operator's "needs you" surfaces show only human-owned gates, rework and terminal failures. A worker question addressed to the operator (new in mcp-server), or to an architect with no deliverable route, is invisible unless the operator opens the task inspector. Project those questions, plus permission waits, into the existing human-action/needs feed — no second store — and let the operator answer in place.

Cross-wave: depends on wave B `run-state` for permission-wait facts; if B exposes no permission-wait fact, ship questions only and say so in the result.

## Verified seams
- `serve_human_action.go serveHumanActionsForTask` (gates only), `serve_types.go serveHumanAction` (gate-shaped), `serve_needs.go serveNeeds`, `serve_command.go buildSnapshot` (~1057; `snap.needs = serveNeeds(...)` ~1158) and task detail `HumanActions` (~1990); snapshot is cached — `invalidateProjectSnapshot`.
- `serve_agent_messages.go handleAgentMessageSend` answers via `PutAgentMessageAsOperator` when replyTo is set; it does not invalidate the snapshot today.
- `ListAgentMessages`, `ListAgentMessagesForTask`, `ResolveAgentContactBinding` (route state per contact).
- UI: HumanActionCard.tsx, TaskInspector.tsx ask/answer form (~245-266), lib/api.ts agentMessage.

## Implementation contract
Locked:
- An item is emitted for each question with ReplyRequired, AnsweredAt empty, not expired, sender task:<id> in this project, where the recipient is `operator`, OR the recipient's binding state is unbound/unsupported/stale (nobody else can answer). Questions to a bound/inbox architect are not operator items. Item: kind `question`, title "Question from <task>", message ID, body, asked-at, recipient label, task ID, and whether the worker is waiting (YieldSender).
- Items are derived at snapshot build from the store (load open questions once per snapshot; no new table). Permission waits from B run-state render as kind `permission` with B's allowed actions.
- Answer uses the existing POST (replyTo => PutAgentMessageAsOperator); on success the server invalidates the project snapshot so the next canonical readback no longer contains the item. The UI removes the card only after readback, never optimistically.
- HumanActionCard renders question items with the body, who asked, and a Reply textarea; TaskInspector shows the same open question at the top of its message section with Reply prefilled (reuse the existing form state).
Proposed: whether question items extend serveHumanAction (with empty GateID) or a sibling type in the same feed; pick the smaller diff that keeps gate items unchanged.

## Failure and edge cases
- Question answered by the architect through the inbox before the operator acts: item disappears on the next snapshot. Operator override would still accept a second answer, so the UI shows "already answered" from readback and disables Reply when AnsweredAt is set; forbidden: a second answer posted from a stale card.
- Double-click Reply: idempotency key per item prevents two answers.
- Expired question: not listed.
- Task in rework: gates are suppressed today; questions are still shown (a waiting worker needs an answer regardless).
- Project without any messages: no extra DB work per task (one query per snapshot).
