# SRV-T-0007 · Render cached Serve UI during daemon startup

## Intent

- What this is: Keep the last useful Tusker screen visible while the local
  runtime starts, then refresh it from live state as soon as the runtime is
  available.
- Why it matters: Opening the desktop app currently replaces useful context
  with an opaque startup screen even though the UI shell and recent read-only
  data are safe to show immediately.
- What "done" looks like: Warm launches show the cached navigation and screen
  content immediately, live data replaces it in the background, and a native
  retry screen appears only when no usable UI can be rendered.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | The desktop window attempts to render the cached Serve UI before waiting for daemon health and does not cover committed content during runtime state changes. | Automated Swift tests cover the optimistic request and visibility state machine. |
| A2 | Main-screen read queries restore bounded recent data from local storage and silently revalidate against the live API. | UI tests cover allowed query keys, expiry, restore, and persistence. |
| A3 | Serve permits the HTML shell to be stored for revalidation and gives fingerprinted assets immutable caching while API responses remain non-cacheable. | Focused Go tests assert cache headers for the SPA shell, assets, and JSON. |
| A4 | A cold launch with no usable cache still exposes an actionable native retry state. | Automated Swift tests cover fallback behavior. |

## Non-goals

- Do not cache mutations, credentials, raw logs, editor bodies, or arbitrary
  knowledge documents.
- Do not delay Serve until project snapshots or daemon reconciliation finish.
- Do not add a service worker or create a second source of truth.
