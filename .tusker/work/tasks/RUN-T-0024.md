# RUN-T-0024 · Redrive must reset the attempt window it counts against

## Intent

Found live during the RUN-T-0017 re-entry trial. `tusker redrive` on two tasks whose retired run rows carried attempt counts of 4 and 15 re-queued them as non-terminal **without resetting the attempt count** — so the sentinel's `attempt_count_within_caps` check (cap 3) opened the invariant circuit on the very next tick, before any new attempt could run. The operator's sanctioned recovery path is self-defeating: redrive → instant circuit → no dispatch → repair by hand (sqlite `attempt_count=0`) → resume.

Redrive's contract is "give this task a fresh chance under fresh limits." That must mean one coherent reset:

1. `tusker redrive` starts a new attempt window: attempt count (or the equivalent baseline the cap check compares against) resets, the budget window resets (already implemented), cooldown clears, and the run row is marked queued with a redrive event carrying actor + reason.
2. History is preserved: prior attempts stay in the attempts table and event log; the reset is of the *counting window*, not the record.
3. The sentinel treats a freshly redriven run as clean: no `attempt_count_within_caps` violation from pre-redrive attempts.
4. Exactly-once semantics stay: a redriven run that loops again re-parks at the cap and needs a fresh explicit redrive.
