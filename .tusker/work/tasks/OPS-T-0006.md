# OPS-T-0006 · Make tusker land drain detached completed worktrees without hidden setup

## Intent

`OPS-T-0005` exposed the first live `tusker land` rough edge: a reviewed/proof-satisfied task in a detached completed worktree could not be landed because the task had no wave membership and no `task/<ID>` branch. The command failed with the correct model-level guard, but gave no recovery command and did not support the queue-drain shape it was built to serve.

Make the landing path explicit for this case. Either teach `tusker land` to create/attach the needed wave and consume a detached completed worktree safely, or make the refusal actionable enough that an operator can run one printed next command without knowing the internal wave/branch ceremony.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | A task with no wave membership gets an actionable `tusker land` refusal that names the required wave command or supported flag. | Inline verification |
| A2 | A detached completed worktree with no `task/<ID>` branch has a supported branchification path, or `tusker land` explains the exact branch command it expects before retry. | Inline verification |
| A3 | The recovery path is covered by a live-style merge-lane test that starts from a review/proof-satisfied task and a detached worktree. | Inline verification |
| A4 | Successful `tusker land` prints a concise landing summary with task, source branch, target, gate result, commit, and whether main moved or remained waiting on open wave tasks. | Inline verification |
| A5 | A batch where no requested task lands exits non-zero or prints an unmistakable failed-batch summary before applying rework transitions. | Inline verification |
| A6 | Failed merge summaries skip progress chatter such as `Auto-merging ...` and preserve the first actionable conflict/error line and path in the audit/task `next_action`. | Inline verification |

## Non-goals

- No weakening of the serialized wave lane.
- No direct main merge path for non-done tasks.
- No hidden task closes.
