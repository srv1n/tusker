# FAC-T-0013 · Daemon dispatch honors project automation setting and resolves a working runner

## Intent

- What this is: two fixes to how the background runtime decides to start
  work. First, it must respect the project's own automation switch: when a
  project says automation is off, the runtime may watch it but must never
  start jobs for it, no matter what the runtime's own registry says. Second,
  before starting any job it must prove the worker program it found actually
  runs, and search the same places the operator's own shell would — today it
  can pick a broken leftover install while a working one sits elsewhere.
- Why it matters: on 2026-07-21 the runtime dispatched two tasks from a
  project whose automation was explicitly off, handed them to a broken
  worker install, and filled the attention list with failures the operator
  never asked for. An orchestrator that starts work against an explicit
  "off" switch cannot be trusted with more autonomy.
- What "done" looks like: with a project's automation off, promoting tasks
  to ready causes no dispatch attempts and a log line explains why; with a
  broken worker first in line and a working one elsewhere, dispatch finds
  the working one or refuses before creating a failed run.

## Acceptance

| ID | Outcome | Proof |

| A1 | A project with automation disabled in its own configuration is never dispatched, even when enabled in the runtime registry; the skip is logged with the reason. | Inline verification |
| A2 | Registry enable/disable controls polling cost only; a dispatch-disabled or registry-disabled project stays fully visible and its tasks remain claimable by interactive sessions. | Inline verification |
| A3 | Runner resolution health-checks the resolved executable before dispatch and falls back to other PATH candidates (including the user's login-shell PATH) when the first is broken. | Inline verification |
| A4 | When no working runner exists, the task stays ready with a clear preflight message; no failed run record is created for a runner that never started. | Inline verification |
| A5 | Work registers identically no matter who drives: an interactive session (Claude Code or codex, outside the daemon) can claim, start, heartbeat, and submit a run on a project whose automation is off — and even one registry-disabled — and the run appears live on the board exactly like a daemon-dispatched one. | Inline verification |

## Non-goals

- No change to the automation setting's storage or the projects CLI surface.
- No new runner kinds; codex and claude resolution only.
- No retry policy changes for runs that genuinely started.

## Implementation notes

Builder appendix — verify paths before editing.

- Dispatch gate: locate the daemon poll/dispatch loop (grep for "dispatch"
  under internal/daemon or internal/orchestrator). The project automation
  flag comes from the repo's tusker.yaml (`automation` under orchestration);
  the registry `enabled` flag lives in the daemon store. Dispatch must
  require BOTH. Log the skip at poll time, once per state change, not every
  tick.
- Incident detail: registry showed enabled:true while project tusker.yaml
  had automation:false; daemon dispatched KNW-T-0001/0002 to
  /opt/homebrew/bin/codex whose vendored binary was missing (ENOENT), while
  a working codex sat at ~/.bun/bin/codex. Reproduce both in tests.
- Second incident, same day: after disabling the project in the registry to
  stop the rogue dispatch, interactive `runs claim` returned `[NOT_FOUND]
  Task not found` for real tasks — `cmd/tusker/project_loader.go:50` skips
  loading a disabled project's notes entirely, so the runtime goes blind to
  the project's work and session-attach cannot register live runs. The
  registry flag currently conflates dispatch permission, polling, and
  visibility; A2 must split these so a dispatch-disabled project remains
  fully visible and claimable.
- Runner resolution: today it appears to take the first PATH hit and only
  then health-check (--version), turning a broken install into a failed run.
  Resolve → health-check → next candidate; consider the login shell's PATH
  (e.g. `$SHELL -lc 'command -v codex'`) since launchd PATH is minimal.
  Cache the resolved-good path per poll cycle, not forever.
- Preflight failures that never launched a worker should surface as a
  project-level need ("no working codex found"), not as per-task failed
  runs.
