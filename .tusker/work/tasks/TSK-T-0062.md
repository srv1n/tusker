# S46: Qualify fresh, migrated and tool-independent documentation journeys

## Story and implementation

As a releasing maintainer, I need end-to-end evidence at the real consumer boundaries. Integrate the preceding stories through existing fixtures and UI test tooling. Fresh journey: initialize, create domain/chapter/proposal/decision, link them, create a task with governing refs, read its packet, inspect CLI search/browse/backlinks, then read/edit via the actual docgraph API. Migrated journey: preview legacy inventory, apply reviewed mapping, reopen old references, inspect packet and save with CAS; injected stale-input and interrupted-apply cases must preserve data. Run the resulting Documents UI at desktop and narrow width with keyboard navigation and capture screenshots/report. A simulated API response alone is not UI runtime acceptance.

Portability journey: copy the migrated docs tree into a disposable directory without .tusker, verify ordinary relative links/assets/anchors and render representative overview/domain/proposal/decision pages with the existing Markdown renderer without Tusker runtime. No new publishing service. Regenerate maps once; build UI dist only after the concurrent dist owner has finished or handed off. Perform focused regression checks plus one delayed typecheck/build. Attribute unrelated failures and unrun installed/native boundaries precisely. Required result: docs, CLI, packet consumer and real browser all agree; queueing a task or passing a metadata check alone does not qualify the product. Return implementation defects to the responsible story rather than broad fixes outside ownership.
