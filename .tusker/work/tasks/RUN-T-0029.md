# RUN-T-0029 · Every project-loading entry point must quarantine broken registrations, not fatal

## Intent

Found live during RUN-T-0017 trial run 2, step 6. RUN-T-0021 taught `tusker daemon run` to quarantine a broken project registration (missing `WORKFLOW.md`) and keep serving healthy projects. But `tusker daemon resume` still loads all registrations through the old fatal path: with the broken kurpod registration enabled, `resume` exits with `[NOT_FOUND] .../kurpod/tusker/WORKFLOW.md` instead of resuming the healthy project.

This is the same bug class fixed once, resurfacing on a second entry point — which means the quarantine behavior lives in the `daemon run` call site rather than in the loader itself.

Semantics:

1. One shared project-loading function owns quarantine semantics: a registration that fails to load is marked quarantined with the error recorded, and loading continues for the remaining registrations.
2. Every CLI and daemon entry point that enumerates or loads project registrations routes through that function — audit at minimum: `daemon run`, `daemon resume`, `daemon stop`, `daemon limits`, `runs` subcommands, `projects list`, `reconcile`, and serve handlers.
3. An entry point whose *target* project is the quarantined one may still error loudly — refusing to resume a project that cannot load is correct; dying because an unrelated registration is broken is the bug.
4. `projects list` surfaces quarantined state and the recorded error so the operator can see what to fix.
