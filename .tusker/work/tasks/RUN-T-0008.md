# RUN-T-0008 · Daemon single-instance guard and SQLITE_BUSY resilience

## Intent

Observed 2026-07-06: a second `tusker daemon` process was started while an incumbent daemon was healthy. The newcomer opened the shared runtime store (`~/Library/Application Support/tusker/daemon.db`) and the *incumbent* crashed fatally with `database is locked (5) (SQLITE_BUSY)` — the accidental double-start killed the healthy daemon and left the queue unattended with no operator-visible signal. Two defects compound here: (1) no single-instance guard, so a double-start is possible at all; (2) SQLITE_BUSY is treated as fatal instead of a retryable contention condition.

Make the daemon safe against both. A second daemon start must detect the live incumbent and exit cleanly without touching the runtime store or disturbing the incumbent. Transient SQLITE_BUSY on runtime-store operations must be absorbed (busy_timeout plus bounded retry), never a process-fatal error. Operators must be able to see which daemon is alive from the CLI without ps-grepping.

Incident record: `.tusker/feedback/agents/2026-07-06-agent-sarav-daemon-sqlite-busy-no-instance-guard.md`.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Starting a second daemon while one is live exits nonzero with a message naming the incumbent pid, without opening the runtime store for writes and without disturbing the incumbent (regression test using the lock/pidfile mechanism). | Inline verification |
| A2 | A stale guard left by a dead daemon (pid no longer running) does not block a fresh start; the new daemon replaces it (regression test). | Inline verification |
| A3 | Runtime-store operations retry on SQLITE_BUSY with a busy_timeout and bounded backoff; contention during the retry window does not terminate the daemon (regression test with a deliberately held write lock). | Inline verification |
| A4 | `tusker automation status` reports the daemon pid, uptime, and runtime-store path so liveness is checkable without ps. | Inline verification |

## Non-goals

- No daemon supervision/auto-restart (launchd or similar is a separate decision).
- No multi-daemon coordination or distributed locking; exactly one daemon per user/host is the model.
- No change to scheduling, leases, or retry policy (RUN-T-0007 owns the capacity-accounting fix).
