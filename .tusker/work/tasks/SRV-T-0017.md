# SRV-T-0017 · Serve UI full parity: complete read views and a real write/action control surface matching the CLI

## Intent

The serve UI (`internal/serve/ui`, React + TanStack + Tailwind v4, Bun) is read-rich but action-poor. A 2026-07-08 parity audit found: the serve HTTP API is GET-only except two mutations — `POST /api/runs/:id/redrive` and `POST /api/review/batch`. Every other operation the CLI exposes has no UI path. Views exist for tasks, runs, epics, waves, needs, docs, roster, daemon, and the review inbox, but several object types (gates, evidence, decisions, feedback, wave-detail-with-land, attempt detail) are thin or absent. Full parity means the UI becomes a complete control surface: everything an operator can see and do via `tusker` from the CLI, they can see and do in the browser — safely, with every mutation returning a visible success or refusal (never silent), and canonical state authoritative in every badge.

This builds directly on the honest-UI foundation just landed (SRV-T-0014 truthful run header, SRV-T-0015 labeled runs list + valid timestamps + terminal-vs-live, SRV-T-0016 redrive feedback + canonical badges) and the repaired merge lane (OPS-T-0006 `tusker land`) and completion classifier (RUN-T-0042 `waiting_for_review`). Reuse those patterns; do not regress them.

Every new mutation endpoint must mirror the exact state transition of its `tusker` CLI command by calling the same underlying store/command path (as `handleRunRedrive` mirrors `redriveCmd`), guard on canonical state, and return a structured `{ok/refused, reason}` the UI renders inline. No hidden task closes; high/critical-risk closes still require explicit human acceptance in the UI.

Semantics (parity surface to close):

1. **Read completeness.** Every domain object reachable from the nav with a view showing what the CLI `show`/`list`/`dashboard` surfaces: task (capsule + contract + verification + evidence + gates), run (detail + attempts + event tail, live), epic, wave (with member roster + land state), gate, evidence, decision, feedback, need, doc, roster, daemon status.
2. **Task lifecycle actions from the UI.** Stage to `ready`, move `review`/`rework`/`backlog`, `cancel`, and `close`/accept — each a new serve endpoint mirroring the `tusker status`/`tusker close` path, with visible success/refusal and canonical badges. Proof-gated and risk-gated exactly as the CLI (close needs proof satisfied; high/critical need human acceptor).
3. **Merge lane from the UI.** Land a review/proof-satisfied task or a wave via an endpoint mirroring `tusker land` (OPS-T-0006), surfacing its honest landing summary (task, source→target, gate result, commit, main moved / waiting on open wave tasks) or the first actionable failure line.
4. **Gate / evidence / feedback actions.** Gate satisfy/waive/obsolete; evidence add + accept; feedback add — each from the UI, mirroring the CLI verbs.
5. **Daemon controls from the UI.** View and drive the daemon: start/stop/resume, set the active-run limit, and read circuit/limit/active-run state — mirroring `tusker daemon run|stop|resume|limits|status`.
6. **Live everywhere.** Run, task, review, and daemon views update over the existing SSE `/api/stream` without manual refresh; no NaN, no stale badges; terminal vs live stays visually distinct.

## Non-goals

- No new domain concepts or schema changes — this is a surface over the existing V7 model and CLI; if a field the UI needs is not exposed by the API, add the read/serialization for it, do not invent state.
- No weakening of guards: canonical-state authority (RUN-T-0037), proof/risk close gating, the serialized wave/land lane (OPS-T-0002/0006), and mutation-must-be-visible (SRV-T-0016) all hold.
- No auth/multi-user/remote-access work (single operator, localhost); that is a later track.
- No redesign of the honest-UI components just landed; extend them.
