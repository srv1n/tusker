## Intent
`deriveRunOperatorState` checks for any open question before anything else (changed in 421d2549), so one unanswered question pins a finished, failed or blocked run to "Waiting on you" and refuses Say and Continue. A queued continuation of a Lost run still shows Lost because the lost check runs before the queued check, which invites a duplicate Continue. ACP tool-in-flight is guessed from words in event text. The runs list computes operator state for every run, reading attempts, messages, all events and two log tails per run.

## Verified seams
- run_state.go `deriveRunOperatorState` (~52): open-question branch (~66), live-owner branch (~69), lost branch (~76), queued branch (~79); `runOperatorStateForRunWithQuietAfter` (~116) fact gathering, permission event scan (~145), ACP tool status guess (~207).
- serve_runs.go `runSummaryChecked` (~54) computing state per run.
- 421d2549 intent: a worker parked on a yield question after its owner exits must still show Waiting on you.

## Implementation contract
Locked, in this order:
1. Waiting on you when: a live owner has an open question from the current attempt or an unresolved `permission_wait`; or the attempt outcome is `waiting_for_human` (yield-parked worker, preserves 421d2549).
2. Working / Quiet as today.
3. Queued when the lease is retry_queued or unclaimed and not terminal, even if a lost/failed reason code remains from the prior attempt.
4. Lost, Blocked, Failed, Stopped, Finished as today.
An open question that does not meet rule 1 does not change the state; it still appears as a needs item.
- Permission wait = a `permission_wait` event without a later `permission_resolved` with the same request id (events emitted by acp-driver-hardening; until then the rule simply never fires).
- ToolInFlight uses typed tool status fields (`status` of the latest tool_call/tool_call_update per tool id, Claude tool_use without tool_result, Codex item.started without item.completed). No free-text matching.
- Runs list: compute operator state only for runs in the returned page, using a bounded tail (last 200 events, one log tail). Run detail keeps the full computation.

## Failure and edge cases
- Run succeeded, stale unanswered question from an earlier attempt → Finished; Continue/Say availability follows Finished. Forbidden: waiting_on_you.
- Worker parked with outcome waiting_for_human, owner gone → Waiting on you.
- Lost run continued, continuation retry_queued → Queued. Forbidden: Lost.
- 500 runs with 50k events each → runs list responds within the existing test timeout and reads at most 200 events per listed run.
