# RUN-T-0028 · Reclaim re-dispatch must consult the attempt cap: park, never dispatch-then-violate

## Intent

Found live during RUN-T-0017 trial run 2, step 2. After the daemon correctly fenced a run whose wrapper had died (AGX-T-0006, attempt_count 3, cap 3), it re-dispatched a fresh attempt — pushing the count to 4 — and one tick later its own sentinel opened the invariant circuit on `attempt_count_within_caps {attempt_count: 4, cap: 3}`. The daemon dispatched what its own invariant calls a violation.

This is the playbook's P2 principle (one eligibility source) violated on the reclaim path: dispatch-after-fence does not consult the attempt cap that the sentinel enforces. RUN-T-0023 fixed queue-vs-park for continuation retries; the reclaim/re-dispatch path needs the same single decision function.

Semantics:

1. Any actor creating a new attempt (fresh dispatch, continuation, reclaim re-dispatch, redrive) consults one shared cap check first. At the cap: park (`parked_no_progress` or `parked_retry_exhausted` as appropriate) with the reason recorded — never dispatch.
2. A parked-at-cap run is redrivable; `tusker redrive` resets the window (RUN-T-0024 semantics) and the task gets a fresh cap.
3. The sentinel's `attempt_count_within_caps` check should be unreachable through any dispatch path — it remains as defense against store corruption and operator surgery only.
4. Trial-observed nuance for the audit: attempts consumed by external interference (fence-and-replace, daemon kills) count against the same cap as failures. Decide and document whether reclaim-caused replacements should count — either answer is acceptable if the cap check and the sentinel agree.
