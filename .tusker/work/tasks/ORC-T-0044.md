# ORC-T-0044 · Schedule eligible project frontiers fairly under shared capacity

## Intent

Multiple enabled projects make bounded progress without registry-order starvation while wave, project, runner, path, and resource limits remain authoritative.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | At equal priority, a project with a waiting eligible frontier receives one global dispatch turn before another project consumes a second slot, with stable tie-breaking across restart. | See mapped verification. |
| A2 | Explicit priority, wave concurrency, project capacity, runner capacity, owned paths, disk pressure, and named resource leases constrain selection with a stable displayed reason. | See mapped verification. |
| A3 | One disabled, stale-wave, held, incompatible, corrupt, or quarantined project cannot block polling or dispatch for healthy sibling projects. | See mapped verification. |
| A4 | A targeted project mutation wakes only that project, while release of a named global resource wakes exactly the projects waiting for that resource. | See mapped verification. |
| A5 | Repeated poll, daemon restart, concurrent mutation, and capacity release cannot duplicate claims or skip a previously waiting project indefinitely. | See mapped verification. |
