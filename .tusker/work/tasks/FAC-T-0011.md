# FAC-T-0011 · Retry a failed task on its own without disturbing its neighbors

## Intent

When one piece of work in a chain fails, retrying it should re-run only that
piece — not the neighbours that already succeeded — and asking for the retry
twice should be no different from asking once. Today retry guards exist but the
retry can be fuzzy about whether it touches neighbours and whether a repeated
request piles up duplicate attempts.

This task makes retrying a single failed piece safe to repeat and scoped to just
that piece.

Done looks like: retrying a failed piece starts a fresh attempt for that piece
alone; running the same retry request twice does not create two competing
attempts; and the neighbouring pieces are left exactly as they were.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Retrying a failed piece starts a new attempt only for that piece. | Inline verification |
| A2 | Running the same retry request twice does not create duplicate competing attempts. | Inline verification |
| A3 | Neighbouring pieces are not restarted by the retry. | Inline verification |

## Non-goals

- No automatic retry on failure; a person or policy still triggers the retry.
- No change to the fan-out child cap or merge rule.
- No cross-project retry; scope is one piece in one project.
- No replay of the old attempt's transcript; that is a separate piece of work.
