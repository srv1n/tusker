# RUN-T-0002 · Named runner profiles: harness, model, effort, subagent policy

## Intent

Runner selection today is a single `default_runner` plus raw command strings. Add named profiles so work can say what kind of agent it wants: `automation.profiles.<name>` in `tusker.yaml` bundling harness (codex_app_server | codex_exec | claude-code), model (e.g. claude-opus-4-8, claude-fable-5, gpt-5.x), reasoning effort, permission/sandbox mode, and subagent policy (allowed yes/no, max concurrent). Dispatch resolves a profile per run: task frontmatter override (`runner_profile`) > lane mapping (e.g. execute lane uses a cheap profile, review lane a frontier profile) > project default. Profiles translate to the right CLI flags/env per harness (model and effort flags differ between codex and claude). This is the foundation for cost-aware routing later (AGX-T-0004 provides the measurements).

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Profiles parse and validate from tusker.yaml; unknown harness/model/effort values produce agent-legible errors. | Inline verification |
| A2 | Dispatch uses the resolved profile: task-level override beats lane mapping beats default, verified by inspecting the spawned command/env in tests. | Inline verification |
| A3 | Execute and review lanes can run different profiles on the same task (e.g. cheap execute, frontier review). | Inline verification |
| A4 | The run record and review packet name the profile, harness, and model used. | Inline verification |

## Non-goals

- No new harnesses.
