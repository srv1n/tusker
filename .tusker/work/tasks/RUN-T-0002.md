# RUN-T-0002 · Named runner profiles: harness, model, effort, subagent policy

## Intent

Runner selection today is a single `default_runner` plus raw command strings. Add named profiles so work can say what kind of agent it wants: `automation.profiles.<name>` in `tusker.yaml` bundling harness (codex_app_server | codex_exec | claude-code), model (e.g. claude-opus-4-8, claude-fable-5, gpt-5.x), reasoning effort, permission/sandbox mode, and subagent policy (allowed yes/no, max concurrent). Sandbox mode must be a first-class profile knob with at least: danger-full-access (YOLO, the operator's usual mode), workspace-write with network on, and workspace-write with network off — the codex adapter currently hardcodes networkAccess false for workspaceWrite (runner_codex_live.go:301), which blocks web search and fetching docs; profiles must expose that switch per lane. Add a guarded-yolo preset following the permissive-default-plus-denylist pattern (as recommended by the Claude Code team): full filesystem and network access, but a denylist blocks destructive commands (recursive rm outside the workspace, git push --force, git reset --hard, destructive database migrations, credential-file writes). Map the denylist per harness: Claude Code permission deny rules or a PreToolUse hook; codex execpolicy. The denylist lives in tusker.yaml so the operator can extend it. Dispatch resolves a profile per run through explicit layers, most specific wins: task frontmatter override (`runner_profile`) > routing rules > lane mapping (e.g. execute lane uses a cheap profile, review lane a frontier profile) > project default > built-in defaults. Routing rules are an ordered `automation.routing` list in tusker.yaml matching task fields (epic, risk, size, domains, title keywords) to a profile — e.g. docs-flavored tasks route to a fast cheap model, high-risk code to a frontier one; first match wins and dispatch logs which rule fired. Ship sensible built-in defaults so a fresh project needs zero profile config. The judgment layer sits above the mechanical one: the planning agent (guided by the skill) sets `runner_profile` on a task at authoring time when it knows better than the rules — rules for the common case, frontmatter for the exception. Profiles translate to the right CLI flags/env per harness (model and effort flags differ between codex and claude). This is the foundation for cost-aware routing later (AGX-T-0004 provides the measurements). Config-file layering (design reference: docs/design/competitive-notes-conductor.md): profiles, routing, and the denylist resolve across four sources, most specific wins — built-in defaults < user-global config (`~/.config/tusker/config.yaml`, cross-project personal defaults such as preferred models) < project `tusker.yaml` (committed, shared) < machine-local override (`tusker.local.yaml` at the repo root, gitignored — secrets and per-machine paths never enter the committed file). Validation reports which file a bad value came from.
