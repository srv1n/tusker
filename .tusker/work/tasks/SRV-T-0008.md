# SRV-T-0008 · Live updates: SSE event stream from the daemon poll loop

## Intent

Operator friction (2026-07-06): with the factory running live, parts of the UI update (queries on the 4s `LIVE_REFETCH_MS` poll) while others sit stale until a hard refresh — uneven refetch coverage, inherent to client polling. Replace discovery-by-polling with push: a `GET /api/stream` Server-Sent Events endpoint hosted by the daemon-embedded server (SRV-T-0007 — the poll loop is in the same process, so it is the natural event source). SSE, not WebSocket: the flow is strictly server→client for the read-only surface, SSE rides plain HTTP through the embedded single-binary server, and browser `EventSource` auto-reconnects across daemon restarts — a normal event in this system, not an edge case.

Event design: small invalidation hints, not data payloads — `{"kind": "<event>", "keys": ["runs", "tasks:AGX-T-0005", ...]}` — emitted on poll tick completion, dispatch, lease/liveness transition, task status change, and review-batch trigger (BACKEND-GAPS §6/§7). The client maps `keys` to TanStack Query keys and invalidates; the existing GET endpoints stay the single source of data. Include a heartbeat comment every ~15s so proxies and EventSource notice a dead daemon quickly. Client keeps a degraded 30–60s polling fallback when the stream is down, and the daemon-down state renders honestly (footer shows stream disconnected + last-event age, no fake green).

## Non-goals

- No WebSocket, no bidirectional messaging, no auth (localhost read-only unchanged).
- No event payload as data source — GET endpoints remain canonical.
- No durable event log (TRC-T-0003 owns event-log-as-source-of-truth exploration).
