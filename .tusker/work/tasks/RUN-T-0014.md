# RUN-T-0014 · Invariant sentinel: the daemon audits itself every tick and halts loudly on violation

## Intent

Binding design: `docs/design/prior-art-playbook.md` §1 (P1) and the fail-stop principle. Every incident so far was silent state corruption discovered by the operator, hours late, by looking at a UI. The sentinel inverts that: at the end of every reconcile tick (RUN-T-0011), the daemon checks a short list of invariants over its own runtime store; any violation means the reconciler itself is buggy — the correct response is fail-stop (halt new dispatch, keep serving reads, scream), never fail-silent.

Initial invariant set (extend as incidents occur — every future incident must add its invariant here or to the e2e suite):

1. No held lease whose task is not dispatch-eligible (the 88-attempt incident's signature).
2. No run whose attempt count exceeds the configured caps without a parked/terminal state.
3. No lease with a fresh heartbeat whose recorded `{pid, start_time}` fails liveness verification (heartbeats must not outlive their process).
4. No two active leases for one task; no lease owned by a daemon generation that is not the incumbent.
5. Spend accounted on active runs is monotonically non-decreasing across ticks (double-count/reset detection; budget layer arrives with RUN-T-0012 but the counter audit is independent).
6. `lastPollAt` advanced since the previous tick (the loop is actually looping).

On violation: dispatch circuit opens (same mechanism as the RUN-T-0012 budget circuit, distinct reason code `invariant_violation`), the violation with full detail is written to the runtime store and daemon log, `tusker daemon status` and the serve API report it first-line, and the serve UI shows a red banner. Recovery is explicit: `tusker daemon resume` after the operator (or a fix) clears the cause — the daemon never self-clears an invariant violation.

## Non-goals

- No auto-remediation: the sentinel detects reconciler bugs; the reconciler (RUN-T-0011) is the remediation for known states. Sentinel firing means unknown territory — that is precisely when automation must stop.
- No alerting integrations (mail/push); surfacing is status/API/UI only for now.
