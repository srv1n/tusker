# ORC-T-0029 · Define the canonical factory-intake routing contract

## Intent

Every installed Tusker agent follows one machine-auditable decision table that defaults multi-task planning to an inert delivery DAG while preserving read-only analysis and lightweight singleton work.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Requests to plan, decompose, task, build out, or create multi-unit implementation work route to a versioned delivery plan without requiring the user to mention Tusker, a DAG, tasks, waves, or the daemon. | See mapped verification. |
| A2 | Evaluation-only requests remain read-only, one genuine singleton may use the direct path, and structural scope rather than a keyword-only heuristic determines the route. | See mapped verification. |
| A3 | Plan creation and import grant no execution authority, while unattended work names one exact fingerprint-bound Start delivery action and never treats project setup, daemon state, release, or paid work as implied. | See mapped verification. |
| A4 | The contract distinguishes product questions the user owns from task IDs, epics, dependencies, runners, workspaces, proof modes, and other factory mechanics the agent must resolve. | See mapped verification. |
| A5 | Representative routing scenarios have stable expected modes and remedies that can be consumed by guidance tests and setup diagnostics. | See mapped verification. |
