# ORC-T-0010 · Clock-based merge windows for the daemon

## Intent

Today the daemon's batch-gate/landing cycle is period-based:
`orchestration.batch_gate.period_hours`, consumed by `scheduleBatchGateIfDue`
in `cmd/tusker/batch_gate.go` (fallback 24h when unset). The cycle fires every
N hours measured from the last run, so its phase drifts with whenever the last
run happened; there are no wall-clock windows.

The backend program runs a day/night rhythm. Think of it as trains leaving at
fixed departure times: scope that arrives late boards the next train. Fixed
departure times are exactly what stops a batch being held open by scope that
keeps arriving — on 2026-07-20 four tasks were held hostage roughly 24h because
the merge window kept sliding as new scope accreted, and nothing ever
"departed". Add configurable wall-clock windows (e.g.
`windows: ["13:00","19:00","03:00"]` under `orchestration.batch_gate` in
WORKFLOW) so the daemon runs the batch-gate/landing cycle AT those local times
rather than every-N-hours. When no windows are configured, the existing
`period_hours` path stays as the fallback.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Windows parse from `orchestration.batch_gate` config (e.g. `windows: ["13:00","19:00","03:00"]`) into an ordered set of daily wall-clock times; malformed entries (`"25:00"`, `"1300"`) are rejected with a named config error, not silently dropped. | Inline verification |
| A2 | Next-window computation is correct including across midnight: from 20:00 the next window in `["13:00","19:00","03:00"]` is 03:00 the next day; from 03:30 it is 13:00 the same day; an exact-boundary time resolves deterministically. | Inline verification |
| A3 | `tusker daemon run --once` fires the cycle when the current time is in or past an un-consumed window since the last recorded run, is a no-op between windows, and fires each window at most once per day. | Inline verification |
| A4 | With no `windows` configured, `scheduleBatchGateIfDue` uses the existing `period_hours` scheduling path unchanged (regression guard). | Inline verification |

## Non-goals

- No sub-daily, day-of-week, calendar, or holiday scheduling; windows are daily
  wall-clock times only.
- No change to what the cycle DOES (batch gate, repair-task spawn, landing) —
  only WHEN it fires.
- No timezone selector in v1: windows are interpreted in the daemon host's local
  time, and that is documented in the config comment.
- launchd/cron timers invoking `tusker daemon run --once` are the stopgap for
  fixed departure times and remain valid; this task does not remove or
  supersede that external-timer path.
