# SGC-T-0005 · Coordinate scratch cleanup with daemon dispatch

## Intent

- What this is: the scratch sweep and the background dispatcher need to agree
  about who is allowed to touch a scratch folder. Today the sweep measures a
  folder, then deletes it a moment later, with nothing preventing a freshly
  dispatched runner from starting to use that same folder in between.
- Why it matters: the window is small and the sweep already re-checks each
  folder immediately before deleting it, so this is unlikely rather than
  routine. But the only way to actually close it is for the sweep and the
  dispatcher to coordinate, and cleanup that races a live writer destroys work.
- What "done" looks like: while the sweep is deleting, the dispatcher cannot
  start new work in the affected project, and any folder belonging to a live run
  is left alone. The residual race is gone rather than merely narrowed.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | While a sweep is applying, dispatch for that project cannot start new work in scratch. | See mapped verification. |
| A2 | A scratch folder belonging to a verified-live run is never deleted, regardless of age. | See mapped verification. |
| A3 | The coordination is honored by every scratch writer, not only the sweep. | See mapped verification. |

## Non-goals

- Changing the retention policy or the TTL.
- The live-runner interlock on task close (SGC-T-0004).

## Implementation notes

Builder appendix. Raised as a HIGH finding by an external review of the SGC
epic on 2026-08-05.

- Current mitigation already shipped: `applyScratchGC` in
  `cmd/tusker/scratch_retention.go` re-walks each entry immediately before
  deleting and skips anything that stopped being stale. There is a `ponytail:`
  comment there naming the residual race. That narrows the window; it does not
  close it.
- A per-vault retention lock is justified here only because it would have real
  participants: the sweep, the daemon dispatcher, and close-time reaping. A lock
  only the sweep observes would not fix anything — check the existing lease and
  directive TTL machinery in `cmd/tusker/runtime_store.go` and
  `cmd/tusker/resource_lease.go` before adding a new primitive.
- Skipping entries associated with a verified-live run is the cheaper half and
  may be worth landing first.
- Name new tests with the substring `ScratchCoordination`.
