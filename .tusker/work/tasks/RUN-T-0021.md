# RUN-T-0021 · Daemon cold start must quarantine broken project registrations, not die

## Intent

Found live during the RUN-T-0017 re-entry trial, step 1 (cold start). With two registered projects — one healthy (`tusker`) and one stale (`kurpod`, whose `WORKFLOW.md` no longer exists because the repo predates the `.tusker/` layout) — `tusker daemon run` exited immediately with:

```
[NOT_FOUND] /Users/sarav/Downloads/side/kurpod/tusker/WORKFLOW.md: WORKFLOW.md not found
```

The registry already models per-project health (`health: "error"`, `last_error: "WORKFLOW.md not found"`), so the daemon has everything it needs to quarantine the broken registration and keep serving the healthy project. Dying instead violates the level-triggered doctrine (playbook §1 P4): one bad entry in persisted state must never take down the whole loop. This is the same failure class as a poison message wedging a queue consumer.

Semantics:

1. At startup and on every tick, a project whose vault/WORKFLOW cannot be loaded is marked `health: error` with the error recorded, skipped for dispatch, and retried on subsequent ticks (it heals automatically if the path reappears).
2. The daemon starts and serves as long as at least one project loads; zero loadable projects is still a running daemon with an honest status (idle, all projects errored), not an exit.
3. Project load errors surface in `daemon status` and `/api/daemon`; the sentinel does not treat a quarantined project as a violation.
4. Disabled projects are never polled (existing behavior preserved).

- No automatic removal of stale registrations (operator's call via `tusker projects remove`).
