## Intent
The wave overview misreports state: `serveWaveList` returns the recorded `authorization` field, so a stale authorization still shows "Auto-run on"; `MemberCount` counts every member entry including non-task members (spec paths) while the full view counts tasks only; armed waves whose tasks are all done or in review show under "Running"; unknown `?view=` values silently return the full payload; `WaveListItem` is declared twice in domain.ts; superseded-authorization directives are counted as queued in the serve recovery projection; and every self-service repair escalation for the project is attached to every wave forever.

## Verified seams
- serve_command.go: `?view=list` branch (~1910) → `serveWaveList` (~2084) with `Authorization: fallback(stringField(wave.Data,"authorization"),"disarmed")`, `MemberCount: len(members)`; any other `view` value falls through. `serveWaveSummaryFor` (~2115) counts only `serveNoteKind(task)=="task"`. `serveWaveAuthorizationState` (~2279) returns the effective state via `waveAuthorizationProjection`.
- `newServeRecoveryContext` (~2176): appends every project escalation (~2189) and every active directive (~2203); `recoveryForWave` (~2294/2303) sets `Queued` from any directive for a member, regardless of its authorization fingerprint; escalations attached at ~2294/2359 without wave/task scoping. `SelfServiceRepairEscalation` has `RecordID` (adaptive_reconcile.go ~320).
- WaveList.tsx ~53: "Running" = `tone(wave)==="on" && running(wave)`; operator has UNCOMMITTED edits here — preserve.
- domain.ts ~908 and ~921: two `interface WaveListItem` declarations (one with `recovery`).

## Implementation contract
Locked:
- List `authorization` is the effective state from `serveWaveAuthorizationState` (e.g. `stale`), not the recorded field.
- `memberCount`/`doneCount` count task members only, matching `serveWaveSummaryFor`.
- `view` accepts `list` or empty; any other value → 400 `{error:"unknown view"}`.
- "Running" requires at least one non-terminal member with a live run or dispatching lease; armed waves with all members done/review render under Done/Review wait, never Running. A queued directive is Queued, never Running.
- Serve recovery ignores directives bound to a superseded wave authorization (fingerprint/authorized_at mismatch, same test as direct_wave_authority.go ~1745) when computing `Queued`, and attaches an escalation only to the wave/task whose member `RecordID` it names.
- One `WaveListItem` interface (with optional `recovery`).
Out of scope (owned elsewhere): deleting/expiring superseded directives at the store (TSK-T-0040 reservation reconciliation; direct_wave_authority.go `queueAuthorizedWaveFrontier`); the doctor's `doctor-stale-reservation` finding (TSK-T-0038, execution_doctor.go); the shared diagnosis rendering and safe-repair controls (TSK-T-0045). Report in the task log if the doctor still resurfaces the stale reservation after `wave start`, naming TSK-T-0040.

## Failure and edge cases
- Wave recorded `authorization: armed` with material changed since → list shows `stale`, tone not "on".
- Wave with members [task A, spec path] → memberCount 1.
- Armed wave, members all `done` → not in Running. Armed wave with one member in review and no live run → not Running.
- `GET ...waves?view=bogus` → 400; `?view=list` and no view unchanged.
- Directive for member X bound to the previous authorization fingerprint → wave not Queued; a directive bound to the current authorization → Queued.
- Escalation for record R in wave W1 → shown on W1/R only; W2 shows none.
