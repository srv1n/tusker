# ORC-T-0074 · Show the multi-agent execution tree and unbound inbox

## Intent

The existing operations experience gains a focused execution drill-down where operators can recognize named work, follow managed and provider-owned children, repair allowed bindings, and understand gaps or attention without opening raw logs.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | Wide and narrow views render wave or direct roots, task attempts, retries and resumes, managed children, provider children, names, ticket and wave links, ownership badges, and active, failed, and needs-attention counts without flattening the graph. | See mapped verification. |
| A2 | Search and filters cover execution name, task, wave, provider ID, agent type, source, binding, and lifecycle, and detail views expose the convergent timeline, parent/root links, source cursors, capabilities, and partial-visibility reasons. | See mapped verification. |
| A3 | An explicit unbound inbox supports rename and guarded attach flows, previews authority impact, reports conflicts and the binding boundary, and never implies earlier history became proof eligible. | See mapped verification. |
| A4 | Controls distinguish Tusker-managed, parent-only provider control, provider-owned read-only, unknown, and stale capability states; no unsupported child stop, resume, proof, claim, arm, land, release, or spending action appears. | See mapped verification. |
| A5 | Keyboard, screen-reader, loading, empty, stale, reset, gap, provider unavailable, and large fan-out fixtures remain understandable and reuse the existing generic factory operations navigation rather than adding a competing top-level product. | See mapped verification. |
