## Intent
The operator will qualify this work by hand before promoting a real project (decision D6). The existing real-work test repository (`tusker demo seed|run|wait|check|reset` and scripts/test-real-work-project.sh, spec real-work-test-repository.md) runs happy-path waves only. Add scripted session scenarios so each failure path can be triggered on demand with a real harness, and a checklist the operator follows in the UI.

## Verified seams
- cmd/tusker/demo_cmd.go verbs; demo_realwork.go `demoRunReal`, `demoCheckRealPreconditions`, progress helper `demoProgressHelper` (~369; bounded ~60 s job that prints progress every ~5 s).
- scripts/test-real-work-project.sh modes offline|real|mixed, `--variant fail-once|reject-once|cancel`, `--require-harness`, `--profile`, `--proof-dir`.

## Implementation contract
Locked:
- New `tusker demo session --repo <dir> --harness claude-code|codex_exec|muse|devin --scenario <name> [--profile <p>] --json` runs one scenario against the seeded standalone task and writes a proof JSON (scenario, harness, native session ids before/after, attempt ids, states observed with timestamps, pass/fail per check, proof label `fixture` or `live-provider`).
- Scenarios: `restart` (kill the daemon mid-run; run keeps going, same attempt, zero new attempts), `kill-worker` (kill the worker; Lost; Continue; same native session id), `say-hard` (Say mid-run; interrupt, resume same session, message visible in the transcript), `say-soft` (Claude only; message reaches the worker between tool calls without interrupt), `ask-wait` (task prompt makes the worker ask via MCP with wait; Waiting on you; answer via `tusker message reply`; worker continues), `ask-nowait` (answer arrives on the next continue), `stop-continue` (Stop; Stopped; Continue; same session), `start-fresh` (new session id; history kept), `permission-deny` (profile denies a tool the task needs; Blocked with a typed reason; fix; Continue).
- Scenarios the harness does not support are reported `unsupported` with the driver's declared reason, never skipped silently.
- The script gains `--variant session:<scenario>` and `--variant session:all`, running in `real` mode only, one harness at a time.
- Offline lane: the same scenarios run against fake harness binaries in `TestDemoSessionScenariosFixture`, so CI covers the orchestration without providers.
- docs/system/session-testing.md: a per-harness manual checklist for the operator in the Serve UI (what to click, what the run page must show, what counts as a pass), the exact CLI commands, and the reset command between runs.
Proposed: flag spellings beyond those above.

## Failure and edge cases
- Scenario started while another run is active in the demo project → refuse with the active run id.
- Harness not installed or not logged in → `unavailable` with the preflight reason, exit non-zero only when `--require-harness` names it.
- Daemon not running for real mode → refuse with the start instruction; never start the daemon itself.
