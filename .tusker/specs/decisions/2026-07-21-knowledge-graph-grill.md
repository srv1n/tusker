# Decision log: the knowledge-graph discussion (2026-07-21)

Same-day follow-on to [[2026-07-21-factory-grill]]. The trigger: the operator
reviewed the freshly built `docs/system/` set and named the real gap — the
documentation system existed only because "a human hammered the agent"; it
must be self-scaffolding, self-updating, and DAG-navigable in ANY repo Tusker
initializes. This log records the discussion that shaped [[knowledge-graph]].

---

## K1 — Should the doc system be built into Tusker itself?

**Operator said:** "You shouldn't come after a human hammers the agent...
where the hell is the doc, where is the canonical document. It should sort of
be a self-updating, self-this thing and when the tickets are created, it
should reference those things... And that entire node structure should also
be organized like a DAG of sorts so that somebody starting knows, at a very
high level, this is what the product is, it branches into four different
sections, and this is how we can navigate from one to the other."

**Locked:** `tusker init` scaffolds the doc tree, spec/decision folders, and
spec skill in every repo; typed front-matter edges make the DAG explicit and
machine-walkable; tickets reference specs which reference docs.

---

## K2 — How do agents find the right doc, and how is duplication prevented?

**Asked/considered:** local embedding database vs ripgrep + front-matter vs
CLI-native retrieval.

**Operator said:** "The biggest problem with documentation is just keeping it
up to date as discussions change... We have to absolutely solve that problem
no matter what way — whether a local embedding database, multiple grep
commands, proper front matter, or the CLI itself supports it in a way that's
easy to parse and chunk and do keywords and quickly get to the answer. The
last thing you want is duplicate documentation, two versions of the same
thing, an underscore v2 v3... the next time you read the wrong one
accidentally and go down that path." Also: it must stay easy for humans —
"the language, the style, the structure."

**Recommendation and ruling:** embeddings rejected — the corpus is small by
design and routing needs exactly one deterministic answer; semantic search
returns near-duplicates and fights the dedup goal. Locked: `docs find`
(deterministic keyword routing over front-matter/headings), `docs new`
(refuses duplicate subjects), unique `subject` keys, version-suffix filename
lint, explicit tombstone supersession, machine-checked readable shape, one
corpus for humans and agents.

---

## K3 — Hand-maintained map or generated?

**Operator said:** "I almost feel like the map and the graph of things should
be auto-generated by running a script, not manually maintained... that way it
forces this sort of structure through this whole diagram."

**Locked:** All maps/indexes/diagrams are generated by `tusker docs map` from
front-matter edges; the generator refuses malformed graphs (that refusal IS
the structural lint); validate diffs committed artifacts against a fresh
regeneration (gofmt pattern). Humans and agents declare edges and write
prose; they never draw the picture. This merged the planned "graph-walk lint"
and "map renderer" into one component.

---

## K4 — Should decision logs appear in `docs find` results?

**Asked:** index decision logs directly, or reachable only through specs?
Recommended: index them, ranked last.

**Operator said:** "Yeah, let's do the docs find." (Accepted the
recommendation.)

**Locked:** Decision logs are indexed, ranked below canonical docs and specs.

---

## K5 — Doc-touch rule: blocker or warning?

**Asked (after expanding the rule mechanics at the operator's request):**
when a task's diff implicates a canonical doc via `describes:` paths and
carries neither a doc edit nor a waiver row, refuse the close (blocker),
warn first then flip (probation), or warn only? Recommended: blocker,
because warnings rot.

**Operator said:** Chose "Warning first, blocker later" — a probation period
(a wave or two) to tune `describes:` paths and false-positive rates, then
flip to blocking.

**Locked:** Warning-first rollout with an explicit planned flip to blocker;
the flip is a config change, not a rebuild.

---

## K6 — What about existing repos with legacy documentation?

**Operator said (mid-session, while artifacts were being written):** "We have
a lot of repositories where we won't be starting fresh... few hundreds of
thousands of lines of code. How will we enforce this? There's a bunch of
documentation that's already sitting. We need instructions to get those in
line with this architecture."

**Ruling:** No big-bang migration. `tusker docs adopt` inventories legacy
markdown, an agent proposes per-doc dispositions (promote / merge /
tombstone / leave), the operator approves the triage table as a whole. Canon
seeds top-down (overview + one doc per subsystem); `describes:` coverage
grows organically via the doc-touch warning. The non-negotiable floor from
day one: one findable answer per subject — unpromoted legacy docs become
tombstones so `docs find` never routes to stale content.

**Locked:** As ruled; `docs adopt` is part of the KNW epic, exercised first
on a real brownfield repo (rzn) as its acceptance artifact.
