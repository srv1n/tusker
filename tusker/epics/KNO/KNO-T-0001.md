# KNO-T-0001 - V6 schemas and path layout

## Agent capsule

- Essence: define the V6 note model and vault layout that all later work depends on.
- Next action: change schemas/templates/init/migration in one vertical slice, then prove a fresh V6 vault validates.
- Read next: `tusker/docs/spec/tusker_v6_rfc.md`, `cmd/tusker/schema.go`, `cmd/tusker/v5_templates.go`, and `skill/assets/templates`.
- Avoid: implementing route search, freshness, or publication behavior in this task.

## Intent

Introduce the breaking V6 model: `domains/` as source truth, `tusker.domain/v6`, `tusker.knowledge/v6`, V6 task/epic knowledge fields, and starter templates/profiles that no longer create `tusker/docs/**` as canonical source.

## Read this when

Read this task when changing note schemas, init output, validation shape, templates, or migration scaffolding for V6.

## Scope

In:
- V6 frontmatter structs or parser support for domain, knowledge, task, and epic records.
- `tusker init --profile generic|library|app|cli|infra|tusker` starter layouts.
- V6 templates for `tusker/SKILL.md`, domain `INDEX.md`, domain `CANON.md`, knowledge pages, tasks, and epics.
- Migration scaffolding from V5 paths/fields to V6 paths/fields.

Out:
- Full Markdown route index.
- Freshness fingerprint calculation.
- Publication output changes beyond preventing new V6 source from using `docs/`.

## Acceptance contract

| # | Outcome | Proof required | Docs impact |
|---|---|---|---|
| 1 | Fresh init can create a minimal V6 vault with `tusker/SKILL.md`, `domains/codebase`, `domains/product`, epics, policy config, and generated directory placeholders. | Focused init/template tests plus fixture inspection. | `spec/v6-rfc`, `reference/templates` |
| 2 | Validator recognizes V6 domain, knowledge, task, and epic schemas with required path and section rules. | Validator tests for valid and invalid fixtures. | `reference/validator` |
| 3 | Existing V5 migration path has an explicit V6 migration entry point and compatibility stance. | Migration tests or dry-run output showing planned moves and field rewrites. | `spec/v5-overview`, `spec/v6-rfc` |
| 4 | New V6 templates do not create authored `tusker/docs/**` as source truth. | Test or snapshot showing created paths under `tusker/domains/**`. | `spec/v6-rfc` |

## Constraints

- Keep canonical source as plain Markdown plus YAML frontmatter.
- Do not create a central authored node registry for V6 knowledge pages.
- Preserve V5 validation/migration enough to move existing vaults deliberately.
- Make the breaking vocabulary explicit; do not hide V6 behind `docs` naming.

## Escalate if

- Fresh init cannot support V5 and V6 without confusing flags.
- Migration would silently destroy task proof or docs-resolution history.
- Existing generated files appear to be the only source for required data.

## Deliverables

- V6 schema definitions and validation paths.
- V6 init profiles and templates.
- Migration dry-run/report shape for V5-to-V6 path and field changes.
- Focused tests for valid/invalid V6 vault fixtures.
