# ORC-S-0003 - Render WORKFLOW.md body as strict prompt template

## Problem

Tusker has a WORKFLOW.md body, but daemon dispatch currently uses a hard-coded generic prompt. That makes the body decorative and pushes too much project behavior into the global skill bundle. Symphony's biggest design lesson is that the workflow body is the product: it is the project-specific runbook the agent actually follows.

## Scope and non-goals

In scope:

- Render WORKFLOW.md body into the first-turn prompt.
- Use strict template semantics: unknown variables or filters fail the attempt.
- Expose stable context for project, workflow, note, attempt, turn, workspace, runtime, and trust profile.
- Preserve a useful default body for projects that do not customize yet.
- Record render failures as attempt failures, not daemon crashes.

Out of scope:

- Continuation turn implementation. That lands in ORC-S-0011.
- Optional tool/MCP extension bridge. That lands in ORC-S-0015 after supervisor and proof surfaces are ready.
- A public plugin system for custom template filters.

Non-goals:

- Make the skill bundle obsolete. The body composes global guidance; it does not replace all reusable docs.
- Allow silent missing variables.

## Acceptance criteria

- [x] renderAttemptPrompt renders the workflow body, not a fixed seven-line prompt.
- [x] The rendered prompt includes note identity, workspace, attempt, evidence expectations, and workflow body text.
- [x] Unknown template variables fail the attempt with a clear error and recorded artifact.
- [x] Generated WORKFLOW.md includes a real starter runbook, not placeholder prose.
- [x] Tests cover valid template, invalid variable, missing section, and context shape.

## Plan

1. Pick the template engine and strict-mode behavior explicitly.
2. Define the render context as a small typed structure.
3. Replace hard-coded prompt rendering with template rendering.
4. Persist rendered prompt artifacts as before.
5. Update default WORKFLOW.md body with the project runbook skeleton.

## Considered and rejected

- **Use Go text/template without strict missing-key behavior** - Rejected unless strict failure can be configured reliably.
- **Keep the body as human docs and add a separate prompt file** - Rejected because it splits project behavior across two files.

## Decision

The workflow body is the first-turn prompt template. This makes project behavior versioned and reviewable.

## Verification plan

- Unit tests for render context and strict failures.
- Integration test: daemon dispatch writes a prompt artifact containing rendered note/workspace values.
- Docs test: generated workflow body contains all required sections.
- Manual inspection of one rendered prompt artifact from a daemon run.
