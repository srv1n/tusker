# ORC-S-0005 - Enforce per-state concurrency caps

## Problem

Tusker parses agents.max_concurrent_agents_by_state but does not enforce it. That is a silent promise break. Users can configure at most one rework and still get multiple rework sessions.

## Scope and non-goals

In scope:

- Enforce per-status concurrency caps during dispatch.
- Make counting use durable note status, not stale runtime guesses.
- Define precedence among global cap, project cap, runner cap, and state cap.
- Expose cap blocks in status/debug output.

Out of scope:

- Risk-profile dispatch routing. That lands in ORC-S-0012.
- Remote worker pool scheduling.

Non-goals:

- Use per-state caps to replace dependency checks.
- Silently ignore unknown state names in workflow.

## Acceptance criteria

- [x] If rework: 1 is configured, a second rework note is not dispatched while one is running.
- [x] State cap enforcement works alongside global and per-project limits.
- [x] Workflow validation rejects caps for states that are not in the tracker state set.
- [x] Runtime rows record state-cap skip reasons in last_error for runs JSON/inspect consumers.
- [x] Tests cover cap hit and cap miss.

## Plan

1. Define cap precedence and document it.
2. Build a current-status count map during each project poll.
3. Check state cap before dispatch.
4. Record cap-blocked reason for operator visibility.
5. Add tests for multiple active statuses.

## Considered and rejected

- No high-risk alternatives recorded for this medium/low-risk story.

## Decision

Per-state caps are part of workflow policy and must block dispatch. They do not mutate note state.

## Verification plan

- Unit test cap evaluator.
- Integration test with two rework notes and cap of one.
- Integration test state cap does not block unrelated active status.
- JSON output includes blocked reason when practical.
