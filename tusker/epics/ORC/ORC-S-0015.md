# ORC-S-0015 - Add optional tool and MCP extension bridge

## Problem

Codex and Claude Code already bring their own harness tools for code work: file edits, shell, approvals, and sandboxing. Tusker should not replace that harness.

The gap is task-specific extension. Some runs need a constrained Tusker tracker tool, a project MCP, browser automation, design asset lookup, or another helper that should be available only when workflow policy allows it. That surface needs to be optional, scoped, audited, and runner-aware.

## Scope and non-goals

In scope:

- Define workflow schema for optional tool/MCP extension manifests.
- Implement a runner-neutral extension model that Codex and Claude Code adapters can translate into native capabilities where supported.
- Start with safe read-only Tusker tools: list, show, handoff.
- Add narrow write tools later: update workpad, attach evidence, review comment, propose follow-up, possibly set status.
- Route Tusker mutations through optimistic writer semantics.
- Record extension availability, tool calls, denials, and results in normalized events.

Out of scope:

- Building a general MCP marketplace or MCP server product.
- Cross-project mutations by default.
- Replacing the CLI for humans.
- Replacing Codex/Claude native harness tools.

Non-goals:

- Let tools bypass risk gates.
- Expose raw filesystem write access through tools.
- Make tool injection mandatory for baseline orchestration.

## Acceptance criteria

- [x] Workflow can opt into a tool/MCP extension manifest by risk profile or task.
- [x] At least one runner can call a read-only Tusker extension when policy allows it, with Codex as the first target and honest degradation elsewhere.
- [x] Claude Code either receives an equivalent safe extension or blocks with an honest unsupported-capability reason.
- [ ] Write tools are scoped to the current project and current attempt unless workflow explicitly says otherwise.
- [ ] Tool writes use the same optimistic concurrency checks as CLI commands.
- [x] Tool calls appear in run events for the Codex bridge.
- [x] The CLI remains available as fallback and human interface.

## Plan

1. Define extension schema and permission model in docs first.
2. Implement runner-neutral manifest parsing.
3. Implement read-only Tusker tools before write tools.
4. Wire Codex native tool handling and Claude degraded handling.
5. Extract reusable note mutation helpers from CLI commands where needed.
6. Add tests for allowed, denied, and unsupported extension calls.

## Considered and rejected

- **Make injected tools the core orchestration model** - Rejected because Codex and Claude already own their coding harnesses. Tusker owns scheduling, state, safety, and evidence.
- **Keep CLI shell-out forever as the only extension seam** - Rejected as the primary long-term seam because the daemon cannot mediate every action.
- **Expose all CLI commands as tools** - Rejected because tool surface must be smaller and policy-aware.

## Decision

Tool/MCP injection is optional extension infrastructure. It lands after runner/session supervision and proof layers are stable.

## Verification plan

- Fake app-server tool-call test for read-only Tusker tool.
- Claude unsupported-extension test returns a clear blocked/unsupported reason.
- Mutation test with optimistic conflict.
- Permission test rejects cross-project or unsafe calls.
- Run event log records tool input summary and result.

## Evidence

2026-04-28 implementation slice:

- Added workflow `extensions` policy with `enabled`, `allowed_tools`, `allowed_mcps`, and `allow_tusker_read_tools`.
- Validation is conservative: extensions are disabled by default; wildcard is allowed only as a sole `*` entry.
- Runner launch environment exports the extension policy and JSON manifest for adapters.
- Codex live runner recognizes native tool-call request shapes and fails closed by default.
- Implemented read-only `tusker.show_current` for Codex when workflow policy allows it.
- Codex extension calls, denials, and results are written to normalized run events.
- Claude Code does not fake support. If native extension tools are requested, the live adapter emits `extension_bridge_unsupported` and fails with an explicit unsupported-capability reason.
- CLI shell-out remains available as the human and fallback interface.

Still open by design:

- Write tools are not accepted yet. They need extracted optimistic writer helpers and conflict tests before Tusker should let agents mutate tracker state through the bridge.
- MCP pass-through policy exists in schema, but no native MCP bridge is exposed yet. That is the next safe slice after read-only tool calls.

## Kill list

- Remove any tests, docs, or defaults that still imply the old unsafe/unenforced behavior.

## Rollout

Start with read-only Tusker tools. Keep status mutation conservative until optimistic writer semantics are extracted and tested. MCP pass-through remains policy-only until a runner-native bridge exists.
