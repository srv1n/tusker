## Problem

The design only works if a human can resume a session, inspect a run, understand why something is blocked, and review proof without spelunking raw logs. Tusker needs operator docs and Obsidian views that match the new runtime model.

## Scope and non-goals

In scope:

- Document run, attempt, turn, session, continuation, retry, and resume concepts for operators.
- Document runs inspect, runs events, sessions, retry, interrupt, and daemon status commands.
- Add or update Obsidian Bases/views for active runs, stale runs, review packets, follow-ups, blocked work, and high-risk work.
- Sync docs into the site.
- Document manual QA recipes.

Out of scope:

- Building a web dashboard.
- External tracker docs.
- Full API reference for future tool host.

Non-goals:

- Make operators read raw SQLite tables.
- Describe features that are not implemented yet as shipped behavior.

## Acceptance criteria

- [x] Developer docs explain the runtime object model and resume cases.
- [x] User/operator docs explain how to inspect, interrupt, retry, and review a run.
- [x] Obsidian views expose active, blocked, verification, human-review, and follow-up work. Stale remains a future refinement once run age is available to Bases.
- [x] Docs clearly mark Codex as first-class and Claude as degraded if that remains true.
- [x] Site sync/build includes the updated docs.
