# ORC-T-0018 · Ship Codex-only Obsidian-to-review daemon loop

## Intent

Ship the first honest Codex-only orchestration cut: a human flips a Tusker task to `active` from Obsidian or the CLI, a local daemon picks it up, runs Codex through `codex app-server` in the prepared workspace, records attempts/turns/sessions/events outside markdown, writes a useful review packet, and moves the task to `review` for human verification.

This is the integration milestone for the Symphony-style workflow. The goal is not to finish every ORC idea; the goal is to make one local loop real and demonstrable.

## Scope

In:
- Wire the existing daemon/project/run command implementations into the CLI behind an internal/operator surface.
- Register and run this repo as a daemon project using the existing runtime store under `DefaultStateRoot`.
- Make the Codex app-server adapter match the current Codex app-server protocol and reject fake resume semantics.
- Prove dispatch from markdown status: only `active` and `rework` tasks are executable.
- Run Codex in the prepared workspace, never the source repo root.
- Persist attempts, turns, sessions, normalized events, raw logs, prompt packets, and supervisor decisions.
- Generate a review packet with enough substance for a human to verify the run.
- Update Obsidian/dashboard output so a human can see active/review/blocked work and live-run state without reading SQLite.
- Update runtime, CLI, Obsidian, and adoption docs to describe only behavior that actually ships.

Out:
- Claude Code parity, Gemini support, Linear/Jira adapters, SSH worker pools, a cloud dashboard, and a web UI.
- Optional tool/MCP extension bridge work except where needed to keep Codex app-server approval/tool requests safe.
- Automatic close. The daemon may move a task to `review`; humans or explicit verification commands close it.
- Full transcript storage in markdown or SQLite.
- Rebuilding the whole ORC stack before getting one Codex path working.

## Constraints

- Codex-only means Codex is the only required live runner for this milestone. Claude paths may remain compile-clean but are not allowed to define the product contract.
- Do not put leases, process ids, retry timers, turn status, token totals, or session refs into task frontmatter.
- Do not promote `ready` tasks automatically. `ready` means shaped; `active` or `rework` means executable.
- Do not auto-close tasks. Review is the daemon handoff boundary.
- Do not claim exact same-thread resume after daemon restart unless the current Codex app-server protocol proves it. If the best safe behavior is forked continuation, record that as `fork_thread` with parent session metadata.
- Keep the public V5 workflow task-centric. Runtime commands can exist, but they should be framed as operator/internal inspection and control, not the normal task lifecycle.
- Do not add a web dashboard to paper over missing CLI/runtime state.

## Escalate if

- Current `codex app-server` cannot support the required thread lifecycle without an upstream protocol change.
- The daemon cannot safely distinguish a clean "done" turn from an app-server process exit.
- The review packet would need to parse unbounded raw transcript text to find proof.
- Obsidian Bases cannot represent live-run state from generated files without misleading users.
