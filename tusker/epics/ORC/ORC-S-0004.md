# ORC-S-0004 - Resolve review-state canon and schema drift

## Problem

The specs say a successful attempt moves to review_state requested, while current code also uses verification_requested. Two near-synonyms in a lifecycle enum are how review and retry bugs creep in. Tusker needs one explicit model: either keep a two-step verification distinction and document it everywhere, or collapse to one review state.

## Scope and non-goals

In scope:

- Make a final decision on verification_requested versus requested.
- Update schema, daemon review handoff, review commands, indexes, skill docs, templates, and specs consistently.
- Add migration or compatibility handling for existing notes.
- Update tests that currently expect the old value.

Out of scope:

- Changing the whole durable status state machine.
- Changing risk/attestation gates beyond the review-state drift.

Non-goals:

- Preserve two states just because both already exist.
- Let CLI, daemon, and docs disagree.

## Acceptance criteria

- [x] There is exactly one documented review-state model across specs, code, templates, and skill references.
- [x] tusker validate enforces the chosen model.
- [x] Daemon handoff and review commands produce valid notes under the chosen model.
- [x] Generated indexes and Obsidian views use the chosen model.
- [x] Migration notes explain how old notes are handled.

## Considered and rejected

- **Keep both states without distinction** - Rejected because validation would encode ambiguity.
- **Collapse immediately without migration handling** - Rejected because existing generated vaults may contain verification_requested.

## Decision

One lifecycle model only. The implementation may include compatibility migration, but product semantics must be singular.

## Verification plan

- Unit tests for allowed review states and invalid transitions.
- Smoke test daemon success to review handoff.
- Smoke test verify, approve, request changes.
- Validate a migrated note with the old state if compatibility is retained.

## Evidence

No execution evidence yet. Attach implementation artifacts, test output, review packet links, screenshots or videos where required by risk and surface.

- Chosen model: keep `verification_requested` distinct from `requested` because verification and human review are separate gates.
- Updated docs/specs/01-vault-tracker.md and docs/specs/06-review-rework-retry.md to match the code/schema/template reality.
- Existing schema already validates `none`, `verification_requested`, `requested`, `changes_requested`, `approved`; validation passed after docs alignment.

## Kill list
