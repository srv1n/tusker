# ORC-S-0002 - Move Codex trust policy into WORKFLOW.md

## Problem

Codex approval and sandbox policy are currently hard-coded in the runner. That means low-risk docs work and critical destructive work get the same authority posture. For an unattended local daemon, that is a bad default.

Trust posture is product policy. It belongs in WORKFLOW.md, then later in risk-tier trust profiles.

## Scope and non-goals

In scope:

- Add explicit Codex policy fields to WORKFLOW.md schema and validation.
- Support approval policy, thread sandbox, turn sandbox policy, turn timeout, read timeout, and stall timeout fields.
- Pass supported policy values into Codex app-server thread and turn requests.
- Choose a safer default than silent danger-full-access plus never-ask.
- Document compatibility behavior for existing workflows.

Out of scope:

- Full risk-tier profile routing. That lands in ORC-S-0012.
- Tool-host permission policy. That lands in ORC-S-0015.
- Claude Code parity.

Non-goals:

- Ban high-trust operation. Users may opt in explicitly.
- Create a hidden global policy outside the project workflow.

## Acceptance criteria

- [x] WORKFLOW.md accepts validated Codex policy fields and rejects unknown/invalid values.
- [x] Codex app-server thread/start and turn/start receive policy from workflow data where supported.
- [x] Default generated workflow is explicit about the selected trust posture.
- [x] Existing workflows get intentional defaulted policy values through the workflow loader.
- [x] tusker workflow init writes the new fields.
- [x] Tests prove runner constants no longer own approval/sandbox policy.

## Plan

1. Extend Workflow.Codex with policy fields and safe defaults.
2. Validate enumerated values and timeout ranges.
3. Thread policy through StartRequest/ResumeRequest or access workflow policy at runner boundary.
4. Apply thread-level fields only on thread start/fork and turn-level fields on turn start.
5. Update workflow docs and default template.

## Considered and rejected

- **Keep current hard-coded defaults for compatibility** - Rejected because the current defaults encode a high-trust posture without project consent.
- **Use environment variables only** - Rejected because workflow policy must be versioned with the project.

## Decision

Codex trust posture is workflow data. High-trust mode remains possible, but it must be visible and intentional.

## Verification plan

- Unit tests for workflow validation and default workflow rendering.
- Fake app-server test confirms policy values in thread/start and turn/start payloads.
- Invalid policy values mark workflow invalid and keep last-known-good behavior once reload support lands.
- Manual test with a custom workflow policy and fake app-server capture.

## Evidence

No execution evidence yet. Attach implementation artifacts, test output, review packet links, screenshots or videos where required by risk and surface.

- Added Codex policy fields to Workflow and CodexPolicy: approval_policy, thread_sandbox, turn_sandbox_policy, turn_timeout_ms, read_timeout_ms, stall_timeout_ms, max_turns.
- Live Codex now passes workflow policy into thread/start, thread/fork, and turn/start.
- Safer defaults are generated in WORKFLOW.md: on-request plus workspace-write, not never plus danger-full-access.
- Verification: go test ./..., go vet ./..., site build, and Tusker vault validate passed.

## Kill list

- Remove any tests, docs, or defaults that still imply the old unsafe/unenforced behavior.

## Rollout

Default new workflows to a safer explicit local profile. Existing workflows should fail loudly or receive a documented migration default, not silently inherit hidden danger-full-access.
