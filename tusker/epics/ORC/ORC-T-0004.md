## Problem

The specs say a successful attempt moves to review status requested, while current code also uses review. Two near-synonyms in a lifecycle enum are how review and retry bugs creep in. Tusker needs one explicit model: either keep a two-step verification distinction and document it everywhere, or collapse to one review state.

## Scope and non-goals

In scope:

- Make a final decision on review versus requested.
- Update schema, daemon review packet, review commands, indexes, skill docs, templates, and specs consistently.
- Reject non-V5 notes clearly and remove old review-state outputs.
- Update tests that currently expect the old value.

Out of scope:

- Changing the whole durable status state machine.
- Changing risk/verification gates beyond the review-state drift.

Non-goals:

- Preserve two states just because both already exist.
- Let CLI, daemon, and docs disagree.

## Acceptance criteria

- [x] There is exactly one documented review-state model across specs, code, templates, and skill references.
- [x] tusker validate enforces the chosen model.
- [x] Daemon review packet and review commands produce valid notes under the chosen model.
- [x] Generated indexes and Obsidian views use the chosen model.
- [x] Validation messages explain how non-V5 notes are handled.

## Considered and rejected

- **Keep both states without distinction** - Rejected because validation would encode ambiguity.
- **Keep aliases for old review states** - Rejected because the V5 lifecycle should have one visible model.

## Decision

One lifecycle model only. Non-V5 note models are invalid; product semantics are singular.

## Verification plan

- Unit tests for allowed review states and invalid transitions.
- Smoke test daemon success to review packet.
- Smoke test verify and close.
- Validate that non-V5 notes fail clearly.
